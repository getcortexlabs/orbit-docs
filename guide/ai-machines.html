AI machines ​

An AI machine is a computer that runs models with Ollama, such as a Mac mini or a Linux machine with a GPU, and serves them to your applications. It can also run another runtime with an OpenAI compatible API. It never runs applications and is never reachable from the internet: the machine dials out to Orbit, and only applications inside the cluster can call it.

What you need ​

  • A Mac with Apple silicon, or a Linux machine, x86-64 or arm64, with systemd. Ollama is installed and running on it, with at least one model pulled, for example ollama pull qwen3:8b.
  • The machine reaches your console's address over HTTPS. Nothing is opened on the machine or on your router.
  • An administrator of the installation adds the machine.

Add a machine ​

  1. Open AI machines → Add machine, give it a name and choose Make the command.
  2. In the machine's terminal, run the command the console shows. It works once, within an hour. On a Linux machine it installs a systemd service: see Linux machines with a GPU. On a Mac it needs no sudo, and it:
    • downloads the agent from your Orbit and checks its SHA-256 before running it;
    • trades the one-time token for the machine's own key, kept in ~/Library/Application Support/Orbit/ai-machine.json;
    • installs the agent in ~/.orbit-ai/bin as a launchd agent (~/Library/LaunchAgents/com.getcortexlabs.orbit-ai.plist), so it starts at login and restarts if it stops. Its log is ~/.orbit-ai/logs/orbit-ai.log.
  3. The machine shows Online with its models, their size, quantization and what they can do (text, tools, vision, thinking, embeddings).

Use it from an application ​

  1. On the machine's page, under Projects with access, check the projects whose applications may use it and choose Save projects.
  2. In the application, open Variables. Under AI machines for this project, pick the machine, keep the name OLLAMA_HOST or change it, and choose Use the machine. Add OLLAMA_MODEL as a plain variable if the application reads it.
  3. Apply the change and deploy.

At deploy time the reference becomes this project's own address, http://orbit-ai.orbit-system.svc/ai/<machine>.<project>.<secret>. It is never stored in the application's variables, and it only answers that project's applications:

  • Another project calling it, even with a copy, gets 403.
  • Taking a project off the list stops its address at once with 403; the other projects keep working. A deploy of its applications then fails until the project is back on the list or the reference is removed.
  • The machine's page lists the applications that refer to it, under Applications using it.

Orbit tells the projects apart by the address a call comes from, which is the calling pod. A project's address therefore answers calls from that project's applications on the cluster, not from a process on a server's own network.

Most clients take it as their base URL:

python
import os
from ollama import Client

client = Client(host=os.environ["OLLAMA_HOST"])
reply = client.chat(model=os.environ["OLLAMA_MODEL"], messages=[{"role": "user", "content": "Hello"}])
  • LangChain: ChatOllama(base_url=os.environ["OLLAMA_HOST"], model=...).
  • OpenAI compatible clients: use OLLAMA_HOST followed by /v1 as the base URL, with any API key.

What an application can do:

  • Allowed: generate, chat and embed (/api/generate, /api/chat, /api/embed, /api/embeddings), read models (/api/tags, /api/show, /api/ps, /api/version), and the OpenAI compatible /v1/chat/completions, /v1/completions, /v1/embeddings, /v1/models and /v1/responses.
  • Refused with 403: pulling, pushing, creating, copying and deleting models. Manage models on the Mac.
  • Streaming: answers arrive as Ollama writes them. A request can carry up to 64 MiB, enough for images sent to vision models.
  • When the Mac is off or asleep: the call answers 503 saying the machine is not connected. It works again as soon as the Mac is back, with nothing to change.
  • Only from inside the cluster: the same path on the console's public address is refused.

The shared address ​

Machines also have one address for the whole machine, from before projects had their own. Any application in the cluster that has it can use the machine, so prefer references. Show address gives it as ready variables, and Turn off stops it once Applications using it shows nobody calling it recently. Applications that still use it get 403 from then on, and Turn it back on restores the same address.

Replace addresses gives the machine a new shared address and every project a new one. The previous ones stop at once; applications with a reference pick up their new address on their next deployment.

Linux machines with a GPU ​

The same command connects a Linux machine, x86-64 or arm64, with systemd. It finds the system and the architecture by itself, asks for sudo, and:

  • creates the orbit-ai user and installs the agent in /var/lib/orbit-ai/bin, with the machine's key in /var/lib/orbit-ai/ai-machine.json;
  • installs and starts the orbit-ai systemd service, which runs as that user with no privileges, starts at boot and restarts if it stops. journalctl -u orbit-ai shows what it does.

The machine's page shows its graphics cards, with their memory, as nvidia-smi lists them, next to the processor and the memory. Everything else works as on a Mac: pools, limits, pulling and removing models, metrics and warnings. The agent reads OLLAMA_NUM_PARALLEL and OLLAMA_MODELS from Ollama's own systemd service.

The agent reaches Ollama at 127.0.0.1:11434, where Ollama's installer leaves it. A Linux machine always starts the agent at boot; the choice between login and boot in the add dialog is for Macs.

Other runtimes ​

A machine can serve its models with a runtime other than Ollama, as long as it has an OpenAI compatible API: LM Studio, llama.cpp's server or vLLM. Connect the machine as usual, then on its page, under Runtime, choose the runtime and Save runtime. The agent switches within half a minute, with nothing to run on the machine.

  • Address: empty uses where the runtime usually answers: http://127.0.0.1:1234 for LM Studio, http://127.0.0.1:8080 for llama.cpp and http://127.0.0.1:8000 for vLLM. You can set another one, always on the machine itself: 127.0.0.1 or localhost with a port. Orbit refuses any other address, and so does the agent.
  • Models: the list comes from the runtime's /v1/models, with names only. Load and remove models in the runtime; the page follows.
  • Calls: applications call the paths under /v1, such as /v1/chat/completions and /v1/embeddings, on the same address as always. Ollama's own /api paths get 404 with a message that says which paths to call.
  • Pools: a pool can mix runtimes. A call to an /api path only goes to the machines that run Ollama.
  • Ollama only: pulling and removing models from the console and the time a model stays in memory. The page says so instead of offering them. Try a model works with every runtime.

An agent from before Orbit 0.3.0 only knows Ollama. It updates itself within an hour and then switches; the page says so meanwhile.

Keep it available ​

Start at login or at boot ​

The add dialog offers two ways to start:

  • At login, the default: the agent starts when you sign in to the Mac, with no sudo. After a restart, nothing comes back until someone signs in, unless automatic login is on.
  • At boot: the command ends with --at-boot and asks for the Mac's password once.
    • It installs the agent as a launchd daemon (/Library/LaunchDaemons/com.getcortexlabs.orbit-ai.plist) and ollama serve as another (com.getcortexlabs.orbit-ai.ollama.plist). Both run as your user, before any login.
    • Quit the Ollama app and remove it from System Settings → General → Login Items, so a second copy does not start when you sign in.

To change how a connected Mac starts, choose New connection command and run it with the other option.

What the page shows ​

Availability on the machine's page says how it comes back after a restart, as the Mac reports it:

  • whether it starts at login or at boot;
  • automatic login;
  • whether it starts up after a power failure;
  • system sleep;
  • FileVault.

It warns about each one that would leave the machine offline:

  • Starts at login without automatic login: nothing returns after a restart until someone signs in.
  • Sleep: a Mac that sleeps stops answering. On a Mac mini, turn on Prevent automatic sleeping when the display is off in System Settings → Energy.
  • Power failure: turn on Start up automatically after a power failure in the same place. Only desktops have it.
  • FileVault: with it on, an unplanned restart waits for the disk password at the Mac, and nothing starts before that, not even at boot.

Keep the model in memory ​

Ollama unloads a model five minutes after its last call, and the next call waits for it to load again, many seconds for a large model. Keep the model in memory on the machine's page changes that to an hour or to always.

Orbit adds it as keep_alive to generate, chat and embed calls that do not set their own. A call that sets keep_alive keeps it. The OpenAI compatible /v1 paths keep Ollama's default.

Status ​

  • Online: while the agent keeps asking Orbit for calls.
  • Offline: after 75 seconds without hearing from it.
  • Waiting to connect: until the first connection.
  • When Ollama does not answer, the page says so while the agent stays connected.

Agent updates ​

The agent on the Mac follows the Orbit it is connected to. After Orbit updates, the agent learns the new version from its next report, within 30 seconds, and updates itself:

  1. It downloads the new agent from Orbit while it keeps serving calls, and checks it against the SHA-256 Orbit announces.
  2. It stops taking new calls and lets the calls in flight finish, for up to two minutes. It never updates in the middle of a call it can wait for.
  3. It replaces its own binary and exits, and launchd starts the new version a few seconds later. Applications that call in that gap get 503 and can retry.

The machine's page shows the agent's version, with updating to and the new version while the update runs. When the download does not match its checksum or the binary cannot be replaced, the current version keeps running, the page says why and the agent tries again within an hour. An agent too old to talk to this Orbit is refused, and the page asks you to run the connection command again from Connection.

Agents installed before Orbit 0.2.46 do not update themselves. The page says a new agent is available; run the connection command from Connection once, and the agent follows Orbit from then on.

Retries and checked answers ​

Orbit tries a call again only while nothing of its answer has reached the application. After the first byte it never does, because a second answer would repeat or contradict what the application already read.

  • When: no machine took the call in time, the machine dropped before answering, or Ollama answered a 5xx error before sending anything.
  • Where: on another machine of the pool when there is one, else on the same machine after a second.
  • How many: 2 times. A pool changes that with Try again when a machine fails, from never to 3.
  • What the application sees: the answer carries Orbit-AI-Attempts, how many attempts it took, and Orbit-AI-Machine, the machine that answered. When every attempt fails, the application gets the last error.

Orbit also checks that an answer is whole:

  • A streamed answer that stops midway ends with one more line, {"error":"the AI machine stopped in the middle of the answer"}, the shape Ollama uses for errors in a stream. On the OpenAI compatible paths it is one more data: event with the same error. A cut answer never looks complete.
  • An answer that is not streamed ("stream": false) is kept until it is whole. If it arrives cut, Orbit tries again, and answers 502 when it keeps happening.

When a call that is not streamed asks for a JSON Schema, Orbit checks the model's text against it. That is format with a schema on /api/chat and /api/generate, or response_format with json_schema on /v1/chat/completions. A text that does not match is tried again like a failure. When no attempt matches, the application gets 422 with validationErrors and the last answer. This is the useful one for extraction work, such as turning listings into fields.

Send Orbit-AI-Validate: off on a call to skip the schema check. Whether an answer is right stays with the application: Orbit only checks its shape. A schema that refers to a file or an address is not checked.

Use and speed ​

Orbit counts every call applications make to a machine or a pool through it, and administrators see the numbers on the machine's page under Use, for the last hour, 24 hours or 7 days:

  • Calls and errors, with the tokens read and written.
  • Tokens per second for each model, from the counts Ollama sends at the end of an answer. For OpenAI compatible calls that stream, Orbit measures from the first token instead.
  • First token: how long a streamed call waited for the first words, on average.
  • Busy: how many calls the machine answered at once on average, against its limit in a pool.
  • Projects: which projects made the calls.

A pool's page shows the time calls waited in its queue, the calls it refused with 429 and which machine answered how many.

Use by project, on the AI machines page, adds every machine up per project and day for the last 7 days, in the time zone Orbit uses, so you can see who uses the machines. Only the calls that generate or embed count; listing models does not. The numbers are kept as long as the other metrics, 8 days.

Try a model ​

Administrators can test a machine from its page, without writing an application. Try a model lists the models that generate text: pick one, type a prompt and send it with Send or Ctrl or ⌘ + Enter. The answer streams in as the model writes it. For a model that sees images, you can attach one image of up to 10 MB.

The prompt takes the same path as an application's call: Orbit, the agent on the Mac, Ollama and the model. An answer proves the whole path works. Under it the page shows:

  • First token: the time from sending to the first words, as the browser measured it.
  • Tokens per second: how fast the model wrote, from Ollama's own count.
  • Answered by: the machine.
  • Model: how long Ollama took to load it, or that it was already in memory.

Nothing is stored: the prompt and the answer stay in your browser and are gone when you close the page. When the machine is offline the panel says so and does not send. When it drops after the page loaded, the panel says the Mac is not connected after about ten seconds. When the Mac takes the prompt but does not answer within a minute, for example while a large model loads, the panel says so and you can send again.

Pools of machines ​

When more than one Mac serves models, a pool puts them behind one address. Applications call that address and Orbit picks the machine for each call.

Click Create pool on the AI machines page, give it a name and tick the machines. A machine can be in more than one pool and keeps its own address. The pool's address, projects with access, shared address and references in Variables work like a machine's, from the pool's page.

For each call, Orbit reads the model it asks for and looks at the pool's online machines:

  1. Only machines that have the model take the call. When none has it, the call gets 404 with the model's name.
  2. A machine with the model already in memory comes before one that would have to load it.
  3. Among those, the machine with the most room left takes the call, so calls spread across the pool.

A machine takes at most Calls at once in a pool calls from pools at the same time. By default that is what Ollama runs in parallel: the agent reads OLLAMA_NUM_PARALLEL on the Mac, and uses 1 when it is not set. You can change it on the machine's page. The machine's own address has no limit, as Ollama queues those calls itself.

When every machine with the model is busy, the call waits for a free one, 30 seconds by default. Wait for a free machine up to, on the pool's page, changes that from 10 seconds to 2 minutes. When no machine frees up in time, or 64 calls are already waiting, the call gets 429 with Retry-After, so the application can try again a little later. When the machines with the model are all offline, the call gets 503.

Calls that ask for no model, such as /api/tags, /api/ps and /v1/models, answer with the models of the pool's online machines together. The pool's page shows each model with how many machines have it and whether one has it in memory, plus the machines online, the free call slots and the calls waiting.

Pull and remove models ​

Administrators manage a machine's models from its page, without opening the Mac's Terminal.

  • Pull a model: type its name as ollama.com/library shows it, such as qwen3:8b, and click Pull. The page shows Ollama's progress, and the pull goes on when you close the page. Stop ends it; Ollama keeps what it downloaded and resumes from there the next time. A machine pulls one model at a time, and the new model shows in the list as soon as it is ready.
  • Disk: the page shows the free disk where Ollama keeps its models. When Ollama reports a model bigger than that, Orbit stops the pull and says how much it needs.
  • Remove a model: Remove beside the model first shows who may still use it: the applications that use the machine and name the model in a variable, and when an application last asked for it. Applications that ask for a removed model get 404 until it is pulled again.

Orbit sends these commands through its own channel to the agent. An application's address still refuses pulling, removing, creating and copying models with 403. Each pull, stopped pull and removal goes to Activity with who did it.

An agent from before Orbit 0.3.0 cannot pull or remove models. It updates itself within an hour; the page says so meanwhile.

Warnings ​

Orbit warns about AI machines like it does about servers. The warnings show on the machine's card and go to the channels that follow them:

  • Offline: the machine has not reached Orbit for 10 minutes. The message gives the likeliest reason it knows.
  • Runtime not answering: the agent is connected, but Ollama, or the runtime you chose, has not answered for 2 minutes.
  • Model missing: for 5 minutes, a model that applications asked the machine for in the last day is not in its list, for example after ollama rm or a typo in the application. Orbit remembers the models asked for, per machine, from the calls themselves.

Move or remove a machine ​

  • New connection command makes a new one-time command, to reinstall the agent or move to another Mac. The current Mac keeps working until the new one connects.

  • Remove pool, on a pool's page, stops the pool's address at once. Its machines keep their own addresses.

  • Remove machine stops its key and its address at once, and takes the machine out of its pools. Calls it was answering end with 503, and calls waiting in a pool go to the other machines. To uninstall the agent from the Mac:

    sh
    launchctl bootout "gui/$(id -u)/com.getcortexlabs.orbit-ai"
sudo launchctl bootout system/com.getcortexlabs.orbit-ai
sudo launchctl bootout system/com.getcortexlabs.orbit-ai.ollama
sudo rm -f /Library/LaunchDaemons/com.getcortexlabs.orbit-ai.plist /Library/LaunchDaemons/com.getcortexlabs.orbit-ai.ollama.plist
rm -rf ~/.orbit-ai ~/Library/LaunchAgents/com.getcortexlabs.orbit-ai.plist "$HOME/Library/Application Support/Orbit/ai-machine.json"

    The sudo lines are only needed after an install at boot; the ones that find nothing say so and change nothing.

    On a Linux machine:

    sh
    sudo systemctl disable --now orbit-ai
sudo rm -f /etc/systemd/system/orbit-ai.service
sudo systemctl daemon-reload
sudo rm -rf /var/lib/orbit-ai
sudo userdel orbit-ai

Coming from an SSH tunnel ​

If you reached Ollama with ssh -R to a server, add the machine here, wait for Online, point the application at the new address, and then stop the tunnel. The agent needs no SSH key on the server.

Direct stream ​

By default the agent polls Orbit over the console's HTTPS address and sends each answer back in uploads about every 100 milliseconds. That works on any network. With more than one machine, or when every millisecond to the first token counts, administrators can turn on the Direct stream under How machines connect on the AI machines page.

With it on, each machine holds one persistent connection to Orbit:

  • A call arrives at once, pushed down the stream instead of waiting for a poll.
  • Tokens leave as the model writes them, with no batching and no new request per batch.
  • Ollama stops at once when the application gives up, instead of at the next upload.

What turning it on changes:

  • Port 7444 opens on the entry servers, outside the proxy, through the cluster's load balancer. Connections are handed, still encrypted, to the active Orbit, which listens for them on port 7445 of its own server. With more than one server, the port follows the active Orbit.
  • The port only speaks TLS 1.3 with a client certificate. Orbit signs one for each machine with its agent CA when the machine connects. A machine connected before Orbit 0.3.0 asks for its certificate once its agent has updated itself. Nothing but a machine with its certificate gets past the handshake, and removing a machine closes its stream and ends its certificate.
  • Your provider's firewall is yours to open. If a firewall or a security list sits in front of the servers, such as Oracle Cloud's, allow inbound TCP 7444 there.

The machine still only dials out. One that cannot reach the port keeps using HTTPS and tries the stream again on its own. Its page shows Connection to Orbit and, when the stream did not open, what the agent said. When a stream breaks, the calls in flight finish over HTTPS.

Address machines dial is the console's address unless you set another. Set the name or IP of an entry server when the console sits behind a proxy that only passes web ports, such as Cloudflare's.

Turning the stream off closes the port and every stream. The machines go on over HTTPS.

How it works ​

The agent never listens on the network. It asks Orbit for calls over the console's HTTPS address, runs each one against Ollama on 127.0.0.1:11434, or the runtime you chose on the machine itself, and sends the answer back in short uploads every 100 milliseconds or so. That keeps long generations alive behind the proxy's timeouts. Inside the cluster, the orbit-ai service in orbit-system points at the active Orbit, which hands each call to the machine. With more than one server, both follow the active Orbit.
