The catalog ​

New project → Catalog lists applications that install in one step: Orbit creates the project, the databases the application needs with daily backups, and the application itself, already configured to use them. Each entry pins an image version, so what you install today is what you get, and the project offers the update when its makers release a newer one.

What installing does ​

  1. Review. The entry's page lists what Orbit creates: the application with its image, port, health check and resources, each database with its size and backup schedule, and every variable with where its value comes from. Secrets are generated in your browser; the ones you need to sign in are shown once, with a copy button. Regenerate them before installing if you prefer.
  2. Create. Orbit creates the project, then the databases, then the application, the same way the Compose import does. Database variables are references, resolved at deploy time, so rotating a database's credentials later keeps working.
  3. Address. Variables that need the application's own address, such as WEBHOOK_URL or PUBLIC_URL, cannot be known before the application exists. Orbit sets them from the generated address after the first deployment and deploys again. Add your own domain afterwards under Domains, then update those variables to it.
  4. Email. n8n, Metabase, Grafana, Directus and Vaultwarden send email for invitations, password resets and alerts. When Resend is connected with a verified sending domain, an administrator can let the installation give the application its own email: a Resend key that only sends from that domain, set in the variables the application reads, such as N8N_SMTP_HOST and N8N_EMAIL_MODE for n8n or GF_SMTP_ENABLED and GF_SMTP_HOST for Grafana, all on port 465 with TLS from the start. It sends as its own name on Orbit's sending domain; a domain of its own can replace it later from its Variables.

The result is an ordinary project: deployments, logs, variables, backups and the terminal all work as for anything else.

When a step fails, the page shows what the machine reported and a Try again button on that step. An application is not started while a database it reads from is not ready, so one failure does not turn into two. What was already created stays in the project, and trying again continues from the failed step: the database, then the applications that were waiting for it, then the address.

Updates ​

A project remembers the entry and version it came from, and its overview offers what is newer. Review the update shows what would change: the new image tag, and any variables the entry gained since, with where their values come from. Applying it deploys the new image, adds the variables and records the new version. If the application's image no longer comes from the entry's repository, the image is left alone.

Newer versions come from two places:

  • The image's registry. Orbit asks it what the makers released after the running version, so a project is offered a new release soon after it is published, without waiting for an Orbit update. New releases of the image says what counts as a release. A later major version is offered apart, with a warning.
  • The catalog that ships with your Orbit. It is what new installations use, and it carries what a registry cannot say: the variables an entry gained, and the lines that cannot update in place. Updating Orbit brings the newer catalog.

Some releases cannot update the one before them in place: the application's makers ship a migration into a new installation instead. The catalog knows these lines. A project on the earlier line is offered that line's last release as its update, and See how to move on its overview lists the steps to the new one, with a link to the makers' guide. Nothing changes in the project until you follow them. Today this applies to Wiki.js 2.

What is not in it yet ​

Applications run without persistent volumes on Orbit, so the catalog holds applications whose state fits in a managed database. Uploaded files stay in the container and are lost on the next deployment unless the application can use a Space. That keeps a few popular ones out for now:

  • Plausible needs ClickHouse, which Orbit does not manage.
  • Uptime Kuma keeps its data in SQLite on a volume.
  • Ghost keeps uploaded images on a volume.

Wiki.js ​

The Wiki.js entry installs Wiki.js 3.4.0 from ghcr.io/requarks/wiki:3.4.0 with a managed PostgreSQL database. Orbit sets ADMIN_EMAIL to your email and generates ADMIN_PASS; sign in with them once the application is up. Pages and uploaded files are kept in the database, so the daily backups cover them.

After the first sign-in, open Administration → Security and turn on Trust X-Forwarded-* Proxy Headers. Orbit serves the wiki through its proxy, and without that setting every visitor counts as one address for sign-in limits and the audit log.

Coming from Wiki.js 2 ​

Wiki.js 3 does not start on a Wiki.js 2 database, so Orbit does not offer it as an update to a project installed from the 2.x entry. That project's overview offers 2.5.317, the last 2.x release, and See how to move lists the way to Wiki.js 3:

  1. Apply the update to 2.5.317 in the project. It is the release that exports for Wiki.js 3.
  2. In the wiki, open Administration → Utilities → Export for Wiki.js 3.x, keep every box checked, create the package and download it. The .wkbackup file holds password hashes, so keep it private. It is written inside the container: download it before the project is deployed again.
  3. Install Wiki.js from the catalog. It becomes a new project with its own database, and the old one keeps running.
  4. In the new wiki, sign in, open Administration → Utilities → Import from Wiki.js 2.x and select the package. The import can be repeated: what is already there is skipped.
  5. Check the pages, move your domain to the new project under Domains, then delete the old project.

The import leaves out mail, authentication and storage settings, and some Markdown is written differently in Wiki.js 3. The Wiki.js upgrade guide lists both.

Woodpecker CI ​

The Woodpecker entry installs Woodpecker Server 3.20.1 and a managed PostgreSQL database with daily backups. It does not install an agent. The server provides the UI, OAuth sign-in and webhook processing; a connected agent runs pipelines. The catalog pins the upstream woodpeckerci/woodpecker-server:v3.20.1 image, published for both AMD64 and ARM64.

Connect GitHub ​

  1. Create a GitHub OAuth App, separate from Orbit's GitHub App. Woodpecker requires an OAuth App, not a GitHub App.
  2. Enter its client ID and client secret in the installation form, plus the GitHub username of the first administrator. The client secret becomes a secret application variable. Registration stays closed (WOODPECKER_OPEN=false); the named administrator can sign in.
  3. If you do not know the address yet, temporarily register https://example.com and https://example.com/authorize in the OAuth App. After installation, Orbit displays the real homepage and authorization callback URL. Replace both temporary values before signing in.
  4. Save the generated WOODPECKER_AGENT_SECRET. Orbit generates a separate, persistent WOODPECKER_GRPC_SECRET for server authentication tokens.

Woodpecker requires a host URL even on its first start. Orbit first supplies http://localhost:8000, then replaces it with the generated HTTPS address and redeploys. If the address step fails, the installation reports that it needs attention: set WOODPECKER_HOST to the application's HTTPS address under Variables and redeploy before signing in. When adding a custom domain later, update WOODPECKER_HOST, the OAuth homepage and its /authorize callback together.

See the upstream GitHub configuration.

Connect a pipeline agent ​

Orbit publishes the server's HTTP port 8000 and probes /api/healthz. Agent traffic uses gRPC port 9000. The generated website URL does not expose that port, and the catalog does not create a runner, a Docker socket mount, Kubernetes permissions or a public gRPC ingress. Pipelines remain queued until an agent connects.

For an agent in the same Kubernetes cluster, an administrator can create a separate private Service targeting the existing deployment. Copy its namespace and deployment name from the application's Kubernetes tab; replace NAMESPACE and DEPLOYMENT below:

sh
kubectl -n NAMESPACE expose deployment DEPLOYMENT \
  --name=woodpecker-agents --type=ClusterIP --port=9000 --target-port=9000

Configure the agent with:

ini
WOODPECKER_SERVER=woodpecker-agents.NAMESPACE.svc.cluster.local:9000
WOODPECKER_AGENT_SECRET=<the generated agent secret>
WOODPECKER_BACKEND=kubernetes

Use the upstream Kubernetes backend guide to give the agent its own service account, namespace and required permissions. The additional private Service is managed outside Orbit; remove it when deleting the project. For an agent outside the cluster, provide an authenticated tunnel or a separate TLS gRPC reverse proxy as described in the upstream server guide. Do not use the website's HTTP endpoint as the agent address.

Keep the Woodpecker server at one replica. Match the agent version to the server, verify it is connected in Woodpecker's Settings → Agents, and run a first pipeline before treating the CI installation as ready. Only the administrator creates additional agent access; this installation does not change Orbit's own CI or deploy to your fleet.

Ranjit ​

Ranjit runs as a service next to your backend. Orbit creates PostgreSQL for its history and sync queue, generates RANJIT_API_KEY, and supplies the HTTPS address as RANJIT_BASE_URL. Configure RANJIT_URL and the generated key in your backend, then use the Go SDK.

The installation starts with OFX/CSV imports and no bank credentials. Add profiles through RANJIT_PROFILES_JSON; certificate, key and client-secret fields accept env:NAME references to secret variables. Redeploy after changing them. Bank API access must already be enabled for the configured accounts. The remote service exposes an API; its dashboard remains local only.

Use the managed PostgreSQL backups. No application volume is required. See the Ranjit server guide for setup and integration examples.

AbacatePay ​

Install the AbacatePay checkout example, then connect the application's Pix payments and redeploy. Open its HTTPS address, use the username orbit and the password shown during installation. The checkout displays its environment before creating a R$1.00 charge. It displays the QR code, checks Orbit's webhook signature and shows the confirmed status when you refresh the order.
