Migrating from DigitalOcean ​

In New project → Migrate from DigitalOcean, an administrator can bring applications from DigitalOcean Kubernetes (DOKS) and data from Managed Databases into one Orbit project. The flow is connect → review → create and copy → switch → verify. DigitalOcean keeps serving until you pause writes and switch DNS. Orbit never deletes the source cluster, applications or databases.

To keep managing domains whose DNS stays at DigitalOcean after the migration, connect DigitalOcean DNS once for every workspace; the migration's own token is kept only for the migration.

Connect and review ​

Use a DigitalOcean API token with permission to read Kubernetes clusters and databases. Reading workloads also needs kubernetes:access_cluster; a token restricted to inventory read permissions cannot access the cluster. Selected namespaces need Kubernetes read access to Deployments, StatefulSets, CronJobs, Services, Pods, Ingresses, ConfigMaps, Secrets and HPAs. The console clears the token field after discovery. Orbit seals source credentials on the server; API responses and browser storage never contain their values.

Select one cluster, its namespaces, the managed databases and a healthy Orbit server. A database-only migration does not need a cluster. For MongoDB, enter the logical database names if DigitalOcean only reports administrative databases. The plan lists each application's image, resources, variables, domains and any blockers. Variable values stay hidden. URLs that unambiguously identify a selected database become references to the new database.

Review memory and CPU capacity, including the maximum replicas of an autoscaler. Orbit checks available disk space when the server reports it, and checks capacity again before starting. All selected resources go into the new project's production environment. Changing a selection requires reviewing the plan again.

The plan expires after 24 hours if copying has not started. Orbit clears its discovery secrets then. Use a new connection to make a fresh plan.

Create and copy ​

Create and copy to Orbit creates the project, imports each database, tests restoring its backup, restores it into the destination and deploys the applications. Orbit uses running image digests when DOKS reports them. If a digest is unavailable, the plan warns that the image tag will be resolved during import. It does not rebuild source code.

For images in DigitalOcean Container Registry, the token also needs permission to generate Docker credentials (registry:read and registry:update). Orbit obtains a separate read-only pull credential and seals it for future deployments. The DigitalOcean API token is cleared once the import begins. Database URLs and CA certificates remain sealed until the migration finishes or is undone, so a final copy can run without that token.

If the managed database restricts trusted sources, either add the Orbit server's public IP yourself or check Allow Orbit to add this server's public IP to the selected databases' trusted sources. This optional action needs database:update; it preserves existing rules. When there are no restrictions, Orbit leaves that policy unchanged. Added trusted-source entries remain after the migration; remove them yourself when no longer needed.

Web applications start against the copied databases for review. Workers and scheduled jobs stay stopped until the final switch, to avoid consuming queues or running schedules twice. Review any external effects your web application performs at startup. You can close the page and return to the migration later; the backend persists progress and resumes after an Orbit restart.

Switch and verify ​

  1. Check the application in Orbit and resolve any errors. A failed step offers Retry; the operation log has the failure details.
  2. Pause all writes at the source, including workers, scheduled jobs and other clients of the database. Orbit requires your confirmation; it cannot detect or enforce this pause on DigitalOcean. The pause must last through the final copy and DNS verification, so its duration depends on data size and propagation.
  3. Choose Copy again and switch. Orbit stops its imported applications, copies and restores the databases again, then starts its applications and workers with the final data.
  4. If Cloudflare is connected for a domain, separately consent to changing its DNS. Orbit saves the original address records and replaces them only after the final copy and rollout. Otherwise, update your DNS provider using the records shown. Keep the original records for rollback.
  5. Choose Verify domains. Orbit checks DNS against its entry servers and requires a successful HTTPS response before marking the migration complete. Keep source writes paused while traffic is moving to Orbit.

For manual DNS, the displayed previous addresses are a resolver snapshot; keep your provider's original CNAME, proxy and TTL settings separately. For Cloudflare, Orbit preserves those settings in its rollback snapshot. An external DNS change since the plan can stop the automated switch with an outdated-preview error rather than overwrite someone else's change.

Undo ​

Before switching, Undo migration removes the project and resources this migration created in Orbit. After switching begins, undo stops the imported applications and restores Cloudflare DNS, or shows the old records for a manual change. Orbit keeps the destination data and waits for DNS verification before declaring undo complete.

Pause writes before undoing. Undo does not copy new Orbit data back to DigitalOcean: reconcile any writes made after switching before resuming the source. Do not delete the DigitalOcean resources until you have verified the move and your recovery plan.

Initial limits ​

  • Only DigitalOcean is supported. Spaces bucket copying is separate work.
  • Single-container Deployments and CronJobs are translated. StatefulSets, persistent volumes, init containers, custom security or scheduling requirements, unsupported probes and unsupported autoscaling metrics are identified and blocked. The flow does not copy volume data, custom resources or DigitalOcean load balancer configuration.
  • Environment values from ConfigMaps become plain variables and values from Secrets become secret variables. Split database connection settings and Kubernetes-internal addresses need adjustment before import; Orbit only rewrites complete, unambiguous database URLs.
  • PostgreSQL imports target 17, MySQL 8.4, MongoDB 8 and Redis 7.4. Newer source major versions are blocked. In particular, managed Valkey 8/9 cannot be imported into Redis 7.4 through this flow. Older versions still need compatible data, extensions and permissions; the restore test must pass before switching.
  • Applications keep Orbit's deployment and probe behavior. The plan reports settings it cannot preserve. No automatic source write pause, reverse data replication or zero-downtime guarantee is provided.
