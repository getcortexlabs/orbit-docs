On this page

Applications ​

An application runs from a container image or from a GitHub, GitLab or Bitbucket repository that Orbit builds on your server.

Deploying ​

  • A deployment waits up to 3 minutes for the application's health check and up to a minute for its certificate. Set ORBIT_HEALTH_TIMEOUT and ORBIT_CERTIFICATE_TIMEOUT (for example 5m) in orbit.service to change either.
  • An application that exits right after starting (a failed migration, a missing variable) fails saying that it stopped right after starting, with its exit code and its last lines, instead of as a health check that never answered.
  • Rollbacks put a previous deployment back, with the resources the application has now.

Health check ​

Open a web application's Settings → Health check to choose an HTTP path, such as /api/health, or Port accepting connections. Workers and jobs have no port and do not show this block. A path must start with /, contain no spaces and be at most 200 characters.

An instance receives traffic only after its HTTP path answers with a 2xx or 3xx within 3 seconds. Without an HTTP path, the readiness check only requires a connection to its port. The deployment waits for the instances to pass this check before switching traffic.

Save for next deploy stores the setting; existing instances keep their current probe until another deployment. Save and redeploy applies it now, using the current deployment's image without rebuilding or following a newer commit or image tag. If redeployment fails, the setting stays saved and the previous deployment keeps serving.

Uptime checks use the saved path on their next check, or / when using a port check. These checks reach the public address once a minute; they have their own timeout and success criteria.

Build and start ​

Open an application's Settings → Build and start to change how it is built and started after it was created. An application from a repository shows the build strategy, the build command, the start command and the port; an application from an image shows the start command and the port.

  • Automatic build installs the dependencies, runs the build command and starts the start command. Leave either command empty to use the one Orbit detects in the repository.
  • Dockerfile builds the Dockerfile at the root of the repository, so its own steps replace the build command. A start command, when set, replaces the Dockerfile's CMD.
  • Static files runs the build command and serves the output with nginx on the chosen port. Static files run no start command, so switching to them removes a saved one.

Sites published through a Space keep their delivery in Static publishing; this block only changes their build command. Save for next deploy stores the settings for the next deployment. Save and deploy stores them and deploys the branch's latest commit with them. If the deploy fails, the settings stay saved and the previous deployment keeps serving.

Addresses and domains ​

  • Generated addresses use sslip.io: <service>-<project>.<server-ip-with-dashes>.sslip.io in production, with the environment's name before the project's elsewhere. They work as soon as the server's ports 80 and 443 are reachable from the internet. Let's Encrypt issues their certificates over HTTP; until it does, the address answers over HTTP.

  • Custom domains need a DNS record at your provider:

    • an A record to the server's IPv4 for a root domain (example.com);
    • a CNAME to the generated address for anything under it (www.example.com).

    With more than one server receiving traffic, every domain needs an A record for each of them instead, and the domain's page lists them.

    Orbit checks every 30 seconds and routes the domain once the record points to the server. With Cloudflare connected, Orbit creates the records itself for domains in your zones. Turn off proxying (Cloudflare's orange cloud) until the certificate is issued: Orbit compares the resolved address with the server's, and Let's Encrypt validates over HTTP.

  • www and the root domain: adding example.com or www.example.com offers the other one too, checked by default, and asks where visitors land. The other one gets its own records and certificate and answers with a permanent redirect to the same path on the one they land on, so www.example.com/menu opens example.com/menu. Its card says Redirects to. Redirects never chain, and the domain visitors land on cannot be removed while another one redirects to it.

Email ​

An application can send email through the Resend account Orbit uses for its own, without anyone opening Resend. It needs Resend connected in Settings → Notifications → Email.

In the application's Variables, the Email section asks for a sending domain:

  • mail.<domain> for each verified custom domain of the application, the recommended choice: a subdomain keeps the site's reputation apart from the mail's;
  • Orbit's own sending domain, shared, for an application without a domain of its own; it then sends as its own name on that domain;
  • another domain you type.

Add email creates or adopts the domain in Resend, publishes its DKIM, SPF and DMARC records where Orbit manages the zone (otherwise it lists them to copy, and Check again asks Resend to verify them), and creates an API key that can only send, and only from that domain. Orbit's own key never reaches an application.

The application gets these variables, as references to its email, so the key stays sealed in Orbit and only reaches it at deploy:

VariableValue
RESEND_API_KEYthe application's key
SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASSWORD, SMTP_SECUREsmtp.resend.com, 465, resend, the key, true
EMAIL_FROMthe sender, no-reply@ on a domain of its own

A variable the application already has keeps its value. The variables reach the application at its next deploy. An application from the catalog that sends email gets them under the names it reads instead, with the constants it needs, such as N8N_EMAIL_MODE=smtp; removing the email removes those too.

  • Rotate key creates a new key, deploys the application with it and deletes the old key once that deploy succeeds; a failed deploy keeps both, since the running version still sends with the old one.
  • Remove email, and deleting the application, delete its keys in Resend and the variables Orbit added. The sending domain stays in Resend, since other applications or Orbit itself may send from it.

Deliveries and bounces ​

Resend reports what happens to each email, and Orbit counts it for the application that sent it: by its sender, or by any address on a domain only that application uses. On a shared domain only its own sender counts, so each application needs a sender of its own; Orbit refuses one that another application, or Orbit itself, already uses. Last 7 days in the Email section shows what was sent, delivered, bounced and marked as spam, the rates, and the latest addresses that bounced.

Bounces and spam complaints count against the whole Resend account, and Resend reviews accounts above 4% bounces or 0.08% complaints. A paused account would stop Orbit's own email too, so once an application sends at least 20 emails in a week and gets near those limits, Orbit opens a warning. An application's bounces never stop Orbit from writing to an address; only bounces of Orbit's own email do.

Resend reports through a webhook that needs Orbit at a public HTTPS address. Orbit registers it when an application gets email, even if Orbit itself sends through SMTP.

Variables and secrets ​

Variables apply on the next deployment. Secrets are sealed at rest and never shown again after you save them. Connecting a database adds a reference such as DATABASE_URL, whose value Orbit fills in at deploy time.

Logs ​

An application's output appears under Logs within a couple of seconds. Orbit keeps the last 1,000 lines of each service. Values of secret variables and common credential patterns are replaced with •••••••• before anything is stored. Older output is still on the server, until Kubernetes rotates it away:

sh
sudo k3s kubectl -n orbit-<project>-<environment> logs deploy/<service>

Terminal ​

Terminal on a service's page opens a shell inside one of its running instances, through Kubernetes, without SSH or kubectl. Pick the instance, open it and work as you would in any terminal: line editing, colours, copy and paste and resizing all work. Workers and jobs have the same tab; a job's instance exists only while a run is in progress.

  • Who: developers, admins and owners. Viewers see the tab but cannot open a shell. API tokens cannot open terminals; only a signed-in member can.
  • Images without a shell: distroless images and those built from scratch have nothing to run. Orbit attaches a temporary debug container with busybox that shares the instance's processes, so ps, /proc and the network are the application's. It stops when the terminal closes.
  • When it closes: after 15 minutes without input, when you sign out, when your role in the workspace changes, or when the instance stops.
  • What is recorded: the activity records who opened and closed which instance and when. Keystrokes and output are never recorded, since they may hold secrets.

The same shell by hand, on the server:

sh
sudo k3s kubectl -n orbit-<project>-<environment> exec -it <instance> -c app -- sh

Resources ​

An application's memory, CPU and instances change from its Settings, always after a preview.

Reserved CPU decides where each instance fits; the CPU limit caps how much it can consume. You can reserve 50m (0.05 vCPU) while keeping a 250m (0.25 vCPU) limit. Usage above the reservation depends on available CPU and is not guaranteed. Reservations must be at least 50m and cannot exceed the limit. Existing applications keep their reservations until you change them; memory still has equal requests and limits.

The preview and server cards separate measured usage, reserved capacity and available for new reservations. A server at 15% CPU usage can still have all its reservations occupied. View reservations by service lists applications, instances, autoscaling maxima and the estimated runtime allowance of 1 GB and 250m. Other workspaces count toward the total without exposing their names. This is Orbit's planned accounting, not an exact inventory of Kubernetes requests; recovery capacity is evaluated separately. Old readings are marked as stale, and build headroom is an additional recommendation, not a duplicate reservation.

  • The preview shows what the change reserves on the server against its capacity. It counts 1 GB and 250m CPU for the runtime and everything else placed there, warns when builds lose their room or the new limit is below what the application used in the last 24 hours, and says that several instances on one server are not high availability.
  • Applying: Orbit replaces the instances one at a time. When there is no room for a second instance, it stops the running one first, and the preview says so as downtime. If the new instances do not become ready, Orbit puts the previous values back.

CPU reservation suggestions ​

Settings can suggest a smaller CPU reservation for an application with fixed instances. Orbit uses the largest measured CPU reading of any individual instance over seven days, adds a 50% margin, rounds up to 25m and keeps a minimum of 50m. The CPU limit, memory and instance count stay as configured. The amount released is capacity for new reservations, not a reduction in the server's monthly bill.

Choose Review suggestion to fill the reservation field and inspect the normal impact preview. Apply change starts the existing resource operation, including capacity checks, rollout progress and recovery of the previous settings if the rollout fails. Advice never applies itself or replaces unsaved form changes.

A suggestion requires at least seven days of absolute per-instance peak readings, at least 95% coverage, no gap longer than five minutes and a latest reading no older than 90 seconds. Collection records a peak only when every expected instance has a recent CPU reading. Older metrics that store only percentages remain available in charts but cannot supply these peaks; upgraded installations need seven days of the new readings before advice becomes available. Measurements describe sampled usage, so review response times under representative traffic after changing a reservation.

Autoscaling changes its trigger when the reservation changes. Orbit therefore explains why advice is unavailable while autoscaling is enabled. Jobs and sites on the shared static server do not receive per-instance CPU suggestions.

Memory suggestions ​

For applications with fixed instances, Settings can suggest a smaller memory reservation and hard limit. Orbit uses the largest total-memory reading of any instance in the current deployment over seven days, including cache. It adds a 50% margin, rounds up to 64 MB and respects a conservative floor: 64 MB for Orbit's static runtime, 128 MB for Go, and 256 MB for Node.js or Python. These floors are product safeguards, not guarantees that a workload will fit. CPU and instance count stay as configured; released memory is room for new reservations, not a lower server bill.

Orbit records the final runtime from its generated build recipe. A framework name alone is not evidence: a VitePress build that produces static files uses the static floor. Custom images and Dockerfiles require manual review. Deployments created before this feature need a new Orbit-generated build to record the runtime; they do not acquire a runtime from their existing labels.

Advice requires seven days of complete total-memory measurements from the current deployment, at least 95% coverage, no gap longer than five minutes and a latest reading no older than 90 seconds. All expected instances must report fresh readings, and mixed rollouts do not count. Older working-set charts remain available but cannot be backfilled into this evidence. A new deployment starts its own observation window. Autoscaled applications, jobs and shared static hosting do not receive these suggestions.

Any observed out-of-memory kill in the last seven days blocks a reduction, including one first observed after Orbit restarts or without a valid memory reading. An open or monitoring memory incident also blocks advice even if it is older. A known termination timestamp ages out normally; an OOM with an unknown timestamp is treated conservatively as a current observation.

Choose Review memory suggestion to fill the memory field, inspect the impact and confirm with Apply change. This uses the existing capacity checks, rollout and recovery of previous settings if the rollout fails. Exceeding the lower hard limit can kill and restart an instance, even after a successful rollout: sampled peaks cannot predict every future workload. Review representative traffic and keep monitoring after applying. Advice never applies itself or replaces another unsaved change.

Review reservations across applications ​

In Overview → Costs → Review reservations, Orbit lists CPU and memory suggestions for applications in the current workspace, including why a suggestion is unavailable. This works even when server prices are zero or unknown. Missing readings or a failed lookup do not become zero usage. Select applications to see the total CPU and memory that could be released; the server bill stays the same.

Each suggestion also says what it takes off the project estimates: the share of each server's price that the released reservations account for, split half by CPU and half by memory over the capacity left after the runtime, the same way project costs are estimated. It says where the price comes from (read from Hostinger or entered in Orbit), says so when a server has no price or costs nothing, and shows the days and completeness of the measurements behind the suggestion. These amounts lower estimates, not the bill: only retiring a server does, which fleet consolidation simulates.

Ted answers Where can I save? with how many applications can lower their reservations and the largest one, and opens this review from the conversation.

Review applications shows the current and proposed values, capacity, warnings and rollout for each application. CPU and memory suggestions for the same application share one resource change; the CPU limit and instance count stay as configured. No resources change during selection or review. Viewers can inspect the evidence; applying requires the developer role or higher.

Apply changes in sequence waits for a confirmed successful operation before moving to the next application. Before each submission, Orbit fetches current suggestions and a fresh capacity preview. A changed proposal or deployment, new downtime, less available capacity, a new warning, or a failed/cancelled operation stops the remaining changes for another review. More capacity freed by earlier successful changes is allowed. Only confirmed successes contribute to the batch's released-capacity total. Previous successes are not undone when a later change stops.

Keep the review window open for the queue to advance. Stop after this application lets the current operation finish and leaves the rest unstarted. Closing the window, leaving the page or switching workspace stops further submissions; an already submitted operation continues and remains visible in Activity. If the result cannot be confirmed, check Activity before trying again. Reopening the window loads fresh suggestions and does not resume a previous batch automatically.

Review fleet consolidation ​

Administrators can open Overview → Costs → Review fleet consolidation to simulate moving services off one paid server. The report covers all workspaces because they share physical capacity. Each server is an independent alternative; do not add the savings or combine plans without a new simulation. Nothing is moved, removed or cancelled from this screen.

The simulation keeps CPU and memory reservations, maximum autoscaling instances and the number of placement servers. It sets aside the estimated runtime allowance (1 GB and 250m) and build headroom (1 GB and 1000m) on each remaining server. It checks the combined placement and recovery after losing one further server, including neighbouring services. It never creates high availability for a service that currently has one server. The planner can backtrack when an individual fit prevents another service from fitting; reaching its search limit is shown as inconclusive.

Open each application's destinations to see incompatibilities or insufficient capacity. Architectures must match the current source server, and participating servers need healthy agent and runtime reports no older than 90 seconds. The original installation server, control-plane members, Orbit standbys and traffic entry points require separate infrastructure work. Databases, object storage and published static artifacts need a data migration and do not receive a relocation plan.

Potential saving after cancellation uses the full recorded price of a candidate server. The report distinguishes prices entered by you from prices read from Hostinger. A blocked server shows its current cost, not an achievable saving. Unknown prices stay unknown; the server still counts toward placement capacity. Stopping a machine or freeing reservations does not itself stop its bill.

This is a reservation snapshot, not a complete Kubernetes inventory or authorization to remove hardware. Image availability, local volumes, disk space, taints, actual scheduling, DNS/HTTPS, traffic and cancellation terms still need verification before any migration. Infrastructure roles remain blockers even if application placements fit. A running operation blocks the recommendation until it finishes and you refresh. Unlike resource reductions, this simulation does not infer lower reservations from seven days of usage: it leaves existing reservations unchanged.

Operating hours for staging and previews ​

Open an application's Settings → Automations → Operating hours to choose the days and times it runs. This is available for deployed containers in staging and preview environments, including workers. Production, development, databases, scheduled jobs and shared static hosting are excluded. A new application has no schedule; each eligible application is configured separately.

Hours follow the installation time zone, including daylight saving changes. Changing the installation time zone changes these schedules too. Opening time is inclusive and closing time is exclusive. An overnight window such as Friday 22:00–02:00 ends on Saturday. Orbit checks schedules every 30 seconds and reconciles the persisted policy after a restart.

Review operating hours explains whether the application will pause or run immediately. Applying requires the developer role or higher. Pausing removes the application's autoscaler and scales its instances to zero, waiting for all pods to disappear before releasing its CPU and memory reservations. Desired replicas, CPU requests and limits, memory and autoscaling settings are preserved. Databases, volumes, domains and stored data are not deleted. The application's address is unavailable while paused; planned pauses do not create failed uptime checks.

At the next opening, Orbit checks available capacity, restores the saved instances and autoscaling, and verifies readiness before confirming success. If other services have consumed the released capacity, waking fails visibly and the application remains paused. Failed automatic transitions retry after five minutes. Capacity is not guaranteed for the next opening. A failed or cancelled transition with an uncertain cluster outcome keeps its reservations until reconciled.

Wake now · 2 hours temporarily overrides the schedule. At the end of two hours, the normal schedule applies again; an open window keeps the application running. Disabling the schedule also wakes the application, subject to capacity and readiness checks.

Wake the application before deploying or changing its runtime. Pushes received while paused do not deploy and are not queued for later. Waking restores the last deployed version; deploy again after waking to publish newer commits. Pause and wake operations appear in Activity with their verified result.

Pausing frees CPU and memory for other work. The server's monthly bill stays the same. Fleet consolidation does not propose moving applications with enabled schedules, since a sleeping application's released capacity is temporary.

Out of memory ​

An application killed for exceeding its memory limit twice within 30 minutes gets an incident and shows as degraded. The incident shows the restarts, the memory chart with the limit, the incoming traffic and the last deployment, each with its source, and keeps the possible causes apart from the facts. Raising the limit from there goes through the resource preview; Orbit then watches for 10 minutes and resolves the incident if no restart follows. Without a fix, an incident resolves after an hour without restarts.

Autoscaling ​

Scale automatically in the same Settings makes the instances follow CPU, between a minimum and a maximum.

  • Instances are added while their average CPU stays above the target share of the CPU reservation, and removed once it has stayed below for 5 minutes.
  • The preview counts memory and CPU reservations at the maximum number of instances; other changes on that server count that maximum too. Usage up to the CPU limit still depends on available capacity.
  • Changing the reservation changes the autoscaling threshold: 70% of 50m is 35m per instance. The preview warns before applying. Service CPU charts continue to show a percentage of the limit.
  • Deployments and resource changes keep the number of instances the autoscaler chose, within the new bounds.
  • The service's metrics show an Instances chart, and the timeline lists each time instances were added or removed with the CPU that led to it.
  • Limits: up to 10 instances, a target between 20% and 95%, and scheduled jobs cannot autoscale. All instances run on the application's server, so autoscaling handles load, not the loss of that server.

Under HTTP load on a test cluster, an application went from 1 to 3 instances in under 2 minutes and back to 1 within 10 minutes after the load stopped.

Servers ​

An application runs on one server by default. With more than one server, its Settings has a Servers section to move it to another server or spread its instances across several.

  • Spreading: instances are spread evenly, one per server where possible. Autoscaling keeps spreading the ones it adds.
  • When a server is lost: its instances start again on the other servers. On a three-server test cluster this took about a minute and a half, most of it Kubernetes waiting before it declares the server lost. The other instances keep serving meanwhile, but requests the router still sends to the lost ones fail until then: 8 of 71 requests, one per second, in the first 52 seconds of the test.
  • The preview shows how many instances each server would hold at the autoscaling maximum and what stays free, and refuses a server that is not ready, has no room or has another CPU architecture than a built image.
  • Recovery capacity: the preview simulates losing each selected server, including the other applications that would move with it and the maximum of autoscaling. A change to the application's own placement or resources is refused if its instances would not fit. Changes to a neighbouring application or database can proceed when they fit normally, but the preview warns which applications would lose recovery capacity, with the CPU and memory shortfall.
  • Continuous checks: Orbit recalculates this after service or server changes and every minute. The application's Servers section shows the current result. If capacity is lost, an alert names the failed-server scenario and the server that lacks room; notification channels can follow it. The alert clears when capacity returns. It suggests an instance maximum that fits all loss scenarios, when possible, or moving workloads/adding capacity. This is a reservation check; network, image compatibility, database replicas and traffic routing also affect recovery.
  • Images: a built image is copied to every chosen server before an instance starts there. Images from a registry are pulled by each server.
  • What it does not cover:
    • with one instance, the application stops until that instance starts on another server, so use two or more;
    • traffic enters only through the main server unless other servers receive it, and even then losing the main server makes the requests sent to its instances fail;
    • moving instances needs the cluster's control plane, which runs only on the main server unless you run it on three servers.

More than one application ​

A project can run several applications in the same environment, such as an API and an admin panel. Add application under Good company opens the same steps as a new project, from a repository or an image. They end with the environment's databases: each one you pick is connected to the new application as a reference, so two applications can use the same database from their first deployment.

Workers and jobs ​

Add a worker or a job from an application's Overview, under Good company. It reuses the application's source and settings with its own name and start command, in the same environment.

  • A worker has no address. Its deployment fails if it restarts or exits within its first 10 seconds.
  • A job runs on its schedule in UTC, or now with Run now. When a run is still going at the next match, that match is skipped. Orbit keeps the last five successful and five failed runs with their output and exit code, and the job shows as degraded while its latest run failed. A new schedule applies on the next deployment.
sh
sudo k3s kubectl -n orbit-<project>-production get cronjobs,jobs,pods
sudo k3s kubectl -n orbit-<project>-production logs job/<run>

Builds ​

  • An application from a repository is built on the server for every deployment of a new commit. Redeploying the same commit with the same settings reuses its image.
  • The first build of each stack downloads its base images: expect a few minutes for Next.js or Nuxt and less than a minute for small Go, Python or static sites. Later builds of the same project are faster.
  • Builds run on the server where the active Orbit runs, for the architecture of the application's servers (details). A Next.js or Nuxt build can use 1.5 GB of memory for a minute or two, so a 2 GB server should not build while it is short on memory.
  • Each service keeps its ten most recent images, and the build cache trims itself as the disk fills.
  • Builds start from a copy of the commit, without the .git folder or the git program. A build step that reads git history fails, and the deployment says so: turn off what reads it, such as lastUpdated in a VitePress config. Orbit also warns about lastUpdated when it detects the repository.
