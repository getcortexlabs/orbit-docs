On this page

Applications ​

An application runs from a container image or from a GitHub, GitLab or Bitbucket repository that Orbit builds on your server.

Deploying ​

  • A deployment waits up to 3 minutes for the application's health check and up to a minute for its certificate. Set ORBIT_HEALTH_TIMEOUT and ORBIT_CERTIFICATE_TIMEOUT (for example 5m) in orbit.service to change either.
  • An application that exits right after starting (a failed migration, a missing variable) fails saying that it stopped right after starting, with its exit code and its last lines, instead of as a health check that never answered.
  • Rollbacks put a previous deployment back, with the resources the application has now.

Image ​

An application created from a container image keeps that image under Settings → Deployment defaults. Edit the Image reference to move to another tag, another digest or a different repository, and choose the Registry credential that pulls it, or add one in place.

  • Orbit checks the reference in the registry with the chosen credential before saving, so a missing tag or a refused credential is reported right away and nothing changes.
  • Save for next deploy stores the image. The running deployment keeps its own image, and the page shows which one is running until the next deployment. Save and deploy stores it and deploys it now. If the deployment fails, the image stays saved and the previous deployment keeps serving.
  • A developer can move to another tag or digest of the same repository. Another repository or another credential needs an admin, the role that creates applications.
  • The change is recorded in Activity, with who made it and the previous and new image.

The port, the start command and the health check are not read again from the new image. Review Build and start and Health check when the new image listens on another port.

New releases of the image ​

When the image's tag carries a version, such as 1.4.0 or v2.3.1, Orbit asks its registry what was released after it, and the project's overview offers the update. Review the update shows the image that would be deployed, and applying it starts a deployment.

  • What counts as a release. Makers publish previews under ordinary version tags, so a higher number alone is not enough. Orbit takes a version as released when one of the repository's moving tags points at it: latest, or the tag of its major version, such as 3. A repository without those tags gets no offers.
  • The same major version is offered as an ordinary update.
  • A later major version is offered apart, with a warning: nobody checked that it starts on the data of the running one. Read what its makers say about the move and take a backup first. If the new version does not become ready, the previous deployment keeps serving.
  • An image under a tag without a version, such as latest or stable, or pinned by digest, has nothing to compare and gets no offers.
  • The registry is asked at most a few times a day, with the application's own registry credential.

Health check ​

Open a web application's Settings → Health check to choose an HTTP path, such as /api/health, or Port accepting connections. Workers and jobs have no port and do not show this block. A path must start with /, contain no spaces and be at most 200 characters.

An instance receives traffic only after its HTTP path answers with a 2xx or 3xx within 3 seconds. Without an HTTP path, the readiness check only requires a connection to its port. The deployment waits for the instances to pass this check before switching traffic.

Save for next deploy stores the setting; existing instances keep their current probe until another deployment. Save and redeploy applies it now, using the current deployment's image without rebuilding or following a newer commit or image tag. If redeployment fails, the setting stays saved and the previous deployment keeps serving.

Uptime checks use the saved path on their next check, or / when using a port check. These checks reach the public address once a minute; they have their own timeout and success criteria.

gRPC ​

Visitors always reach Orbit's router over HTTPS, with HTTP/2 when their client supports it. Settings → Protocol chooses how the router talks to a web application:

  • Automatic, the default, uses gRPC when the source depends on a gRPC server library (google.golang.org/grpc or connectrpc.com/connect in go.mod, @grpc/grpc-js or @connectrpc/connect-node in package.json, grpcio for Python, tonic in Cargo.toml) and, after the health check, the port answers HTTP/2 without TLS (h2c). The deployment log says which it chose. Once confirmed, later deployments start on gRPC, so calls never fall back to HTTP/1.1 during a redeploy. An application from an image stays on HTTP/1.1 unless you choose gRPC.
  • gRPC (HTTP/2 without TLS) always talks h2c to the port. Every request goes that way, so the server must speak h2c; plain HTTP routes keep working if the server handles both, but WebSockets from browsers do not pass.
  • HTTP/1.1 never uses h2c, which suits web servers, WebSockets and server-sent events.

The application serves gRPC on its port without TLS; the router adds TLS for clients. Clients connect to the application's address on port 443, for example grpc.example.com:443.

Requests through the router can last as long as they need, so a gRPC stream or a slow upload stays open past a minute. Traefik 3 cuts a request after 60 seconds by default; Orbit turns that limit off, as Traefik 2 had it, and Traefik restarts once on its first start after updating. Idle connections still close on their own.

With gRPC, Kubernetes checks a health path over HTTP/1.1 and uptime checks reach it through the router over HTTP/2, so serve it on both or keep the port check. A pure gRPC server answers an uptime check with an HTTP error below 500, which still counts as up.

Behind Cloudflare's proxy, turn on gRPC under Network for the zone, or Cloudflare answers gRPC calls with 403; the deployment log names each proxied address. Cloudflare Tunnel does not carry gRPC on public hostnames, so point those straight at the server.

Build and start ​

Open an application's Settings → Build and start to change how it is built and started after it was created. An application from a repository shows the build strategy, the build command, the start command and the port; an application from an image shows the start command and the port.

  • Automatic build installs the dependencies, runs the build command and starts the start command. Leave either command empty to use the one Orbit detects in the repository.
  • Dockerfile builds the Dockerfile at the root of the repository, so its own steps replace the build command. A start command, when set, replaces the Dockerfile's CMD.
  • Static files runs the build command and serves the output with nginx on the chosen port. Static files run no start command, so switching to them removes a saved one.

Sites published through a Space keep their delivery in Static publishing; this block only changes their build command. Save for next deploy stores the settings for the next deployment. Save and deploy stores them and deploys the branch's latest commit with them. If the deploy fails, the settings stay saved and the previous deployment keeps serving.

Mavis projects ​

A repository with a mavis.config.json at its root, as create-mavis writes it, is detected from that file instead of from package.json. Orbit runs the web app and says which other targets, such as iOS, Android or Mac, run on devices instead.

  • Mavis + Nuxt with server rendering runs as a Node.js service: the build command is the root build:web script, or the web app's own build, and the start command is node apps/web/.output/server/index.mjs (.output/server/index.mjs in a project with only a web app).
  • Mavis + Nuxt with generated pages (ssg) and Mavis + Vue with Vite are static sites: Orbit runs build:web, generate or build and serves .output/public or dist, with no application container.
  • The package manager comes from the lockfile, or from the config when the repository has none.

A Mavis project without a web app has nothing for a server to run, so the detection asks you to choose the settings.

Addresses and domains ​

  • Generated addresses use sslip.io: <service>-<project>.<server-ip-with-dashes>.sslip.io in production, with the environment's name before the project's elsewhere. They work as soon as the server's ports 80 and 443 are reachable from the internet. Let's Encrypt issues their certificates over HTTP; until it does, the address answers over HTTP.

  • Custom domains need a DNS record at your provider:

    • an A record to the server's IPv4 for a root domain (example.com);
    • a CNAME to the generated address for anything under it (www.example.com).

    With more than one server receiving traffic, every domain needs an A record for each of them instead, and the domain's page lists them.

    Orbit checks every 30 seconds and routes the domain once the record points to the server. With Cloudflare connected, Orbit creates the records itself for domains in your zones. Turn off proxying (Cloudflare's orange cloud) until the certificate is issued: Orbit compares the resolved address with the server's, and Let's Encrypt validates over HTTP.

  • www and the root domain: adding example.com or www.example.com offers the other one too, checked by default, and asks where visitors land. The other one gets its own records and certificate and answers with a permanent redirect to the same path on the one they land on, so www.example.com/menu opens example.com/menu. Its card says Redirects to. Redirects never chain, and the domain visitors land on cannot be removed while another one redirects to it.

Email ​

An application can send email through the Resend account Orbit uses for its own, without anyone opening Resend. It needs Resend connected in Settings → Notifications → Email.

In the application's Variables, the Email section asks for a sending domain:

  • mail.<domain> for each verified custom domain of the application, the recommended choice: a subdomain keeps the site's reputation apart from the mail's;
  • Orbit's own sending domain, shared, for an application without a domain of its own; it then sends as its own name on that domain;
  • another domain you type.

Add email creates or adopts the domain in Resend, publishes its DKIM, SPF and DMARC records where Orbit manages the zone (otherwise it lists them to copy, and Check again asks Resend to verify them), and creates an API key that can only send, and only from that domain. Orbit's own key never reaches an application.

The application gets these variables, as references to its email, so the key stays sealed in Orbit and only reaches it at deploy:

VariableValue
RESEND_API_KEYthe application's key
SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASSWORD, SMTP_SECUREsmtp.resend.com, 465, resend, the key, true
EMAIL_FROMthe sender, no-reply@ on a domain of its own

A variable the application already has keeps its value. The variables reach the application at its next deploy. An application from the catalog that sends email gets them under the names it reads instead, with the constants it needs, such as N8N_EMAIL_MODE=smtp; removing the email removes those too.

  • Rotate key creates a new key, deploys the application with it and deletes the old key once that deploy succeeds; a failed deploy keeps both, since the running version still sends with the old one.
  • Remove email, and deleting the application, delete its keys in Resend and the variables Orbit added. The sending domain stays in Resend, since other applications or Orbit itself may send from it.

Deliveries and bounces ​

Resend reports what happens to each email, and Orbit counts it for the application that sent it: by its sender, or by any address on a domain only that application uses. On a shared domain only its own sender counts, so each application needs a sender of its own; Orbit refuses one that another application, or Orbit itself, already uses. Last 7 days in the Email section shows what was sent, delivered, bounced and marked as spam, the rates, and the latest addresses that bounced.

Bounces and spam complaints count against the whole Resend account, and Resend reviews accounts above 4% bounces or 0.08% complaints. A paused account would stop Orbit's own email too, so once an application sends at least 20 emails in a week and gets near those limits, Orbit opens a warning. An application's bounces never stop Orbit from writing to an address; only bounces of Orbit's own email do.

Resend reports through a webhook that needs Orbit at a public HTTPS address. Orbit registers it when an application gets email, even if Orbit itself sends through SMTP.

You can set an optional Sender name, such as Rafael Augusto by Jolt, and edit it later without changing the address or key. It applies immediately to shared email and forms. Applications using EMAIL_FROM receive the formatted name and address on their next deploy. Leave the name blank to use only the address.

Receive email ​

After configuring sending, open Variables → Email → Receive email. Enable receiving and choose a dedicated subdomain below the sending domain, such as in.mail.example.com. Each address can deliver to an application route (support → POST /inbound) or forward to a mailbox. Up to 20 addresses share the subdomain. A static site can forward; an HTTP application is needed to process a route.

Orbit enables receiving in Resend and publishes the required records through the connected DNS provider. With external DNS, copy the records shown in the panel and use Save and check DNS. Existing conflicting records are preserved. Use a separate subdomain so the MX of an existing mailbox stays intact. The Orbit console must have a public HTTPS address for Resend's signed webhook.

For a route, redeploy after setup: ORBIT_INBOUND_SECRET arrives as a secret variable. Orbit posts JSON directly to that application's internal Kubernetes Service; it never follows redirects to another host. The payload contains id, the receiving address, and email with sender, recipients, subject, text, HTML, headers, authentication results and attachments. An attachment's content is base64; filenames and HTML are untrusted user content. The combined fetched metadata and attachment bytes must fit 10 MB, with at most 20 attachments.

Verify the exact request bytes before parsing JSON. This Node.js helper checks the HMAC and five-minute timestamp window:

js
import { createHmac, timingSafeEqual } from "node:crypto";

function validInbound(headers, rawBody, secret) {
  const id = headers["x-orbit-delivery-id"];
  const stamp = headers["x-orbit-timestamp"];
  const signature = headers["x-orbit-signature"];
  if (
    !id ||
    !/^\d+$/.test(stamp ?? "") ||
    Math.abs(Date.now() / 1000 - Number(stamp)) > 300 ||
    !/^v1=[a-f0-9]{64}$/.test(signature ?? "")
  )
    return false;
  const expected = createHmac("sha256", secret)
    .update(`${id}.${stamp}.`)
    .update(rawBody)
    .digest();
  return timingSafeEqual(expected, Buffer.from(signature.slice(3), "hex"));
}

Return 2xx after durably accepting the message. Deduplicate by id in the same transaction as your work: a timeout or restart can repeat a delivery. Other responses, including redirects, are retried with backoff up to the selected 1 to 7 days. Forwarding uses the application's sender, sets the original sender as reply-to, and stops after 24 hours, within Resend's idempotency window. Orbit rejects forwarding loops it can identify.

The panel shows the latest 50 delivery receipts and errors. Orbit stores routing metadata, not bodies or attachment contents; those are fetched from Resend on each attempt. Receipts are removed seven days after expiry. Disabling receiving or changing routes cancels pending work for the old configuration. Removing application email stops receiving too; DNS and the Resend domain remain for explicit cleanup. In-flight requests may already have been accepted.

Reply to Orbit warnings ​

An installation administrator can enable Settings → Notifications → Resend → Reply to alerts, using a dedicated subdomain of Orbit's sending domain. A warning email then has a random reply address valid for seven days. Reply with ok on the first line to acknowledge it, or silence 1h to delay its queued notifications for one hour. The warning stays open until the underlying condition recovers.

The sender must have been a recipient of that alert, still be an Orbit member with developer access to the affected workspace (installation administrator for server warnings), and pass Resend's structured DKIM and DMARC checks. Forged message headers cannot supply these checks. A successful reply is consumed once and recorded under the member's name in Activity. Messages that fail these checks are ignored and logged. This receiving feature does not add a mailbox or conversation view.

Provider contracts: received email and authentication, attachments, receiving domains.

Shared email and forms ​

A static site can collect submissions and publish approved entries without a separate API or database. A backend can also ask Orbit to send email with the application's sending identity. Both use the application's email, configured through Resend, and appear under Variables → Email and forms.

Email from a backend ​

Choose Create sending key and save the key in your backend's secrets as ORBIT_EMAIL_KEY. Orbit shows it once. This key can only send and read delivery receipts for this application; it cannot administer Orbit or another application. Replacing or revoking it stops new requests with the old key immediately. Already queued emails still run. Keep the key out of frontend code, static builds and source control.

The console provides the endpoint and a copyable example. Send POST /api/v1/public/services/{serviceId}/emails with Authorization: Bearer <key>, Content-Type: application/json, and an Idempotency-Key of 8 to 128 characters. Choose the content you need:

json
{
  "to": ["person@example.com"],
  "content": {
    "template": { "id": "welcome", "variables": { "NAME": "Ada", "COUNT": 3 } }
  }
}
json
{
  "to": ["person@example.com"],
  "content": {
    "subject": "Welcome",
    "html": "<h1>Hello, Ada</h1>",
    "text": "Hello, Ada"
  }
}

A published Resend template can be referenced by ID or alias. Variables are strings or numbers. A template cannot be combined with html or text; its subject is optional. Without a template, a subject and HTML or text are required. replyTo is optional. Orbit fixes the sender to the application's configured address, so one application cannot impersonate another. Create and publish templates in Resend; Orbit does not copy or edit them.

A 202 response means the message is durably queued. Read GET /api/v1/public/services/{serviceId}/emails/{id} with the same key to see queued, sent (accepted by Resend), or failed. Delivery and bounce outcomes remain in the existing Email section. Retry a request with its original idempotency key and body; reusing a key with different content is refused. Each request accepts up to 10 recipients and 100 KB of content. Attachments and bulk marketing are outside this API.

Forms without a moderation dashboard ​

Choose Add form. Set its name, approval recipient and allowed website origins, then add the fields your site needs: short text, long text, email or URL. Each field has a stable key and explicit required/public switches. Fields are private by default. Public reading of approved entries is also off until enabled. Use exact origins such as https://docs.example.com; http://localhost:3000 is allowed during development.

The default approval email is ready to use. You can instead choose a published Resend template, HTML or plain text. Custom HTML/text uses for field values, for all fields and for the form name. Include , or both and . Orbit escapes interpolated values in HTML. Resend templates receive the field keys and these uppercase variables automatically; the optional variables JSON maps other template names, for example {"HEADLINE":""}. Never rely on these links in a public field.

Your site posts JSON to the supplied /api/v1/public/forms/{formId}/submissions endpoint. It needs no secret. Send a fresh idempotency key for each intentional submission and reuse it when retrying that submission:

js
fetch("https://orbit.example.com/api/v1/public/forms/frm_example/submissions", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Idempotency-Key": crypto.randomUUID(),
  },
  body: JSON.stringify({
    data: { name: "My app", video: "https://example.com/demo" },
    website: "",
  }),
});

Only configured field keys are accepted. The request must come from an allowed origin. Keep the website honeypot empty and hidden from people. Origins are a browser boundary, not proof of a human visitor; Orbit also applies persistent per-form visitor throttles and application quotas. Add stronger bot checks in your own frontend or proxy if needed. URLs are stored as links, never fetched by Orbit; binary uploads are not part of this flow.

Submissions and their approval emails are stored together. Temporary provider failures retry with backoff, so an outage does not lose a submission. The recipient opens the review page, reads the fields and explicitly confirms approval or rejection. GET requests never change state, including links opened by email scanners. Links expire after seven days and work for one decision. Anyone with the private link can act; forwarding it delegates that decision.

With public reading enabled, GET /api/v1/public/forms/{formId}/entries returns up to 50 approved entries and a nextCursor for the next page. It contains only fields marked public at submission time and still public now. Marking a private field public later never exposes older private values. Pending and rejected entries stay private. Render returned strings as text, not unsanitized HTML. Fetch this endpoint when the showcase opens; no site rebuild is needed.

Admins can edit or pause the form without changing its endpoints. Removing it deletes its submissions and queued emails. To remove one entry without a dashboard, use the authenticated Orbit API: DELETE /api/v1/services/{serviceId}/shared/forms/{formId}/entries/{entryId} (an administrator session or workspace admin API token, not the sending key).

Limits and persistence ​

Each application can have ten forms and queue 100 emails per rolling day. Each form stores at most 1,000 submissions and accepts ten submissions per visitor per hour. Email attempts and receipts are retained for seven days. Transient delivery failures retry at most eight times and stop within 23 hours, before Resend's 24-hour idempotency window ends. Permanent provider errors stop immediately; inspect the recent attempts and the application's email configuration.

Retention is configurable: 0 keeps submissions until removed, while 7 to 365 days deletes them automatically, including approved entries. A changed retention policy applies to new submissions. The storage cap still applies without automatic expiration. Email bodies waiting in the outbox are sealed and removed when sending finishes. The feature uses Orbit's existing durable store and encryption key; include both in your installation backup and recovery plan. It does not create a PostgreSQL instance per site.

The demo keeps its keys and sample submissions in memory and never sends real email. Reloading clears them. In production, the queue survives restarts and follows the active Orbit's replicated store. Existing Worker/D1 data is not migrated by enabling this feature.

Variables and secrets ​

Variables apply on the next deployment. Secrets are sealed at rest and never shown again after you save them. Connecting a database adds a reference such as DATABASE_URL, whose value Orbit fills in at deploy time. A reference can also point at another application.

When a command or a plain variable still holds text meant to be replaced, such as <your-token> or https://<app address>, Orbit shows a warning where you edit it and on the application's overview. It does not block the deploy: Orbit uses the value exactly as written. HTML tags, email addresses in angle brackets, links and shell redirection do not count.

Logs ​

An application's output appears under Logs within a couple of seconds. Orbit keeps the last 1,000 lines of each service. Values of secret variables and common credential patterns are replaced with •••••••• before anything is stored. Older output is still on the server, until Kubernetes rotates it away:

sh
sudo k3s kubectl -n orbit-<project>-<environment> logs deploy/<service>

Terminal ​

Terminal on a service's page opens a shell inside one of its running instances, through Kubernetes, without SSH or kubectl. Pick the instance, open it and work as you would in any terminal: line editing, colours, copy and paste and resizing all work. Workers and jobs have the same tab; a job's instance exists only while a run is in progress.

  • Who: developers, admins and owners. Viewers see the tab but cannot open a shell. API tokens cannot open terminals; only a signed-in member can.
  • Images without a shell: distroless images and those built from scratch have nothing to run. Orbit attaches a temporary debug container with busybox that shares the instance's processes, so ps, /proc and the network are the application's. It stops when the terminal closes.
  • When it closes: after 15 minutes without input, when you sign out, when your role in the workspace changes, or when the instance stops.
  • What is recorded: the activity records who opened and closed which instance and when. Keystrokes and output are never recorded, since they may hold secrets.

The same shell by hand, on the server:

sh
sudo k3s kubectl -n orbit-<project>-<environment> exec -it <instance> -c app -- sh

Resources ​

An application's memory, CPU and instances change from its Settings, always after a preview.

Reserved CPU decides where each instance fits; the CPU limit caps how much it can consume. You can reserve 50m (0.05 vCPU) while keeping a 250m (0.25 vCPU) limit. Usage above the reservation depends on available CPU and is not guaranteed. Reservations must be at least 50m and cannot exceed the limit. Existing applications keep their reservations until you change them.

Memory reserved per instance works the same way for memory: it decides where an instance fits and how much of the server it holds, while the memory limit stays its ceiling. An application can reserve 192 MB and keep a 512 MB limit, so a quiet service stops holding memory it does not use. The trade-off is priority: when the server runs short of memory, an instance using more than its reservation is among the first the server stops, before instances within theirs. Reservations must be at least 64 MB and cannot exceed the limit. Existing and new applications reserve their full limit until you lower the reservation; raising the limit of an application that reserves its full limit raises both. Databases always reserve their full size.

The preview and server cards separate measured usage, reserved capacity and available for new reservations. A server at 15% CPU usage can still have all its reservations occupied. View reservations by service lists applications, instances, autoscaling maxima and the estimated runtime allowance of 1 GB and 250m. Other workspaces count toward the total without exposing their names. This is Orbit's planned accounting, not an exact inventory of Kubernetes requests; recovery capacity is evaluated separately. Old readings are marked as stale. Builds are not part of these reservations: they use memory that is free when they start, as build capacity explains.

  • The preview shows what the change reserves on the server against its capacity. It counts 1 GB and 250m CPU for the runtime and everything else placed there, warns when the new limit or reservation is below what the application used in the last 24 hours, explains what a reservation below the limit means, and says that several instances on one server are not high availability.
  • Applying: Orbit replaces the instances one at a time. When there is no room for a second instance, it stops the running one first, and the preview says so as downtime. If the new instances do not become ready, Orbit puts the previous values back.

CPU reservation suggestions ​

Settings can suggest a smaller CPU reservation for an application with fixed instances. Orbit uses the largest measured CPU reading of any individual instance over seven days, adds a 50% margin, rounds up to 25m and keeps a minimum of 50m. The CPU limit, memory and instance count stay as configured. The amount released is capacity for new reservations, not a reduction in the server's monthly bill.

Choose Review suggestion to fill the reservation field and inspect the normal impact preview. Apply change starts the existing resource operation, including capacity checks, rollout progress and recovery of the previous settings if the rollout fails. Advice never applies itself or replaces unsaved form changes.

A suggestion requires at least seven days of absolute per-instance peak readings, at least 95% coverage, no gap longer than five minutes and a latest reading no older than 90 seconds. Collection records a peak only when every expected instance has a recent CPU reading. Older metrics that store only percentages remain available in charts but cannot supply these peaks; upgraded installations need seven days of the new readings before advice becomes available. Measurements describe sampled usage, so review response times under representative traffic after changing a reservation.

Autoscaling changes its trigger when the reservation changes. Orbit therefore explains why advice is unavailable while autoscaling is enabled. Jobs and sites on the shared static server do not receive per-instance CPU suggestions.

Memory suggestions ​

For applications with fixed instances, Settings can suggest a smaller memory reservation. The memory limit stays as it is, so the application can still use up to it. Orbit uses the largest total-memory reading of any instance in the current deployment over seven days, including cache. It adds a 50% margin, which keeps the usual peak inside the reservation, rounds up to 64 MB and respects a floor: 64 MB for Orbit's static runtime, 128 MB for Go, 256 MB for Node.js or Python, and a quarter of the memory limit for custom images and Dockerfiles, whose startup peak may fall outside the observed week. These floors are product safeguards, not guarantees that a workload will fit. The limit, CPU and instance count stay as configured; released memory is room for new reservations, not a lower server bill.

Orbit records the final runtime from its generated build recipe. A framework name alone is not evidence: a VitePress build that produces static files uses the static floor, and an image without an Orbit build uses the quarter-of-the-limit floor.

Advice requires seven days of complete total-memory measurements from the current deployment, at least 95% coverage, no gap longer than five minutes and a latest reading no older than 90 seconds. All expected instances must report fresh readings, and mixed rollouts do not count. Older working-set charts remain available but cannot be backfilled into this evidence. A new deployment starts its own observation window. Autoscaled applications, jobs and shared static hosting do not receive these suggestions.

Any observed out-of-memory kill in the last seven days blocks a reduction, including one first observed after Orbit restarts or without a valid memory reading. An open or monitoring memory incident also blocks advice even if it is older. A known termination timestamp ages out normally; an OOM with an unknown timestamp is treated conservatively as a current observation.

Choose Review memory suggestion to fill the reservation field, inspect the impact and confirm with Apply change. This uses the existing capacity checks, rollout and recovery of previous settings if the rollout fails. An instance that later uses more than its new reservation keeps running up to its limit, but is among the first stopped if the server runs short of memory: sampled peaks cannot predict every future workload. Review representative traffic and keep monitoring after applying. Advice never applies itself or replaces another unsaved change.

Review reservations across applications ​

In Overview → Costs → Review reservations, Orbit lists CPU and memory suggestions for applications in the current workspace, including why a suggestion is unavailable. This works even when server prices are zero or unknown. Missing readings or a failed lookup do not become zero usage. Select applications to see the total CPU and memory that could be released; the server bill stays the same.

Each suggestion also says what it takes off the project estimates: the share of each server's price that the released reservations account for, split half by CPU and half by memory over the capacity left after the runtime, the same way project costs are estimated. It says where the price comes from (read from Hostinger or entered in Orbit), says so when a server has no price or costs nothing, and shows the days and completeness of the measurements behind the suggestion. These amounts lower estimates, not the bill: only retiring a server does, which fleet consolidation simulates.

Ted answers Where can I save? with how many applications can lower their reservations and the largest one, and opens this review from the conversation.

Review applications shows the current and proposed values, capacity, warnings and rollout for each application. CPU and memory suggestions for the same application share one resource change; the CPU limit and instance count stay as configured. No resources change during selection or review. Viewers can inspect the evidence; applying requires the developer role or higher.

Apply changes in sequence waits for a confirmed successful operation before moving to the next application. Before each submission, Orbit fetches current suggestions and a fresh capacity preview. A changed proposal or deployment, new downtime, less available capacity, a new warning, or a failed/cancelled operation stops the remaining changes for another review. More capacity freed by earlier successful changes is allowed. Only confirmed successes contribute to the batch's released-capacity total. Previous successes are not undone when a later change stops.

Keep the review window open for the queue to advance. Stop after this application lets the current operation finish and leaves the rest unstarted. Closing the window, leaving the page or switching workspace stops further submissions; an already submitted operation continues and remains visible in Activity. If the result cannot be confirmed, check Activity before trying again. Reopening the window loads fresh suggestions and does not resume a previous batch automatically.

Review fleet consolidation ​

Administrators can open Overview → Costs → Review fleet consolidation to simulate moving services off one paid server. The report covers all workspaces because they share physical capacity. Each server is an independent alternative; do not add the savings or combine plans without a new simulation. Nothing is moved, removed or cancelled from this screen.

The simulation keeps CPU and memory reservations, maximum autoscaling instances and the number of placement servers. It sets aside the estimated runtime allowance (1 GB and 250m) and build headroom (1 GB and 1000m) on each remaining server. It checks the combined placement and recovery after losing one further server, including neighbouring services. It never creates high availability for a service that currently has one server. The planner can backtrack when an individual fit prevents another service from fitting; reaching its search limit is shown as inconclusive.

Open each application's destinations to see incompatibilities or insufficient capacity. Architectures must match the current source server, and participating servers need healthy agent and runtime reports no older than 90 seconds. The original installation server, control-plane members, Orbit standbys and traffic entry points require separate infrastructure work. Databases, object storage and published static artifacts need a data migration and do not receive a relocation plan.

Potential saving after cancellation uses the full recorded price of a candidate server. The report distinguishes prices entered by you from prices read from Hostinger. A blocked server shows its current cost, not an achievable saving. Unknown prices stay unknown; the server still counts toward placement capacity. Stopping a machine or freeing reservations does not itself stop its bill.

This is a reservation snapshot, not a complete Kubernetes inventory or authorization to remove hardware. Image availability, local volumes, disk space, taints, actual scheduling, DNS/HTTPS, traffic and cancellation terms still need verification before any migration. Infrastructure roles remain blockers even if application placements fit. A running operation blocks the recommendation until it finishes and you refresh. Unlike resource reductions, this simulation does not infer lower reservations from seven days of usage: it leaves existing reservations unchanged.

Operating hours for staging and previews ​

Open an application's Settings → Automations → Operating hours to choose the days and times it runs. This is available for deployed containers in staging and preview environments, including workers. Production, development, databases, scheduled jobs and shared static hosting are excluded. A new application has no schedule; each eligible application is configured separately.

Hours follow the installation time zone, including daylight saving changes. Changing the installation time zone changes these schedules too. Opening time is inclusive and closing time is exclusive. An overnight window such as Friday 22:00 to Saturday 02:00 ends on Saturday. Orbit checks schedules every 30 seconds and reconciles the persisted policy after a restart.

Review operating hours explains whether the application will pause or run immediately. Applying requires the developer role or higher. Pausing removes the application's autoscaler and scales its instances to zero, waiting for all pods to disappear before releasing its CPU and memory reservations. Desired replicas, CPU requests and limits, memory and autoscaling settings are preserved. Databases, volumes, domains and stored data are not deleted. The application's address is unavailable while paused; planned pauses do not create failed uptime checks.

At the next opening, Orbit checks available capacity, restores the saved instances and autoscaling, and verifies readiness before confirming success. If other services have consumed the released capacity, waking fails visibly and the application remains paused. Failed automatic transitions retry after five minutes. Capacity is not guaranteed for the next opening. A failed or cancelled transition with an uncertain cluster outcome keeps its reservations until reconciled.

Wake now · 2 hours temporarily overrides the schedule. At the end of two hours, the normal schedule applies again; an open window keeps the application running. Disabling the schedule also wakes the application, subject to capacity and readiness checks.

Wake the application before deploying or changing its runtime. Pushes received while paused do not deploy and are not queued for later. Waking restores the last deployed version; deploy again after waking to publish newer commits. Pause and wake operations appear in Activity with their verified result.

Pausing frees CPU and memory for other work. The server's monthly bill stays the same. Fleet consolidation does not propose moving applications with enabled schedules, since a sleeping application's released capacity is temporary.

Restart an application ​

A restart replaces an application's instances with new ones of the version it already runs, one at a time when it has more than one, and waits until they answer. Nothing is built or pulled again, and variables saved since the last deployment still wait for a deployment. It is an operation like a deployment: it appears in Activity under who asked for it and can be followed and retried.

Use Restart at the top of the application's page: Orbit says what will happen and asks before it starts. The API has POST /services/{serviceId}/restarts and an AI agent has restart_app. It needs the developer role. Databases, scheduled jobs, shared static hosting and applications that were never deployed are not restarted this way, an application that sleeps or is paused has to be woken or resumed first, and a restart waits while another operation changes the application.

Pause an application by hand ​

Pause, beside Restart, stops an application until someone resumes it. It works in any environment, production included, and does not depend on operating hours: a paused application stays asleep through its schedule, and Wake now does not lift the pause. Use it to take something out of the air on purpose: an application that is misbehaving, one that must not run during a migration, or one nobody needs for a while.

Orbit says what will happen and asks first. Then it stops the instances and waits for them to disappear before releasing their CPU and memory. The application stops answering at its address, and uptime checks stop while it is paused. Its configuration, variables, domains, volumes and databases stay as they are, and so do its saved instances, resources and autoscaling. The page shows who paused it and since when, and Activity records it. Deployments and restarts are refused while it is paused; pushes received meanwhile do not deploy and are not queued for later.

Resume brings it back: Orbit checks that the application still fits on its server, restores its instances and waits until they answer. If other services took the space, the resume fails visibly and the application stays paused. An application with operating hours follows them again after a resume, so outside its hours it stays asleep until they open.

Pausing and resuming need the developer role. The API has POST /services/{serviceId}/pause and POST /services/{serviceId}/resume, and an AI agent has pause_app and resume_app, each after you confirm. Databases, scheduled jobs, shared static hosting and applications that were never deployed are not paused this way.

Out of memory ​

An application killed for exceeding its memory limit twice within 30 minutes gets an incident and shows as degraded. The incident shows the restarts, the memory chart with the limit, the incoming traffic and the last deployment, each with its source, and keeps the possible causes apart from the facts. Raising the limit from there goes through the resource preview; Orbit then watches for 10 minutes and resolves the incident if no restart follows. Without a fix, an incident resolves after an hour without restarts.

Incident notes and resolving by hand ​

When an application or a database keeps running out of memory, Orbit opens an incident with the evidence it gathered. The incident page has Notes: write what was tried and what fixed it, and the note stays with the incident, signed and dated, also after Orbit updates the incident with new evidence and after it resolves. Whoever meets the same problem later reads it there.

Mark as resolved closes the incident now, without waiting for Orbit to see the application stay calm, and records who did it. Orbit keeps watching: if the problem happens again it opens a new incident, as it does after resolving one itself, and the one you closed stays closed. Both take the developer role in the workspace, and an AI agent can do both.

Autoscaling ​

Scale automatically in the same Settings makes the instances follow CPU, between a minimum and a maximum.

  • Instances are added while their average CPU stays above the target share of the CPU reservation, and removed once it has stayed below for 5 minutes.
  • The preview counts memory and CPU reservations at the maximum number of instances; other changes on that server count that maximum too. Usage up to the CPU limit still depends on available capacity.
  • Changing the reservation changes the autoscaling threshold: 70% of 50m is 35m per instance. The preview warns before applying. Service CPU charts continue to show a percentage of the limit.
  • Deployments and resource changes keep the number of instances the autoscaler chose, within the new bounds.
  • The service's metrics show an Instances chart, and the timeline lists each time instances were added or removed with the CPU that led to it.
  • Limits: up to 10 instances, a target between 20% and 95%, and scheduled jobs cannot autoscale. All instances run on the application's server, so autoscaling handles load, not the loss of that server.

Under HTTP load on a test cluster, an application went from 1 to 3 instances in under 2 minutes and back to 1 within 10 minutes after the load stopped.

Servers ​

An application runs on one server by default. With more than one server, its Settings has a Servers section to move it to another server or spread its instances across several.

  • Spreading: instances are spread evenly, one per server where possible. Autoscaling keeps spreading the ones it adds.
  • When a server is lost: its instances start again on the other servers. On a three-server test cluster this took about a minute and a half, most of it Kubernetes waiting before it declares the server lost. The other instances keep serving meanwhile, but requests the router still sends to the lost ones fail until then: 8 of 71 requests, one per second, in the first 52 seconds of the test.
  • The preview shows how many instances each server would hold at the autoscaling maximum and what stays free, and refuses a server that is not ready, has no room or has another CPU architecture than a built image.
  • Recovery capacity: the preview simulates losing each selected server, including the other applications that would move with it and the maximum of autoscaling. A change to the application's own placement or resources is refused if its instances would not fit. Changes to a neighbouring application or database can proceed when they fit normally, but the preview warns which applications would lose recovery capacity, with the CPU and memory shortfall.
  • Continuous checks: Orbit recalculates this after service or server changes and every minute. The application's Servers section shows the current result. If capacity is lost, an alert names the failed-server scenario and the server that lacks room; notification channels can follow it. The alert clears when capacity returns. It suggests an instance maximum that fits all loss scenarios, when possible, or moving workloads/adding capacity. This is a reservation check; network, image compatibility, database replicas and traffic routing also affect recovery.
  • Images: a built image is copied to every chosen server before an instance starts there. Images from a registry are pulled by each server.
  • What it does not cover:
    • with one instance, the application stops until that instance starts on another server, so use two or more;
    • traffic enters only through the main server unless other servers receive it, and even then losing the main server makes the requests sent to its instances fail;
    • moving instances needs the cluster's control plane, which runs only on the main server unless you run it on three servers.

More than one application ​

A project can run several applications in the same environment, such as an API and an admin panel. Add application under Good company opens the same steps as a new project, from a repository or an image. They end with the environment's databases: each one you pick is connected to the new application as a reference, so two applications can use the same database from their first deployment.

Calling another application ​

Every application that answers HTTP has an internal address, shown under At a glance with a copy button. It goes through the cluster's network, not the internet, on port 80, whatever port the application listens on.

FromAddress
The same project and environmenthttp://<name>, such as http://encoder
Any project in the same workspacehttp://<name>.orbit-<project>-<environment>.svc.cluster.local

To avoid writing it by hand, add a Reference in the calling application's Variables and choose the application under Applications:

  • Connection URL gives the full address, such as http://encoder.orbit-shop-production.svc.cluster.local.
  • Host gives the name without http://.
  • Port gives 80.

Orbit fills the value in at each deploy. Removing the referenced application makes the next deploy of the caller fail and name the variable, so it never starts pointing at nothing. In a pull request preview, a reference to an application of the source environment points at that application's copy in the preview.

Workers, jobs and sites served from shared static hosting have no internal address: they do not listen on a port of their own.

Applications only accept connections from their own workspace. Any application in another project of the same workspace can call them, the public address keeps working through the ingress, and Orbit's own checks still reach them. An application in another workspace is refused, even when it knows the address. A database keeps its own, stricter rules: see databases.

Workers and jobs ​

Choose Process type in the Configuration step of New project to start with a web application, worker or job. Workers and jobs have no public address, port or HTTP health check. Set the complete start command, including arguments, under Build and runtime. Jobs also require a cron schedule and time zone; the initial selection uses the installation's time zone. The review shows both, and deploying prepares the job without starting a run immediately. Use Run now after deployment or wait for its next scheduled time.

You can also add a worker or job from an existing application's Overview, under Good company. This path reuses that application's source and settings with its own name and start command, in the same environment. Process type is chosen at creation; changing it requires a new service.

  • A worker has no address. Its deployment passes once every instance has run 10 seconds without stopping. One restart is tolerated, as for a web application: a new instance can be refused its first connection to a workspace database for a moment, until the network lets it through. A second restart, or a crash loop, fails the deployment.
  • A job runs on its schedule in the selected time zone, or now with Run now. When a run is still going at the next match, that match is skipped. Orbit keeps the last five successful and five failed runs with their output and exit code, and the job shows as degraded while its latest run failed. A new schedule applies on the next deployment.

Builds ​

  • An application from a repository is built on the server for every deployment of a new commit. Redeploying the same commit with the same settings reuses its image.
  • The first build of each stack downloads its base images: expect a few minutes for Next.js or Nuxt and less than a minute for small Go, Python or static sites. Later builds of the same project are faster.
  • Builds run on the server where the active Orbit runs, for the architecture of the application's servers (details). A Next.js or Nuxt build can use 1.5 GB of memory for a minute or two, so a 2 GB server should not build while it is short on memory.
  • Each service keeps its ten most recent images. The build cache is kept to a tenth of the disk, or less while the disk has under a fifth free, and never below 2 GB, so builds stay warm without the cache taking the disk.
  • Builds normally start from a copy of the commit without .git. Build and start → Git history can include recent history or disable recognized VitePress update dates in the build copy. The repository is unchanged.

Private repositories ​

A build from a GitHub repository can read the other repositories of the same GitHub account that Orbit's GitHub App can read, with nothing to configure and no change to the Dockerfile. Go modules, Cargo git dependencies, npm and pip packages from git and a plain git clone in a RUN step all work, whether the URL uses https://github.com/, git@github.com: or ssh://git@github.com/.

  • The token: each build gets its own token, which can only read repository contents and is revoked when the build ends. It reaches every RUN step as a BuildKit secret, so it is never written to a layer, the image history or the build cache, and Orbit hides it in the build log.
  • Go: Orbit sets GOPRIVATE for the account so module names never go to the public proxy. A Dockerfile that sets GOPRIVATE, GONOPROXY or GONOSUMDB itself keeps its own value.
  • Cargo: when a Cargo.toml or Cargo.lock points at the account, Cargo fetches through the git program with the same access.
  • Submodules: submodules on GitHub are downloaded at the commit the repository pins, up to three levels deep. A submodule the App cannot read stays empty.
  • What the image needs: the git program in the build stage that downloads the repositories. Debian based images such as golang and rust have it; Alpine and slim images need apk add --no-cache git or apt-get install -y git. Without it, the deployment fails with that instruction.
  • Limits: GitHub only for now. A step that writes its environment into the image would copy the token, which no longer works once the build ends. Pull requests from forks never build, so they never receive a token.

Git history ​

When a build reports spawn git ENOENT or not a git repository, Build with git history and retry saves the choice and rebuilds the failed commit. Automatic Node, Python, Go and static recipes make Git available and mount the history read-only for build commands. It is not copied into the final image or static files. The server running Orbit needs the git command installed.

Orbit fetches the pinned commit with shallow history (depth 100), without tags. GitHub submodules are downloaded as described in private repositories. Older per-page dates may be approximate; repositories that require complete history need their own build workflow. Credentials are supplied only to the fetch process and never written into the checkout. History is removed with the temporary build context.

Source detection offers this choice before the first build when it recognizes VitePress lastUpdated: true. Build VitePress without update dates turns those literal settings off only in the disposable configuration files the detector reads. It does not rewrite computed settings, functions or imported configuration. With a custom Dockerfile, select an automatic strategy to use Orbit's history mount, or manage Git in the Dockerfile yourself.

The change appears in Activity. To undo it, select Use the repository settings, without history in Build and start, save and deploy again.

Output directory ​

When a static build succeeds but its output folder is missing, the failure lets you enter the folder it actually produces. For VitePress this is commonly docs/.vitepress/dist; other tools often use dist or build. Paths are relative to the repository. Empty Output directory restores automatic detection. Check the build log before changing it.

Build command ​

A missing package script is different from an error in the code. Check scripts in package.json, then enter the correct command in the failure panel, for example npm run docs:build. Saving starts a deployment of the same commit with the corrected settings. The command remains visible and editable in Build and start.

Application port ​

For a port mismatch, Orbit shows the configured port and the port it detected. Review the proposed port in the failure panel before saving. The application must listen on 0.0.0.0, not only localhost.

Architecture ​

An image for arm64 cannot run natively on an x86_64 server. Choose compatible servers under Servers, or build for the intended architecture. This requires a placement or build decision; retrying the same image does not fix it.

Build memory ​

A JavaScript heap error or an explicit memory allocation failure means the build process ran out of memory. Check the server running the active Orbit, other builds and the process limit reported in the log. A heap limit and an exhausted host need different changes. Increasing the application's runtime memory does not increase the memory available to the builder. Orbit links to this guidance rather than applying an unrelated runtime change.

Remove receiving email ​

Disable receiving, then choose Review removal in the receiving panel. The same flow is available for alert replies in the installation's email settings. Disabling receiving alone does not remove its domain or DNS records.

Disconnect preserves provider resources. Remove resources created by Orbit removes only the Resend domain and DNS records whose creation Orbit recorded and whose current identity still matches. Adopted, shared, changed or older resources without ownership evidence stay intact; the preview explains each decision. Active sending domains and unrelated DNS records are preserved.

The generic DNS Release action does not release records owned by receiving email. Use the receiving removal flow so ownership is checked before any provider mutation. Remove receiving before deleting its application, environment, project or sending configuration.

Confirm the domain name to start a tracked operation. Provider failures keep the configuration and progress available for Retry. Do not enable receiving again or edit the database to finish cleanup. Previous delivery metadata follows its normal retention period.

Shared secrets ​

Under Settings → Security → Secrets, choose the installation or workspace. For a project-owned secret, open that project's settings. Give it a name, enter the value, and select the environments and projects that may use it. A project can use its own secrets in the selected environments. Installation and workspace secrets require an explicit project grant.

Under Variables on an application, select the secret, optionally change its variable name, apply and deploy. Orbit resolves it at deployment. The console only shows its name and access settings after saving. To rotate the value, edit the original secret and redeploy consumers. Running processes keep their current environment until replaced. After rotation or revocation, redeploy the desired source version with current credentials to recover an older release.

Pix payments ​

In project settings, create a Dev secret and a production secret, then connect them under Pix payments. Select each environment where the Dev secret may run, including previews. A project can share its connection with named projects in its workspace. Grant these consumers access to both referenced secrets. In the application's Variables, choose the connection and deploy. A trusted pull-request preview inherits its source application's connection with the Dev key.

The workload receives ORBIT_PAYMENTS_URL, ORBIT_PAYMENTS_TOKEN, ORBIT_PAYMENTS_MODE and ORBIT_PAYMENTS_WEBHOOK_SECRET. The ABACATEPAY_API_KEY variable also grants the workload the key's capabilities directly at the provider. Grant access only to projects that may exercise those permissions.

Send POST $ORBIT_PAYMENTS_URL/charges with bearer authentication, an Idempotency-Key unique to the order, and {"amount": 100} for R$1.00. Store the request key before sending. Reuse it on retries. The response includes the provider charge ID, amount, status, Pix copy-and-paste code and QR image. Send an authenticated GET $ORBIT_PAYMENTS_URL/charges/{requestKey} to read that order again.

Orbit registers the merchant webhook when the first charge is created in each mode. The manager must have a public HTTPS address. Give the provider keys permission to read the store, list and create webhooks, and create transparent charges. Dev simulation also needs permission to simulate a transparent payment. Connection verification reports the permission actually checked. The event history covers charges created through the gateway.

Implement POST /webhooks/orbit/payments on the application. Verify the X-Orbit-Signature header as v1= followed by the lowercase hex HMAC-SHA256 of deliveryId.timestamp.rawBody with ORBIT_PAYMENTS_WEBHOOK_SECRET. Read the first two values from X-Orbit-Delivery-Id and X-Orbit-Timestamp. Accept only recent timestamps, deduplicate by delivery ID, and answer 2xx after processing. Events carry the charge ID, amount in cents, status and mode. See the latest 50 deliveries from the last seven days in the application. In a Dev environment choose Simulate R$1 in Dev to exercise the route.

For a recurring Pix checkout, send POST $ORBIT_PAYMENTS_URL/subscriptions with the same authentication and order key. Use {"productId":"prod_…"} with a recurring product from the merchant. An optional customerId identifies a provider customer. Give the merchant key SUBSCRIPTION:CREATE. Present the returned checkoutUrl for payer approval. Orbit matches subscription events to the original provider checkout ID across renewals and sends only payment identifiers, amount, mode and status. If the connection drops during creation and the result is uncertain, check the checkout in AbacatePay before starting another order. Orbit blocks a second creation with the same key to prevent duplicate subscriptions.
