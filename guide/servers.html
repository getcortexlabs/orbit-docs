More servers ​

Adding one ​

Add Server in the console: give the server's name, IP and SSH user, confirm its host key fingerprint and authorize a temporary key (or paste your own). Orbit runs the same checks and plan as on the first machine and, after you approve it, joins the server to the cluster as a K3s agent with its own Orbit agent. New services can then be placed on it. A VPS at Hostinger can also be ordered or added without typing its address.

Discarding a server ​

A server that is not installed yet can be discarded from its setup or with Discard on its card in Servers, whenever no operation runs on it:

  • Before its installation starts, nothing was installed on it, and Orbit forgets it together with the temporary key it generated. If you added that key to the server, remove its line from ~/.ssh/authorized_keys there.

  • After its installation failed, Orbit first removes its node from the cluster, revokes its agent and stops letting its addresses through the main server's firewall. The machine itself is left as it is. To keep using it for something else, remove what Orbit installed:

    sh
    sudo systemctl disable --now k3s-agent orbit-agent orbit-firewall
sudo rm -rf /etc/rancher/k3s /etc/orbit-agent /var/lib/orbit-agent /usr/local/lib/orbit /var/lib/orbit \
  /usr/local/bin/k3s /usr/local/bin/orbit-agent /etc/systemd/system/k3s-agent.service \
  /etc/systemd/system/orbit-agent.service /etc/systemd/system/orbit-firewall.service
sudo reboot

More servers add room, not high availability

A service runs on the server you choose and stops if that server stops, unless it is an application spread across servers or a database with PostgreSQL replicas. Traffic enters through the main server unless you choose other servers to receive it.

Servers from Hostinger ​

With the Hostinger token an administrator connected under Settings → System → Hostinger: DNS and servers, Add server offers two more ways in, next to adding a machine by address. The same token serves Hostinger DNS; Hostinger tokens have no scopes, so it acts with the permissions of the account that created it.

  • Order from Hostinger: pick a plan, a billing period, a data center and a payment method of the account. Before anything is bought, Orbit shows what Hostinger charges now for the first period, what it renews at, and what the server will count for on the costs page, all before taxes. The order only goes out after you confirm that charge, and Orbit checks the price again when you do: if it changed in between, nothing is bought and the new price is shown. Hostinger creates the VPS with Ubuntu 24.04 and Orbit's setup key; the server appears in Servers as being created and, once it runs, reaches the installation checks like a server added by address. Orbit marks the order before placing it, so a retry, or Orbit restarting in the middle, looks for the VPS it bought instead of buying another. When Hostinger is still taking the payment, Orbit waits for the new VPS to appear in the account.
  • A Hostinger VPS you have: pick one of the account's machines and give it a name. Orbit adds its setup key for root through Hostinger's API, so there is no address to type and no command to run. Erase it and install Ubuntu 24.04 first reinstalls the VPS from scratch before adding it; everything on it, and its snapshot, is lost.

In both cases the address and the machine come from Hostinger's API, and there is no other channel to compare the host key with, so Orbit trusts the one it reads on its first connection. The setup key is removed once the server joins, as with a server added by address. The order renews until you cancel it in hPanel: removing the server from Orbit does not cancel it.

Servers already in the cluster whose address belongs to a VPS of the account are linked to it on their own. Orbit reads the account's machines again every ten minutes. On a linked server, Hostinger VPS on its card shows the plan, data center, state, snapshot and firewall, and:

  • Restart stops and starts the VPS and waits until it runs again. When Orbit runs on that server, it stops with it and comes back with it.
  • Take snapshot asks Hostinger for a snapshot of the whole disk. Hostinger keeps one snapshot per VPS, so a new one replaces the previous. Orbit also takes one of every linked server before it updates itself, and of the servers involved before it moves the control plane, unless the last snapshot is less than an hour old; a snapshot that fails is noted in the operation's log and the change goes on.
  • Restore snapshot puts the disk back as it was when the snapshot was taken, after a second click. Everything written since is lost; on a control plane server, prefer it only when the whole change went wrong.

Hostinger's firewall: a Hostinger firewall is off by default. When one is active on a linked server, Orbit adds rules that let in the traffic of your other servers, and ports 80 and 443 on servers that receive traffic. Rules you added in hPanel stay, and the ones Orbit added for a server that left are removed.

Network requirements ​

  • Every server must reach the main server's IPv4 on TCP 6443 (Kubernetes) and 7443 (Orbit's agents).
  • The main server must reach every other server on TCP 10250 (logs and commands).
  • All servers must reach each other on UDP 51820 (WireGuard, which encrypts traffic between servers).
  • Orbit opens these on the main server for your servers only, by their public address and by their address on a private network the servers share. When ufw is active on a server, Orbit allows the other servers' addresses there too.
  • Images that reject everything but SSH, such as Oracle Cloud's Ubuntu images, whose own iptables rules end in REJECT: Orbit lets your other servers through them on the main server and on the new one, and the rules come back after a reboot.
  • Every server keeps the others' addresses up to date. When a server joins or is discarded, and every ten minutes, Orbit sends each server, through its agent, the addresses of all the others (public, private and their addresses in the cluster), and the server rewrites its firewall's list: new servers are let in, through ufw too when it is active, and servers that left are removed.
  • Private networks: when the main server has a private address (as on Oracle Cloud, AWS or Hetzner networks), a new server first tries it, then the main server's public address. Before starting K3s, it checks that one of them answers on 6443, and if none does, the installation stops within seconds naming the addresses it tried and where traffic comes from. When both servers are on the same private network, they must reach each other on it: if only the public address answers, the installation stops there and says whether the main server refused the connection (its own firewall) or nothing answered (a cloud firewall), because traffic between servers would be refused later. Before starting the agent, the new server also checks that it reaches the agent channel on 7443 and that its certificate covers the address it uses. Once it joined, Orbit checks from it that applications there reach the Kubernetes API and applications on another server, and stops with the part that failed otherwise.
  • Servers on separate networks: enable the encrypted network before joining new servers or adding control plane members across providers. Existing clusters can migrate with their applications running. Without it, the legacy public-address path remains available for workers only.
  • Cloud firewalls are outside Orbit's reach. On Oracle Cloud, the subnet's security list only lets SSH through by default: add an ingress rule for the subnet's range (such as 10.0.0.0/24) with all protocols. When the main server runs on Oracle Cloud, a server that cannot join says so: it names the rule to add, with the new server's subnet as the source (or its public address when it is on another network), and links the main server in the Oracle console, where its subnet and security list are one click away. AWS security groups and Hetzner firewalls need the same ports between your servers.

The first join restarts K3s once on the main server to turn on WireGuard. Running applications keep running.

Orbit encrypted network ​

Under Servers → Connect my fleet, Orbit prepares a WireGuard network (orbit0) between your servers. Each gets a stable address from an unused /24 within 100.64.0.0/10. Orbit checks existing interfaces and routes, including VPNs, before reserving addresses. Keys are sealed in Orbit storage and written to root-only files on their server.

  1. In each provider firewall, allow UDP 51821, inbound and outbound, between the public endpoints listed in the dialog. On Oracle, add rules to each instance's security list or NSG. Orbit configures the operating system firewall.
  2. Start connecting. Every directed path must pass 1380-byte probes before Orbit changes K3s. A blocked port stops the operation and identifies the server.
  3. Orbit migrates one node at a time, checks the other members' health before proceeding, and waits for Kubernetes to confirm the new address. For etcd members it saves a snapshot, updates the member URL and lets K3s renew certificates with the new address. Container processes keep running; the Kubernetes API can be temporarily unavailable while a single control plane restarts.

If the switch fails, a process independent of the console attempts to restore the previous configuration and etcd address. Its recovery journal is /etc/orbit-agent/network-migration.json, accessible only to root. Retrying retains the reserved keys and addresses. If recovery also fails, the operation reports that and stops before migrating another node.

New servers join through the enabled network. Kubelet, Flannel and etcd use these addresses; the authenticated agent channel stays independent on TCP 7443. Flannel keeps wireguard-native, with its MTU derived from the 1380-byte interface: host-gw requires a layer-2 network that a WireGuard mesh does not provide.

The network requires direct UDP connectivity between public endpoints. Keepalive and roaming maintain NAT mappings but do not replace port forwarding for restrictive NAT or CGNAT. Orbit provides no relay; failed probes prevent migration. Applications, databases, entry servers and Orbit copies still need their own replicas to tolerate a server loss.

From SSH ​

On the active Orbit server, root can run the same operations through the private 0600 Unix socket. Workspace API tokens cannot administer the installation's network. orbit status lists server IDs.

sh
sudo orbit servers connect
sudo orbit servers control-plane --servers srv_one,srv_two
sudo orbit servers standbys
sudo orbit servers entry --server srv_one --enabled=true

Each command prints its operation ID and follows progress through service restarts. --no-wait returns after acceptance; sudo orbit servers follow --operation op_id reconnects to that operation. Run later commands only after the preceding operation succeeds. Enabling traffic also changes the DNS records that custom domains require, as described below.

Receiving traffic ​

Traffic enters through the main server by default. Another ready server can receive it too: Receive traffic on its card under Servers. Orbit then runs the router on that server as well, waits until it is ready and checks that the server answers on port 80. If it does not, Orbit takes the change back and says so.

  • Firewall: open TCP 80 and 443 to the internet in your provider's firewall and, when ufw is active, on the server: sudo ufw allow 80/tcp && sudo ufw allow 443/tcp. Orbit does not open them for you.
  • DNS: every custom domain then needs an A record for each server that receives traffic, subdomains included, which otherwise use a CNAME. The domain's page lists them, and a domain that was already verified shows them again until Orbit finds them all. Resolvers spread visitors across those addresses, and Orbit keeps routing a domain that resolves to any of them.
  • Generated addresses (sslip.io) keep pointing to the main server, since each one carries a single IP.
  • Certificates are issued as before: Let's Encrypt can validate a domain through any server that receives traffic.
  • Closed ports: a server that cannot open ports 80 and 443, such as one behind NAT, can receive traffic through Cloudflare Tunnel instead.
  • Stopping: Stop receiving traffic removes the router from that server. Take its address out of your DNS first, or visitors whose resolver picks it get no answer.

What it covers and what it does not, as measured on a three-server test cluster:

  • Losing a server that receives traffic: visitors whose resolver picked it get no answer until their DNS stops returning it. Requests through the main server kept working, except those sent to the instance that ran on the lost server: 8 of 71 requests, one per second, failed in the first 52 seconds, until Kubernetes declared the server lost.
  • Losing the main server: the other servers keep answering. With the control plane on the main server only, it stops too, so nothing takes the instances that ran there out of the routers' lists and the requests sent to them fail. With the control plane on three servers, the routers stop sending requests to them once Kubernetes declares the main server lost. See the control plane limit.

Out of DNS ​

A server that receives traffic can leave the DNS answers without losing its role: Take out of DNS on its card, the main server included. Orbit removes its address from the A records of the domains, previews and console address whose DNS it manages, through Cloudflare, DigitalOcean or Hostinger, and the card shows Out of DNS. The router keeps running, so Put back in DNS returns it at once.

  • The last one stays: Orbit refuses to take out the only server that still answers, since visitors need at least one address.
  • Domains pointed by hand need the same change at your DNS provider. Their page lists the records without the server that left.
  • Caches: resolvers that kept the old answer use it for up to five minutes, the time to live of the records Orbit writes.

Automatic DNS failover, in Settings under System, does it by itself: when a server that receives traffic has not answered for three minutes, Orbit takes it out of the DNS answers, and puts it back once its router answers on port 80 again. A server taken out by hand stays out until someone puts it back. Off until an administrator turns it on. Either way, the warning A server that receives traffic stops answering opens after three minutes.

Control plane on three servers ​

Kubernetes keeps the cluster's state and makes its decisions on the main server: where instances run, when they move after a server is lost, when a database fails over. With at least three servers, Run on three servers under Servers puts that on the main server and two servers you choose.

  • What happens: Orbit keeps etcd's ports, 2379 and 2380, for your servers. It restarts k3s once on the main server to move the cluster's data from SQLite to etcd, then restarts k3s as a server on each chosen server, one at a time. Kubernetes does not answer for about a minute during the first restart, and applications keep running. On a test cluster the move to etcd took 16 to 18 seconds and each server joined in 11 to 26 seconds.
  • Requirements: each chosen server must be ready and have at least 2 GB of memory. A server that does not qualify cannot be checked, and the dialog says why next to its name: it is still being set up, its agent is offline, Kubernetes does not report it as ready, or it has too little memory. K3s recommends 2 CPU cores and an SSD, since etcd writes often. Your servers must reach each other on TCP 2379 and 2380: Orbit allows that between them with ufw and keeps those ports closed to the internet, but a provider firewall that filters traffic between servers needs it too.
  • Disk health: every agent measures its disk once a minute, with 20 small writes that each wait for the disk (fsync), and on control plane members it also reads etcd's own fsync times. The server's card shows the result under Inspect: the 99th percentile, how many writes took over a second in the last hour, the slowest one, and which processes wrote the most meanwhile. etcd needs fsync under 10 ms; a disk that takes 100 ms or more for 5 minutes opens the warning too slow for the control plane, shows Slow disk on the card and next to the server's name in the three-server dialog, and the operation that joins it measures the disk first and says so. Network block storage, such as a cloud block volume shared by etcd, images and builds, is the usual cause: a stall of a few seconds there holds the whole cluster and the console. Orbit softens it two ways: a standby copy of Orbit on a slow disk waits 6 seconds longer before taking over, so a copy on a healthy disk wins, and on control plane members BuildKit's writes are capped at half of what the disk can take, so a build cannot starve etcd.
  • Lease timings: the controller manager, the cloud controller manager and the scheduler run inside the k3s process, and each ends the whole process, etcd member and API server included, when it cannot renew its lease in time. K3s gives them 15 seconds, which an etcd leader change on a disk that stalls for a few seconds is enough to exceed. Orbit gives them 60 seconds to hold a lease and 40 to renew it on every server that runs the control plane. New servers get these timings when they are installed; existing ones get them from their agent within a few minutes of Orbit starting, one server at a time, with a k3s restart on each so etcd keeps its majority. On the server Orbit itself runs on, k3s is not restarted: it uses the timings the next time it starts. The card shows k3s restarted when k3s exited on its own during the last day, and Inspect says how many times, when, and whether it lost a lease just before.
  • Which networks: servers on the same reachable network qualify directly. For different providers or provider NAT, first enable the encrypted network. The dialog accepts a NAT server only after its migration has finished and Kubernetes reports its stable overlay address.
  • If a server cannot join: when k3s does not come up as a server on a chosen server, Orbit puts that server back as an agent, with its configuration restored, and the operation says what k3s reported there. The usual cause is a firewall between the servers on TCP 2379 or 2380. Open the path and run it again. A server that an earlier version of Orbit left half way goes back to being an agent by itself once Orbit and its agent run this version.
  • Why three: etcd needs a majority of its members. With three, one can be lost. With two, losing either one stops the cluster, which is worse than one, so the console only offers three.
  • The cluster's own services: DNS, cert-manager, the database operator and metrics can then run on any of the three. DNS and the database operator run two copies each. K3s puts its own services back on the main server whenever it restarts on a server, so Orbit checks every 20 seconds and spreads them again.
  • Orbit itself still runs only on the main server. When it is lost, the cluster keeps working, but the console and the API wait for it to come back.

Measured three times on a three-server test cluster with the main server killed:

  • Kubernetes answered on another server 7 to 12 seconds later.
  • A PostgreSQL database with three instances and its primary on the main server had a new primary after 1 minute 30 to 40 seconds.
  • The application's instance that ran on the main server ran again elsewhere after 1 minute 43 to 55 seconds.
  • Through another server that receives traffic, 10 to 11 of about 155 requests failed, the last one 69 to 74 seconds after the loss. From an application on a third server, calling it by its service name, 16 to 17 of about 200 requests failed, the last one 71 to 77 seconds after the loss.
  • An application deployed after the loss started normally.

There is no way back to one server in the console, and it cannot replace a lost control plane server yet. If one of the three is lost for good, the other two keep a majority, but losing a second one stops the cluster.

Copies of Orbit ​

With the control plane on three servers, Keep copies of Orbit under Servers installs Orbit on the two other control plane servers, where it waits as a standby.

  • What a standby holds: a copy of Orbit's database, its certificate authority and the key that seals secrets. It copies them once, then follows every committed change.
  • When a change counts: Orbit answers a change once a standby has it. If no standby answers within 2 seconds, Orbit answers anyway, and that change can be lost if the active server is lost before a standby catches up.
  • The lease: the active Orbit renews a Kubernetes lease every 2 seconds and stops itself if it cannot renew it for 10 seconds. When the lease goes 15 seconds without a renewal, the standby with the latest copy takes it over and starts serving.
  • Agents learn the three addresses and move to the next one when the current one stops answering.
  • Operations that were running resume on the new active server once kiln, Orbit's job queue, declares the old one gone, about a minute later.
  • The console answers on every server that receives traffic, at orbit.<its address with dashes>.sslip.io. Set the standbys to receive traffic to reach the console when the main server is lost.
  • A server that comes back after being lost joins as a standby: it discards its own copy and takes a fresh one from the active server.
  • After the active Orbit restarts: the log of changes the standbys follow is kept on disk next to the data. When the active Orbit stops cleanly on the same server, for an update, a restart or a lost lease, it first refuses further writes, sends the standbys the last changes and leaves the whole log on disk, and the next start continues it: the standbys resume from where they were, in a second, and can take over right away. It keeps renewing its lease until the log is closed, so no standby takes over while it can still write, and a restart takes a few seconds and keeps the lease. After a crash, a restore, or when a standby took over, the new active Orbit starts a new log, and every standby downloads the database again before it can take over. The download takes seconds on a healthy network. A standby whose download or stream stalls gives up after 30 seconds without data and tries again, says so in its log, and Orbit opens the warning a copy of Orbit cannot take over when a standby has not followed the active for 2 minutes. Under the servers, each copy says whether it follows and how far behind it is, and whether it last resumed or downloaded the whole database, and when.

Measured on a three-server test cluster with the main server killed: a standby took the lease after 16 to 17 seconds (three runs) and answered at once, with the project created just before the loss. A project created afterwards worked, and the main server, once back, came back as a standby.

What it does not cover yet:

  • builds run where BuildKit is installed, the main server; the new active server installs it on its first build;
  • generated sslip.io addresses of your applications point to the main server;
  • the console cannot add, remove or replace a standby.

Losing a member for good ​

  • A control plane server that will not come back: the two that remain keep working, though losing another one would stop the cluster. Run sudo k3s kubectl delete node <name> on one of them so Kubernetes stops waiting for it; K3s then tries to remove it from etcd as well. Orbit cannot make another server a member from the console yet.
  • Going back to one server: the console has no way back. Install Orbit on a new server and restore the latest orbit backup there.

If a server goes down ​

Every server card has If it goes down, which says, before anything breaks, what losing that server would do:

  • Stops: applications, databases and Spaces that run only there, with their public names. Each one links to its fix: spread the application over servers, add a replica to the database, or keep the Space's backups elsewhere. The fix runs through its usual preview.
  • Slows down: spread applications whose other servers cannot hold every instance, and databases that fail over to a replica after about a minute without writes.
  • Carries on: spread applications that move to the other servers with room for them, and static sites served by the other servers that receive traffic.
  • Orbit and Kubernetes: whether a copy of Orbit takes over, within about 20 seconds, or the console stops until the server returns; and whether Kubernetes keeps running on the other control plane servers or stops, in which case nothing moves and no database fails over.
  • Visitors: for each domain, the share of DNS answers that point at the server and would get no reply until DNS changes. With automatic DNS failover on, that lasts about three minutes plus the records' five minutes in caches. Cloudflare Tunnel answers from any server instead.

The overview shows a resilience score: the share of your services that keep answering after the loss of any one server, with the server whose loss stops the most of them and a link to its list.

Join tokens ​

Every server keeps a K3s join token in its configuration. A server that joins gets a token for agents only, which cannot add a server to the control plane: the main server gives agents a token of their own the first time a server joins.

Renew join tokens, in the cluster panel of Servers, is for clusters created before that, or after a server was exposed. Orbit then:

  1. Gives agents a token of their own if they had none, restarting K3s once on the main server.
  2. Writes the agents' token in every other server's configuration, through its agent, without restarting it. A server whose agent is older keeps its previous token in its configuration, which stops working in the next step.
  3. Replaces the servers' token (k3s token rotate) and restarts K3s once more on the main server. From then on, a token copied from any server no longer lets a machine join.

Applications keep running throughout, and servers already in the cluster stay in it. It is refused while a server is being installed, and for clusters whose control plane runs on several servers.

Builds and updates ​

  • Builds run on the server where the active Orbit runs, and Orbit copies the image to the application's servers before each deployment. The image targets the architecture of the application's first server, so all its servers share one architecture.
  • When that architecture differs from the builder's, for example x86_64 servers built from an ARM64 server after a failover, static files are built natively and packaged for the target. Other images run their build steps through QEMU emulation: the first such build installs Ubuntu's qemu-user and registers only that architecture with systemd-binfmt. Emulated builds take several times longer than native ones.
  • Updating from the console also updates the agents on your other servers and Orbit on the standbys. install.sh updates only the server it runs on.

Agents ​

Each server's agent reports its health and inventory over mutual TLS. A server turns offline about 90 seconds after its last heartbeat, and the console then shows its workloads as unknown.

sh
sudo orbit revoke-agent --server srv_…   # refuse that server's agent at once
sudo orbit enroll-agent --server srv_…   # on the same machine: a new token, a new certificate, a restarted agent

Server ids are in orbit status. Once an agent enrolls, the certificates its server had before are revoked, so only the newest enrollment is trusted.

Looking at the cluster ​

sh
sudo k3s kubectl get nodes -L orbit.cortexlabs.dev/server
sudo k3s kubectl get pods -A -o wide
journalctl -u k3s-agent -f    # on the other server

What your servers cost ​

Type in what each server costs from its card in Servers: the monthly amount from your provider's bill, in its currency. Only Orbit administrators can set or remove a price. A server from Hostinger gets its price from its subscription, spread over the months of the billing period and kept up to date, until someone types another one.

Orbit then splits each server's price between the projects whose services reserve resources on it:

  • A service's share is what it reserves on that server, with CPU and memory weighing half each, out of what the server offers once Orbit's own reserve is set aside. An application spread over several servers pays on each for the instances it keeps there, and a database pays for its memory on every server that keeps a copy.
  • A project's cost is the sum of its services' shares, preview environments included.
  • What no service reserves is shown as Not reserved, and projects of other workspaces count together as one share, without their names.
  • On every server, the shares add up to its price to the cent. Prices in different currencies are never added together: each currency gets its own total.

Projects shows the total and what each project costs a month. The overview shows the same total and where money goes unused: the part of each server nobody reserves, and services whose busiest instance uses less than a third of the memory it reserves. Lowering those reservations in a service's Resources frees room for other projects.

Servers still being added are left out, and servers without a price are listed so you can set one.

These are reservation estimates, not separate bills for each project. A project made entirely of sites published through Spaces shows Shared hosting: those sites have no dedicated CPU or memory reservation, and their build, storage and traffic costs are not allocated individually. A static site served by its own container still has an estimate, including VitePress. If a project also has containers or databases, their shares remain visible.

Price not set means a server needs a monthly price. Server price set to zero means its price was explicitly entered as zero; it does not establish that hosting is free. An estimate smaller than one cent is shown as Less than one cent instead of zero. Estimates update when a site switches between container and shared hosting.

Optimization history ​

Open Overview → Costs → Optimization history to review successful resource changes for applications in the current workspace. The history starts when this feature is installed; it does not reconstruct earlier changes. Each entry keeps the application, project, environment, time, operation ID and before/after configuration, even after the project is deleted.

The net capacity figure compares each application's first recorded configuration with its latest confirmed configuration, including the maximum number of autoscaled instances. Reductions are positive; increases are negative. Raising a reservation again reduces the earlier gain instead of counting both changes as savings. CPU reservations and CPU limits are shown separately. Temporary operating-hours pauses do not count as a permanent reduction. Removed applications, changes still running or not confirmed, and configurations changed outside the history are excluded from the current total. A gap in the recorded sequence starts a new comparison baseline.

Administrators can also review the separate Server price history for the entire fleet. It records manual edits and provider price updates with their currency and source. An unknown price is different from zero. Recorded prices do not prove a lower invoice or cancellation of a provider subscription: freeing capacity leaves the server's monthly bill unchanged.
