Managing DNS records ​

The DNS page lists every record of the Cloudflare zones, DigitalOcean domains and Hostinger domains your workspace reaches, and lets you add, change and delete them without leaving Orbit. It needs Cloudflare connected, either a token for the workspace or one shared by every workspace with zones assigned to it, or DigitalOcean DNS or Hostinger DNS connected with domains assigned to the workspace. When more than one provider is connected, each zone says which one it comes from.

Using DigitalOcean DNS ​

Domains whose nameservers are ns1.digitalocean.com, ns2.digitalocean.com and ns3.digitalocean.com can be managed the same way as Cloudflare zones. An administrator connects one DigitalOcean token for the whole installation under Settings → System → DigitalOcean DNS for every workspace and chooses which workspaces use each domain; there is no token per workspace.

  • The token: a personal access token created in DigitalOcean under API with custom scopes domain:read, domain:create, domain:update and domain:delete. Orbit checks it by creating and deleting a TXT record named _orbit-check in each domain; a domain the token cannot write is listed as read only. The token is sealed and never shown again.
  • What Orbit does there: the records of your applications' custom domains and of a project's previews are created, updated when entry servers change and deleted with the domain, with Configure automatically on the domain's page working the same way as on Cloudflare. The wildcard certificate of a project's previews is issued through DigitalOcean too. Orbit recognizes its own records by their ids, since DigitalOcean has no record comments.
  • Differences from Cloudflare: there is no proxy, so every record is DNS only and the dialog hides the proxy switch; the TTL is a number of seconds from 30 up, 300 by default, without an automatic value; comments are not kept; NS records can be edited too; SRV records are listed but not edited yet. The same provider rules keep Orbit from touching records it did not create.
  • Previously migrated applications: the migration from DigitalOcean keeps its own token for the duration of the migration; DNS management uses the token connected here.

Using Hostinger DNS ​

Domains whose nameservers are ns1.dns-parking.com and ns2.dns-parking.com, the DNS Hostinger gives every domain in hPanel, can be managed the same way. An administrator connects one Hostinger API token for the whole installation under Settings → System → Hostinger: DNS and servers and chooses which workspaces use each domain; there is no token per workspace. The same token lets administrators order and add Hostinger servers.

  • The token: create it in hPanel under Profile → API. Hostinger tokens have no scopes: a token acts with the permissions of the account that created it, so use the account that holds the domains. Only active domains registered in that account are listed, because Hostinger's API has no list of DNS zones; a domain registered elsewhere that only points its nameservers at Hostinger does not appear. If you give it an expiry, connect a new one here before it runs out. Orbit checks the token by listing the account's active domains and by asking Hostinger to validate a TXT record named _orbit-check in each one, without writing it. The token is sealed and never shown again.
  • What Orbit does there: the records of your applications' custom domains and of a project's previews are created, updated when entry servers change and deleted with the domain, and Configure automatically works the same way as on Cloudflare. Hostinger has no record ids or comments, so Orbit recognizes its own records by name, type and value, which it keeps on the domain.
  • Previews: cert-manager cannot prove a Hostinger zone is yours, so there is no wildcard certificate for a project's previews there. Each preview gets its own certificate from Let's Encrypt when it is created, which takes a few seconds longer the first time it opens.
  • Zone history: Hostinger keeps a copy of the zone before every change, whoever made it. History on the DNS page lists them, newest first, and Restore puts the zone back as that copy has it, after you confirm. Right after, Orbit writes again the records it keeps in that zone for your domains, previews and console address, so restoring an older copy does not take an application offline. If the copy has a record in the way of one of them, the domain's card says so.
  • Differences from Cloudflare: there is no proxy; the TTL is a number of seconds from 60 up, 300 by default, and Hostinger keeps one TTL for all the values of a name and type, so changing it on one record changes it for its siblings; comments are not kept; NS records can be edited too; SRV records are listed but not edited yet. A name and type with a value disabled in hPanel is left alone, since rewriting it would turn that value back on: enable or delete it in hPanel first.

Moving a domain's DNS to Cloudflare ​

Registrars such as GoDaddy and Squarespace host DNS with no API Orbit can use, so Orbit cannot change records there. Orbit can move the DNS to Cloudflare for you; the domain stays registered where you bought it, and only its nameservers change.

Add the domain to the application and open Configure automatically. When its DNS lives at such a host, the dialog shows Move DNS to Cloudflare:

  1. Where it lives. The registrar, read from the registry through RDAP, and the DNS host, read from the nameservers. When DNSSEC is on, a warning says to turn it off at the registrar and wait a day before changing the nameservers, or the domain stops resolving.
  2. A Cloudflare account. The workspace's own token, or, for an administrator, the token the installation shares. A brand new account with no zone yet works: the token needs Zone: Zone: Edit and Zone: DNS: Edit for all zones of the account.
  3. The records. Orbit reads the zone at its own nameservers: the apex, www, mail, the names of your domains in the zone, MX, TXT (SPF and verification), CAA, _dmarc, _domainconnect and the DKIM selectors of common mail services. Each one says whether it is copied. Three are left behind and say why: an address where Orbit's record for the domain takes its place, a name parked at the registrar's placeholder page, and an alias whose target does not exist. DNS cannot list a zone, so check for uncommon names you use and add them on the DNS page later.
  4. Create the zone. Orbit creates it in Cloudflare with the records marked to copy, and shows the two nameservers Cloudflare assigned, each with a copy button. A record Cloudflare refuses is named, and the others are created anyway.
  5. The steps. From there the dialog lists what is left, each step turning green on its own. Orbit checks every half minute, with the dialog open or closed:
    • DNSSEC. When it was on, the registrar's steps to turn it off come first. Once the registry stops publishing the DS record, a countdown waits out its TTL, since resolvers may still hold it, and only then shows the nameservers. At Registro.br, DNSSEC cannot be turned off on its own DNS and goes away by itself after the change, so there is no wait.
    • Nameservers. The registrar's own steps, with a link to its panel, for Squarespace, GoDaddy, Namecheap, Hostinger and Registro.br, and general ones for any other. The step is done when the registry, read through RDAP, delegates to Cloudflare. The domain keeps answering from its old host meanwhile.
    • Public resolvers. Cloudflare (1.1.1.1), Google (8.8.8.8) and Quad9 (9.9.9.9), each one green once it gives the new nameservers.
    • Cloudflare. The zone turns active, which takes from minutes to a few hours. Orbit asks Cloudflare to look again at most once an hour.
    • HTTPS. Orbit configures the domain in the new zone with the records it created for it, and the certificate follows. A zone created with the shared token goes to the workspace it was moved for.

If Cloudflare already has the zone, in this account or another, the move is refused: remove it there, or connect the account that has it.

What the page shows ​

Pick a zone at the top. Each record shows its type, name, value, proxy and TTL, and:

  • The server it reaches, for address records that point at one of your servers, with its health.
  • Orbit · application, for the records Orbit keeps for a custom domain, the previews of a project or the console address. The link opens the application.
  • A warning when the record sends visitors to a server that is not answering, to a server that does not receive traffic, or when the domain Orbit keeps it for is still waiting to be verified.

Zones the token can only read are marked read only. Their records, and record types the page does not edit (such as SRV), show a lock: change them at the zone's provider.

Adding and changing records ​

Add record creates an A, AAAA, CNAME, MX, TXT or CAA record. Type the name relative to the zone (@ for the zone itself, or www), or a full hostname inside it. For an A record, the dialog lists your servers so you can point the name at one of them.

  • Proxy: only A, AAAA and CNAME records go through the Cloudflare proxy. Keep DNS only for names Orbit verifies and gets certificates for, since Orbit compares the address with your servers.
  • TTL: Auto, or between one minute and one day. Proxied records always use Auto.
  • The type of an existing record cannot change. Delete it and add a new one.
  • Comments starting with Orbit are reserved for the records Orbit manages.

Records Orbit manages ​

Orbit keeps the records of your domains matching the servers that receive traffic, so you rarely need to touch them. Changing or deleting one asks you to confirm, and then Orbit stops managing the DNS of that name: it no longer updates its records when your servers change, and the domain is checked against public DNS again. If the records stop matching what the application needs, the domain's card says so, and Configure automatically puts Orbit back in charge.

When a server goes down ​

A server that stops answering stays in DNS: Orbit does not take it out by itself. Visitors whose resolver picks its address get no reply until it comes back, and the page flags those records so you can see them at a glance. Point the names elsewhere while the server is down, or put a proxy with health checks or Cloudflare Tunnel in front of the applications that must keep answering.
