Tokens de API e CI ​

Um token de API deixa um script ou um pipeline de CI usar a API do Orbit sem a conta de uma pessoa, por exemplo para fazer o deploy da imagem que o pipeline acabou de construir. Cada token pertence a um workspace, age com um papel nele e mostra o próprio nome na atividade em tudo o que faz.

Criando um token ​

  1. Em Configurações → Tokens de API, dê ao token um nome que diga onde ele é usado, como GitHub Actions, e escolha o papel e quando ele expira: em 30 dias, 90 dias, um ano, ou nunca.
  2. Copie o token na hora e guarde nos secrets do seu CI. Ele começa com orbit_, aparece uma vez, e o Orbit guarda só um hash dele.
  • Quem cria tokens: proprietários e admins, para os papéis de admin, desenvolvedor e leitor. Tokens nunca são proprietários.
  • A lista mostra o papel de cada token, quem criou, quando expira e quando foi usado por último, então fica fácil achar um token que ninguém usa mais.

O que um token pode fazer ​

Um token age como um membro com o papel dele, com as mesmas verificações. Veja Membros e papéis.

  • Desenvolvedor é o papel para CI: faz deploy e rollback, mas não revela credenciais, não restaura backups e não apaga nada.
  • Leitor serve para dashboards e scripts que só leem.
  • Admin faz tudo o que um admin faz no workspace, então guarde para automações que realmente precisam.

Algumas coisas sempre exigem uma pessoa conectada no console, seja qual for o papel do token: gerenciar membros e convites, e criar ou revogar tokens. Ali um token recebe 403 signInRequired. Servidores, atualizações do Orbit e novos workspaces ficam com o administrador do Orbit, então um token recebe 403 administratorRequired neles.

Deploy pelo GitHub Actions ​

Toda aplicação mostra isso na aba Configurações, já com o ID e o endereço dela. Guarde o token como o secret ORBIT_TOKEN do repositório e adicione um passo depois que a imagem for enviada:

yaml
name: Release
on:
  push:
    branches: [main]
jobs:
  release:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: ghcr.io/acme/shop:${{ github.sha }}
      - name: Deploy to Orbit
        env:
          ORBIT_URL: https://orbit.example.com
          ORBIT_TOKEN: ${{ secrets.ORBIT_TOKEN }}
        run: |
          curl -fsSL https://github.com/getcortexlabs/orbit-releases/releases/latest/download/orbit-linux-amd64.tar.gz | tar -xz orbit
          ./orbit deploy svc_0123456789ab --image ghcr.io/acme/shop:${{ github.sha }}
  • A imagem continua no repositório da aplicação. Um deploy pelo CI muda só a tag ou o digest, e a nova referência vira a imagem da aplicação. Outro repositório responde 422 imageOutsideRepository, então um token de desenvolvedor vazado não consegue rodar a imagem de outra pessoa com as variáveis da sua aplicação.
  • Um registry privado precisa da mesma credencial de registry com que a aplicação foi criada, que um admin adiciona uma vez.
  • Aplicações construídas a partir de um repositório fazem deploy de um commit: ./orbit deploy svc_0123456789ab --commit "$GITHUB_SHA". O Orbit constrói esse commit do branch conectado, do mesmo jeito que um push faria.

orbit deploy ​

O orbit deploy faz parte do mesmo binário orbit que roda no seu servidor, nos builds para Linux de toda versão. Ele lê ORBIT_URL (o endereço do console) e ORBIT_TOKEN do ambiente, inicia o deploy e acompanha, mostrando cada passo e os logs.

FlagFaz
--image referênciaFaz deploy desta tag ou deste digest da imagem da aplicação
--commit shaFaz deploy deste commit, para uma aplicação construída a partir de um repositório
--no-waitInicia o deploy e volta sem acompanhar
--timeout 30mPara de acompanhar depois desse tempo; o deploy continua
--url endereçoO endereço do console, no lugar de ORBIT_URL

Ele sai com 0 quando a nova versão está no ar, e com 1 quando o deploy falha, é cancelado ou é recusado, depois de mostrar o motivo. Se a conexão cair enquanto ele inicia o deploy, ele tenta de novo com a mesma chave de idempotência, então o deploy nunca começa duas vezes.

Com curl ​

Qualquer cliente HTTP funciona. Mande o token no cabeçalho Authorization e uma Idempotency-Key que continue igual se o passo for repetido:

sh
curl -fsS -X POST "$ORBIT_URL/api/v1/services/svc_0123456789ab/deployments" \
  -H "Authorization: Bearer $ORBIT_TOKEN" \
  -H "Idempotency-Key: deploy-$GITHUB_RUN_ID-$GITHUB_RUN_ATTEMPT" \
  -H "Content-Type: application/json" \
  -d '{"image":"ghcr.io/acme/shop:'"$GITHUB_SHA"'"}'

A resposta é 202 Accepted com a operação. Acompanhe em GET /api/v1/operations/{id} até a phase ser succeeded, failed ou cancelled.

Revogação e expiração ​

  • Revogar um token em Configurações → Tokens de API para o token na hora: o próximo pedido dele recebe 401 apiTokenInvalid.
  • Um token expirado recebe 401 apiTokenExpired. Crie outro e troque o secret no seu CI.
  • Tokens pertencem ao workspace, não a quem os criou, então continuam funcionando quando essa pessoa sai. Revise a lista quando alguém sair e revogue o que essa pessoa configurou se aquilo tiver que parar.
