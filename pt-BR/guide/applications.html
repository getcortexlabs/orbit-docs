Aplicações ​

Uma aplicação roda a partir de uma imagem de contêiner ou de um repositório do GitHub, GitLab ou Bitbucket que o Orbit compila no seu servidor.

Publicando ​

  • Um deploy espera até 3 minutos pelo health check da aplicação e até um minuto pelo certificado. Defina ORBIT_HEALTH_TIMEOUT e ORBIT_CERTIFICATE_TIMEOUT (por exemplo 5m) no orbit.service para mudar qualquer um dos dois.
  • Uma aplicação que sai logo depois de iniciar (uma migração que falhou, uma variável faltando) falha dizendo que parou logo depois de iniciar, com o código de saída e as últimas linhas, em vez de parecer um health check que nunca respondeu.
  • Rollbacks colocam um deploy anterior de volta, com os recursos que a aplicação tem agora.

Verificação de saúde ​

Abra Configurações → Verificação de saúde de uma aplicação web para escolher um Caminho HTTP, como /api/health, ou Porta aceitando conexões. Workers e jobs não têm porta e não mostram esse bloco. O caminho precisa começar com /, não conter espaços e ter no máximo 200 caracteres.

Uma instância só recebe tráfego depois que o caminho HTTP responde com 2xx ou 3xx em até 3 segundos. Sem um caminho HTTP, basta a porta aceitar uma conexão. O deploy espera as instâncias passarem nessa verificação antes de mudar o tráfego.

Salvar para o próximo deploy guarda a configuração; as instâncias atuais mantêm a verificação até outro deploy. Salvar e fazer deploy aplica agora, usando a imagem do deploy atual sem refazer o build nem seguir um commit ou tag mais recente. Se o deploy falhar, a configuração continua salva e o deploy anterior continua atendendo.

As verificações de disponibilidade usam o caminho salvo na próxima verificação, ou / quando a verificação é de porta. Elas acessam o endereço público uma vez por minuto e têm seu próprio tempo limite e critérios de sucesso.

Build e inicialização ​

Abra Configurações → Build e inicialização de uma aplicação para mudar como ela é construída e iniciada depois de criada. Uma aplicação de repositório mostra a estratégia de build, o comando de build, o comando de start e a porta; uma aplicação de imagem mostra o comando de start e a porta.

  • Build automático instala as dependências, roda o comando de build e inicia com o comando de start. Deixe um comando vazio para usar o que o Orbit detecta no repositório.
  • Dockerfile constrói o Dockerfile da raiz do repositório, então os passos dele substituem o comando de build. Um comando de start, quando preenchido, substitui o CMD do Dockerfile.
  • Arquivos estáticos roda o comando de build e serve o resultado com nginx na porta escolhida. Arquivos estáticos não rodam comando de start, então trocar para eles remove o que estiver salvo.

Sites publicados por um Space continuam com a entrega em Publicação estática; este bloco só muda o comando de build deles. Salvar para o próximo deploy guarda as configurações para o próximo deploy. Salvar e fazer deploy guarda e publica o commit mais recente da branch com elas. Se o deploy falhar, as configurações continuam salvas e o deploy anterior segue no ar.

Endereços e domínios ​

  • Endereços gerados usam sslip.io: <serviço>-<projeto>.<ip-do-servidor-com-traços>.sslip.io em produção, com o nome do ambiente antes do projeto nos demais. Funcionam assim que as portas 80 e 443 do servidor estão acessíveis pela internet. O Let's Encrypt emite os certificados por HTTP; até isso acontecer, o endereço responde em HTTP.

  • Domínios próprios precisam de um registro DNS no seu provedor:

    • um registro A para o IPv4 do servidor, para um domínio raiz (example.com);
    • um CNAME para o endereço gerado, para qualquer coisa abaixo dele (www.example.com).

    Com mais de um servidor recebendo tráfego, cada domínio precisa de um registro A para cada um deles, e a página do domínio lista esses registros.

    O Orbit confere a cada 30 segundos e passa a rotear o domínio quando o registro aponta para o servidor. Com a Cloudflare conectada, o Orbit cria os registros sozinho para domínios nas suas zonas. Desligue o proxy (a nuvem laranja da Cloudflare) até o certificado sair: o Orbit compara o endereço resolvido com o do servidor, e o Let's Encrypt valida por HTTP.

  • www e o domínio raiz: adicionar example.com ou www.example.com oferece também o outro, já marcado, e pergunta onde os visitantes chegam. O outro ganha registros e certificado próprios e responde com um redirecionamento permanente para o mesmo caminho naquele onde os visitantes chegam, então www.example.com/menu abre example.com/menu. O card dele diz Redireciona para. Redirecionamentos nunca se encadeiam, e o domínio onde os visitantes chegam não pode ser removido enquanto outro redireciona para ele.

Email ​

Uma aplicação pode enviar email pela conta do Resend que o Orbit usa para os próprios envios, sem ninguém abrir o Resend. Para isso, o Resend precisa estar conectado em Configurações → Notificações → Email.

Em Variáveis da aplicação, a seção Email pede um domínio de envio:

  • mail.<domínio> para cada domínio próprio verificado da aplicação, a escolha recomendada: um subdomínio separa a reputação do site da reputação do email;
  • o domínio de envio do próprio Orbit, compartilhado, para uma aplicação sem domínio próprio; ela envia com o próprio nome nesse domínio;
  • outro domínio que você digitar.

Adicionar email cria ou adota o domínio no Resend, publica os registros DKIM, SPF e DMARC dele onde o Orbit gerencia a zona (senão lista para você copiar, e Conferir de novo pede ao Resend para verificar), e cria uma chave de API que só envia, e só por esse domínio. A chave do próprio Orbit nunca chega a uma aplicação.

A aplicação recebe estas variáveis, como referências ao email dela, então a chave fica selada no Orbit e só chega a ela no deploy:

VariávelValor
RESEND_API_KEYa chave da aplicação
SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASSWORD, SMTP_SECUREsmtp.resend.com, 465, resend, a chave, true
EMAIL_FROMo remetente, no-reply@ num domínio próprio

Uma variável que a aplicação já tem mantém o valor. As variáveis chegam à aplicação no próximo deploy. Uma aplicação do catálogo que envia email recebe essas variáveis com os nomes que ela lê, junto com as constantes de que precisa, como N8N_EMAIL_MODE=smtp; remover o email remove essas também.

  • Trocar a chave cria uma chave nova, faz o deploy da aplicação com ela e apaga a antiga quando esse deploy der certo; um deploy que falha mantém as duas, porque a versão no ar ainda envia com a antiga.
  • Remover o email, e excluir a aplicação, apagam as chaves dela no Resend e as variáveis que o Orbit acrescentou. O domínio de envio continua no Resend, porque outras aplicações ou o próprio Orbit podem enviar por ele.

Entregas e retornos ​

O Resend informa o que acontece com cada email, e o Orbit conta para a aplicação que enviou: pelo remetente dela, ou por qualquer endereço em um domínio que só ela usa. Em um domínio compartilhado só o remetente dela conta, então cada aplicação precisa de um remetente próprio; o Orbit recusa um que outra aplicação, ou o próprio Orbit, já usa. Últimos 7 dias, na seção Email, mostra o que foi enviado, entregue, voltou e foi marcado como spam, as taxas e os últimos endereços que voltaram.

Retornos e reclamações de spam contam para a conta inteira do Resend, e o Resend revisa contas acima de 4% de retornos ou 0,08% de reclamações. Uma conta pausada também pararia o email do próprio Orbit, então quando uma aplicação envia pelo menos 20 emails em uma semana e chega perto desses limites, o Orbit abre um aviso. Os retornos de uma aplicação nunca impedem o Orbit de escrever para um endereço; só os retornos do email do próprio Orbit fazem isso.

O Resend informa por um webhook que precisa do Orbit em um endereço HTTPS público. O Orbit registra esse webhook quando uma aplicação ganha email, mesmo que o próprio Orbit envie por SMTP.

Variáveis e segredos ​

As variáveis valem a partir do próximo deploy. Segredos são guardados selados e nunca mais aparecem depois de salvos. Conectar um banco adiciona uma referência como DATABASE_URL, cujo valor o Orbit preenche na hora do deploy.

Logs ​

A saída de uma aplicação aparece em Logs em poucos segundos. O Orbit guarda as últimas 1.000 linhas de cada serviço. Valores de variáveis secretas e padrões comuns de credenciais viram •••••••• antes de qualquer coisa ser guardada. A saída mais antiga continua no servidor até o Kubernetes descartá-la:

sh
sudo k3s kubectl -n orbit-<projeto>-<ambiente> logs deploy/<serviço>

Terminal ​

Terminal, na página de um serviço, abre um shell dentro de uma das instâncias em execução, pelo Kubernetes, sem SSH nem kubectl. Escolha a instância, abra e trabalhe como em qualquer terminal: edição de linha, cores, copiar e colar e redimensionar funcionam. Workers e jobs têm a mesma aba; a instância de um job só existe enquanto uma execução está em andamento.

  • Quem: desenvolvedores, admins e proprietários. Leitores veem a aba, mas não abrem shell. Tokens de API não abrem terminais; só um membro logado.
  • Imagens sem shell: imagens distroless e as construídas do zero não têm o que rodar. O Orbit anexa um contêiner de depuração temporário com busybox que compartilha os processos da instância, então ps, /proc e a rede são os da aplicação. Ele para quando o terminal fecha.
  • Quando fecha: depois de 15 minutos sem digitar, quando você sai da conta, quando seu papel no workspace muda, ou quando a instância para.
  • O que fica registrado: a atividade registra quem abriu e fechou qual instância e quando. Teclas e saída nunca são gravadas, porque podem conter segredos.

O mesmo shell à mão, no servidor:

sh
sudo k3s kubectl -n orbit-<projeto>-<ambiente> exec -it <instância> -c app -- sh

Recursos ​

Memória, CPU e instâncias de uma aplicação mudam nas suas Configurações, sempre depois de uma prévia.

Reserva de CPU é a quantidade usada para decidir onde cada instância cabe; limite de CPU é o máximo que ela pode consumir. Você pode reservar 50m (0,05 vCPU) e manter o limite em 250m (0,25 vCPU). O consumo acima da reserva depende de CPU disponível: não é garantido. A reserva mínima é 50m e não pode superar o limite. Aplicações existentes continuam reservando o mesmo valor até você alterá-lo; memória continua com reserva igual ao limite.

A prévia e os cartões dos servidores separam uso medido, reservado e disponível para novas reservas. CPU com 15% de uso ainda pode ter todas as reservas ocupadas. Ver reservas por serviço mostra as aplicações, suas instâncias, o máximo do autoscaling e a margem estimada de 1 GB e 250m para o runtime. Serviços de outros workspaces entram no total sem expor seus nomes. Essa é a contabilidade planejada do Orbit, não um inventário exato das reservas no Kubernetes; a capacidade de recuperação é avaliada separadamente. Leituras antigas são identificadas e a margem para builds é uma recomendação adicional, não uma reserva duplicada.

  • A prévia mostra o que a mudança reserva no servidor frente à capacidade dele. Ela conta 1 GB e 250m de CPU para o runtime e tudo o mais que está no servidor, avisa quando os builds perdem o espaço deles ou quando o novo limite fica abaixo do que a aplicação usou nas últimas 24 horas, e diz que várias instâncias num servidor só não são alta disponibilidade.
  • Aplicando: o Orbit troca as instâncias uma por vez. Quando não há espaço para uma segunda instância, ele para a que está rodando antes, e a prévia avisa isso como indisponibilidade. Se as novas instâncias não ficarem prontas, o Orbit volta os valores anteriores.

Sugestões de reserva de CPU ​

As Configurações podem sugerir uma reserva de CPU menor para uma aplicação com instâncias fixas. O Orbit usa a maior leitura de CPU de qualquer instância nos últimos sete dias, soma uma margem de 50%, arredonda para cima em múltiplos de 25m e mantém o mínimo de 50m. O limite de CPU, a memória e o número de instâncias ficam como estão. O que se libera é espaço para novas reservas, não uma redução na mensalidade do servidor.

Escolha Revisar sugestão para preencher o campo da reserva e ver a prévia de impacto de sempre. Aplicar mudança inicia a operação de recursos que já existe, com a checagem de capacidade, o andamento do rollout e a volta às configurações anteriores se o rollout falhar. Uma sugestão nunca se aplica sozinha nem substitui mudanças não salvas do formulário.

Uma sugestão precisa de pelo menos sete dias de leituras absolutas de pico por instância, cobertura mínima de 95%, nenhuma falha maior que cinco minutos e uma leitura de no máximo 90 segundos atrás. A coleta só registra um pico quando todas as instâncias esperadas têm uma leitura recente de CPU. Métricas antigas que guardam só percentuais continuam nos gráficos, mas não servem como pico; instalações atualizadas precisam de sete dias das leituras novas antes de a sugestão aparecer. As medições descrevem o uso amostrado, então confira os tempos de resposta com tráfego representativo depois de mudar uma reserva.

O autoscaling muda o seu gatilho quando a reserva muda. Por isso o Orbit explica por que não há sugestão enquanto o autoscaling estiver ligado. Jobs e sites no servidor estático compartilhado não recebem sugestões de CPU por instância.

Sugestões de memória ​

Para aplicações com instâncias fixas, as Configurações podem sugerir uma reserva de memória e um limite rígido menores. O Orbit usa a maior leitura de memória total de qualquer instância do deploy atual nos últimos sete dias, cache incluído. Ele soma uma margem de 50%, arredonda para cima em múltiplos de 64 MB e respeita um piso conservador: 64 MB para o runtime estático do Orbit, 128 MB para Go e 256 MB para Node.js ou Python. Esses pisos são salvaguardas do produto, não garantias de que uma carga vai caber. CPU e número de instâncias ficam como estão; a memória liberada é espaço para novas reservas, não uma mensalidade menor.

O Orbit registra o runtime final a partir da receita de build que ele gerou. O nome de um framework sozinho não é evidência: um build do VitePress que gera arquivos estáticos usa o piso do estático. Imagens próprias e Dockerfiles exigem revisão manual. Deploys anteriores a esse recurso precisam de um novo build gerado pelo Orbit para registrar o runtime; eles não ganham um runtime a partir dos rótulos que já têm.

A sugestão precisa de sete dias de medições completas de memória total do deploy atual, cobertura mínima de 95%, nenhuma falha maior que cinco minutos e uma leitura de no máximo 90 segundos atrás. Todas as instâncias esperadas precisam mandar leituras recentes, e rollouts misturados não contam. Gráficos antigos de working set continuam disponíveis, mas não podem ser usados como essa evidência. Um deploy novo começa a sua própria janela de observação. Aplicações com autoscaling, jobs e a hospedagem estática compartilhada não recebem essas sugestões.

Qualquer morte por falta de memória nos últimos sete dias bloqueia uma redução, inclusive uma vista pela primeira vez depois de o Orbit reiniciar ou sem leitura de memória válida. Um incidente de memória aberto ou em observação também bloqueia a sugestão, mesmo que seja antigo. Uma morte com horário conhecido sai da janela normalmente; uma sem horário conhecido é tratada, por precaução, como atual.

Escolha Revisar sugestão de memória para preencher o campo de memória, veja o impacto e confirme com Aplicar mudança. Isso usa as checagens de capacidade, o rollout e a volta às configurações anteriores se o rollout falhar. Passar do novo limite rígido pode matar e reiniciar uma instância, mesmo depois de um rollout bem-sucedido: picos amostrados não preveem toda carga futura. Confira com tráfego representativo e continue acompanhando depois de aplicar. Uma sugestão nunca se aplica sozinha nem substitui outra mudança não salva.

Revisar reservas de todas as aplicações ​

Em Visão geral → Custos → Revisar reservas, o Orbit lista as sugestões de CPU e memória das aplicações do workspace atual, inclusive o motivo de uma sugestão não estar disponível. Isso funciona mesmo quando os preços dos servidores são zero ou desconhecidos. Leituras que faltam ou uma consulta que falhou não viram uso zero. Selecione aplicações para ver o total de CPU e memória que pode ser liberado; a mensalidade do servidor continua a mesma.

Cada sugestão também diz quanto tira das estimativas dos projetos: a parte do preço de cada servidor que as reservas liberadas ocupam, dividida meio a meio entre CPU e memória sobre a capacidade que sobra depois do runtime, do mesmo jeito que os custos dos projetos são estimados. Ela diz de onde vem o preço (lido da Hostinger ou informado no Orbit), avisa quando um servidor não tem preço ou não custa nada, e mostra os dias e a completude das medições que sustentam a sugestão. Esses valores baixam as estimativas, não a mensalidade: só tirar um servidor faz isso, e a consolidação da frota simula essa saída.

O Ted responde Onde posso economizar? com quantas aplicações podem reduzir as reservas e qual é a maior, e abre esta revisão a partir da conversa.

Revisar mostra os valores atuais e propostos, a capacidade, os avisos e o rollout de cada aplicação. As sugestões de CPU e de memória da mesma aplicação viram uma única mudança de recursos; o limite de CPU e o número de instâncias ficam como estão. Nada muda durante a seleção ou a revisão. Quem só pode ver consegue olhar a evidência; aplicar exige o papel de desenvolvedor ou maior.

Aplicar mudanças em sequência espera uma operação confirmada com sucesso antes de passar para a próxima aplicação. Antes de cada envio, o Orbit busca as sugestões atuais e uma prévia de capacidade nova. Uma proposta ou um deploy diferente, uma indisponibilidade nova, menos capacidade disponível, um aviso novo, ou uma operação que falhou ou foi cancelada param as mudanças que faltam para outra revisão. Mais capacidade liberada por mudanças anteriores bem-sucedidas é aceita. Só sucessos confirmados entram no total liberado da rodada. Sucessos anteriores não são desfeitos quando uma mudança seguinte para.

Mantenha a janela de revisão aberta para a fila avançar. Parar após esta aplicação deixa a operação atual terminar e não inicia as demais. Fechar a janela, sair da página ou trocar de workspace para os próximos envios; uma operação já enviada continua e fica visível em Atividade. Se o resultado não puder ser confirmado, confira a Atividade antes de tentar de novo. Abrir a janela de novo carrega sugestões novas e não retoma sozinha uma rodada anterior.

Revisar a consolidação da frota ​

Administradores podem abrir Visão geral → Custos → Revisar consolidação da frota para simular a saída dos serviços de um servidor pago. O relatório cobre todos os workspaces, porque eles dividem a mesma capacidade física. Cada servidor é uma alternativa independente; não some as economias nem combine planos sem uma nova simulação. Nada é movido, removido ou cancelado por esta tela.

A simulação mantém as reservas de CPU e memória, o máximo de instâncias do autoscaling e o número de servidores de cada serviço. Ela separa em cada servidor que fica a margem estimada do runtime (1 GB e 250m) e a margem de builds (1 GB e 1000m). Ela confere o posicionamento combinado e a recuperação depois da perda de mais um servidor, incluindo os serviços vizinhos. Ela nunca cria alta disponibilidade para um serviço que hoje está num servidor só. O planejador pode voltar atrás quando um encaixe impede outro serviço de caber; quando chega ao limite de busca, o resultado aparece como inconclusivo.

Abra os destinos de cada aplicação para ver incompatibilidades ou falta de capacidade. As arquiteturas precisam ser iguais à do servidor de origem, e os servidores envolvidos precisam de relatórios saudáveis do agente e do runtime de no máximo 90 segundos atrás. O servidor original da instalação, os membros do plano de controle, as cópias do Orbit e os servidores de entrada de tráfego exigem um trabalho de infraestrutura à parte. Bancos, armazenamento de objetos e artefatos estáticos publicados precisam de uma migração de dados e não recebem um plano de mudança.

Economia possível depois do cancelamento usa o preço registrado inteiro de um servidor candidato. O relatório separa preços informados por você de preços lidos da Hostinger. Um servidor bloqueado mostra o custo atual, não uma economia alcançável. Preços desconhecidos continuam desconhecidos; o servidor ainda conta na capacidade de posicionamento. Desligar uma máquina ou liberar reservas não para a cobrança dela.

Isto é uma foto das reservas, não um inventário completo do Kubernetes nem uma autorização para remover hardware. Disponibilidade das imagens, volumes locais, espaço em disco, taints, o agendamento de verdade, DNS e HTTPS, tráfego e as condições de cancelamento ainda precisam ser conferidos antes de qualquer migração. Papéis de infraestrutura continuam bloqueando mesmo quando os posicionamentos das aplicações cabem. Uma operação em andamento bloqueia a recomendação até terminar e você atualizar. Diferente das reduções de recursos, esta simulação não deduz reservas menores a partir de sete dias de uso: ela mantém as reservas atuais.

Horário de funcionamento para staging e previews ​

Abra Configurações → Automações → Horário de funcionamento de uma aplicação para escolher os dias e horários em que ela roda. Isso vale para containers publicados em ambientes de staging e de preview, workers incluídos. Produção, desenvolvimento, bancos, jobs agendados e a hospedagem estática compartilhada ficam de fora. Uma aplicação nova não tem horário; cada aplicação elegível é configurada separadamente.

Os horários seguem o fuso horário da instalação, inclusive as mudanças de horário de verão. Mudar o fuso da instalação muda esses horários também. O horário de abertura entra e o de fechamento não. Uma janela que atravessa a noite, como sexta das 22:00 às 02:00, termina no sábado. O Orbit confere os horários a cada 30 segundos e reconcilia a política salva depois de um reinício.

Revisar horário explica se a aplicação vai pausar ou rodar na hora. Aplicar exige o papel de desenvolvedor ou maior. Pausar remove o autoscaler da aplicação e reduz as instâncias a zero, esperando todos os pods sumirem antes de liberar as reservas de CPU e memória. As réplicas desejadas, as reservas e limites de CPU, a memória e o autoscaling ficam guardados. Bancos, volumes, domínios e dados guardados não são apagados. O endereço da aplicação fica fora do ar enquanto ela está pausada; pausas planejadas não geram falhas nas checagens de uptime.

Na próxima abertura, o Orbit confere a capacidade disponível, devolve as instâncias e o autoscaling guardados e verifica se ficaram prontas antes de confirmar o sucesso. Se outros serviços ocuparam a capacidade liberada, acordar falha de forma visível e a aplicação continua pausada. Transições automáticas que falham tentam de novo depois de cinco minutos. A capacidade não é garantida para a próxima abertura. Uma transição que falhou ou foi cancelada com resultado incerto no cluster mantém as reservas até ser reconciliada.

Acordar agora · 2 horas passa por cima do horário temporariamente. Depois das duas horas, o horário normal volta a valer; uma janela aberta mantém a aplicação rodando. Desligar o horário também acorda a aplicação, sujeito às checagens de capacidade e de prontidão.

Acorde a aplicação antes de publicar ou de mudar o runtime dela. Pushes recebidos durante a pausa não publicam e não ficam numa fila para depois. Acordar devolve a última versão publicada; publique de novo depois de acordar para levar commits mais novos. As operações de pausar e acordar aparecem na Atividade com o resultado verificado.

Pausar libera CPU e memória para outros trabalhos. A mensalidade do servidor continua a mesma. A consolidação da frota não propõe mover aplicações com horário ligado, porque a capacidade liberada por uma aplicação dormindo é temporária.

Falta de memória ​

Uma aplicação morta por passar do limite de memória duas vezes em 30 minutos ganha um incidente e aparece como degradada. O incidente mostra os reinícios, o gráfico de memória com o limite, o tráfego de entrada e o último deploy, cada um com a sua origem, e separa as causas possíveis dos fatos. Aumentar o limite por ali passa pela prévia de recursos; o Orbit então observa por 10 minutos e resolve o incidente se nenhum reinício acontecer. Sem correção, um incidente se resolve depois de uma hora sem reinícios.

Autoscaling ​

Escalar automaticamente nas mesmas Configurações faz as instâncias acompanharem a CPU, entre um mínimo e um máximo.

  • Instâncias são adicionadas enquanto a CPU média fica acima da fração alvo da reserva de CPU, e removidas depois que ela fica abaixo por 5 minutos.
  • A prévia conta a memória e a reserva de CPU no máximo de instâncias; outras mudanças naquele servidor também contam esse máximo. O consumo até o limite continua dependendo da CPU disponível.
  • Alterar a reserva muda o alvo do autoscaling: 70% de 50m corresponde a 35m por instância. A prévia avisa antes de aplicar. Os gráficos de CPU do serviço continuam mostrando porcentagem do limite.
  • Deploys e mudanças de recursos mantêm o número de instâncias que o autoscaler escolheu, dentro dos novos limites.
  • As métricas do serviço mostram um gráfico de Instâncias, e a linha do tempo lista cada vez que instâncias foram adicionadas ou removidas, com a CPU que levou a isso.
  • Limites: até 10 instâncias, alvo entre 20% e 95%, e jobs agendados não escalam. Todas as instâncias rodam no servidor da aplicação, então o autoscaling lida com carga, não com a perda desse servidor.

Sob carga HTTP num cluster de teste, uma aplicação foi de 1 para 3 instâncias em menos de 2 minutos e voltou para 1 em até 10 minutos depois que a carga parou.

Servidores ​

Uma aplicação roda num servidor só por padrão. Com mais de um servidor, as Configurações dela ganham a seção Servidores, para mudá-la de servidor ou espalhar as instâncias entre vários.

  • Espalhando: as instâncias se dividem por igual, uma por servidor quando possível. O autoscaling continua espalhando as que ele adiciona.
  • Quando um servidor se perde: as instâncias dele voltam nos outros servidores. Num cluster de teste com três servidores isso levou cerca de um minuto e meio, a maior parte esperando o Kubernetes declarar o servidor perdido. As outras instâncias continuam atendendo enquanto isso, mas as requisições que o roteador ainda manda para as perdidas falham até lá: 8 de 71 requisições, uma por segundo, nos primeiros 52 segundos do teste.
  • A prévia mostra quantas instâncias cada servidor teria no máximo do autoscaling e o que fica livre, e recusa um servidor que não está pronto, que não tem espaço ou que tem outra arquitetura de CPU que a de uma imagem compilada.
  • Capacidade de recuperação: a prévia simula a perda de cada servidor selecionado, incluindo as outras aplicações que mudariam junto e o máximo do autoscaling. Uma alteração na distribuição ou nos recursos da própria aplicação é recusada se suas instâncias não couberem. Mudanças numa aplicação vizinha ou num banco podem prosseguir quando cabem normalmente, mas a prévia avisa quais aplicações perderiam capacidade de recuperação, com a falta de CPU e memória.
  • Verificação contínua: o Orbit recalcula após mudanças nos serviços ou servidores e a cada minuto. A seção Servidores da aplicação mostra o resultado atual. Se faltar capacidade, um aviso identifica o cenário de perda e o servidor sem espaço; canais de notificação podem acompanhá-lo. O aviso se resolve quando a capacidade volta. Quando possível, ele sugere um máximo de instâncias que cabe em todos os cenários, ou mover aplicações e aumentar a capacidade. Essa verificação considera reservas; rede, compatibilidade da imagem, réplicas de bancos e entrada do tráfego também influenciam a recuperação.
  • Imagens: uma imagem compilada é copiada para cada servidor escolhido antes de uma instância começar ali. Imagens de um registry são baixadas por cada servidor.
  • O que isso não cobre:
    • com uma instância só, a aplicação para até essa instância subir em outro servidor, então use duas ou mais;
    • o tráfego só entra pelo servidor principal, a menos que outros servidores o recebam, e mesmo assim perder o principal faz falhar as requisições enviadas para as instâncias dele;
    • mover instâncias depende do plano de controle do cluster, que roda só no servidor principal a menos que você o rode em três servidores.

Mais de uma aplicação ​

Um projeto pode rodar várias aplicações no mesmo ambiente, como uma API e um painel de administração. Adicionar aplicação, em Boas companhias, abre os mesmos passos de um projeto novo, a partir de um repositório ou de uma imagem. No fim aparecem os bancos do ambiente: cada um que você marcar é conectado à nova aplicação como referência, então duas aplicações podem usar o mesmo banco desde o primeiro deploy.

Workers e jobs ​

Adicione um worker ou um job na Visão geral de uma aplicação, em Boas companhias. Ele reaproveita o código e as configurações da aplicação, com nome e comando de início próprios, no mesmo ambiente.

  • Um worker não tem endereço. O deploy dele falha se ele reiniciar ou sair nos primeiros 10 segundos.
  • Um job roda no seu agendamento em UTC, ou na hora com Rodar agora. Quando uma execução ainda está rodando no próximo horário, esse horário é pulado. O Orbit guarda as últimas cinco execuções com sucesso e as cinco com falha, com saída e código de saída, e o job aparece como degradado enquanto a última execução tiver falhado. Um agendamento novo vale a partir do próximo deploy.
sh
sudo k3s kubectl -n orbit-<projeto>-production get cronjobs,jobs,pods
sudo k3s kubectl -n orbit-<projeto>-production logs job/<execução>

Builds ​

  • Uma aplicação de repositório é compilada no servidor a cada deploy de um commit novo. Publicar de novo o mesmo commit com as mesmas configurações reaproveita a imagem.
  • O primeiro build de cada stack baixa as imagens base: conte alguns minutos para Next.js ou Nuxt e menos de um minuto para sites pequenos em Go, Python ou estáticos. Os builds seguintes do mesmo projeto são mais rápidos.
  • Os builds rodam no servidor onde o Orbit ativo está, para a arquitetura dos servidores da aplicação (detalhes). Um build de Next.js ou Nuxt pode usar 1,5 GB de memória por um ou dois minutos, então um servidor de 2 GB não deve fazer build quando está com pouca memória.
  • Cada serviço guarda as suas dez imagens mais recentes, e o cache de build se limpa sozinho conforme o disco enche.
  • Os builds partem de uma cópia do commit, sem a pasta .git e sem o programa git. Um passo de build que lê o histórico do git falha, e o deploy explica o motivo: desligue o que lê esse histórico, como o lastUpdated na configuração do VitePress. O Orbit também avisa sobre o lastUpdated quando detecta o repositório.
