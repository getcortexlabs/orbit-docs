Nesta página

Bancos de dados ​

O Orbit roda PostgreSQL, MySQL 8.4, MongoDB 8.0, Redis 7.4, Neo4j Community e OpenSearch ao lado das suas aplicações, cada um com um volume no disco do servidor em /var/lib/rancher/k3s/storage. Bancos PostgreSQL novos rodam no CloudNativePG. Arquivos, como uploads, ficam em Spaces.

Os dados ficam no disco de um servidor

Se esse servidor for perdido, os dados vão junto, a menos que os backups vão para um armazenamento externo. Os tamanhos de armazenamento são pedidos, não impostos.

Criar um banco de dados ​

Abra Bancos de dados → Criar banco de dados. Com Independente, o banco fica diretamente no workspace atual, mesmo sem projetos. Com Em um projeto, você escolhe o projeto e o ambiente. Nos dois casos, escolha servidor, memória, armazenamento e, nos motores com backup gerenciado, o agendamento inicial.

Conectando aplicações ​

  • Bancos de projeto aceitam aplicações do mesmo ambiente. Bancos independentes aceitam conexões explícitas de aplicações de qualquer projeto do mesmo workspace. Outros workspaces não conseguem vê-los nem se conectar. O endereço é <nome>.orbit-<projeto>-<ambiente>.svc.cluster.local para bancos de projeto e <nome>.orbit-workspace-<sufixo-do-id-do-workspace>-production.svc.cluster.local para bancos independentes. Para os motores relacionais e o MongoDB, o Orbit cria o banco e o usuário com o nome do serviço (trocando - por _) e gera uma senha aleatória.
  • Conectar numa aplicação adiciona uma referência como DATABASE_URL (MONGODB_URL para MongoDB, REDIS_URL para Redis, quatro delas para um Space) às variáveis dela. O valor é preenchido no deploy da aplicação, então publique de novo depois de conectar. A página do banco lista as aplicações que o usam.
  • O mesmo banco pode atender várias aplicações do ambiente: conecte cada uma, ou marque o banco ao adicionar uma aplicação ao projeto.

Neo4j e OpenSearch ​

Os dois motores rodam em instância única com volume persistente. Escolha Independente para conectar aplicações de vários projetos do mesmo workspace ou Em um projeto para limitar as conexões a um ambiente.

MotorMemória mínimaConexão da aplicação
Neo4j Community 5.26 LTS1 GiBConecte o driver usando NEO4J_URI e passe NEO4J_USERNAME e NEO4J_PASSWORD na autenticação. O Bolt escuta na porta 7687. O banco inicial e o usuário se chamam neo4j.
OpenSearch 32 GiBUse o endereço REST autenticado em OPENSEARCH_URL, na porta 9200. A aplicação pode criar e consultar índices. Aplicações conectadas à mesma instância compartilham credenciais e índices.

Os endereços são privados. Mostrar credenciais fornece um túnel SSH para clientes no computador. Para recuperação, planeje um dump offline do Neo4j ou um snapshot do OpenSearch com acesso de operador. Backups agendados, importação, restauração e rotação de senha pelo Orbit ainda estão indisponíveis para esses motores. O volume conserva os dados quando o pod reinicia. A perda do servidor pode causar a perda do volume.

Explorar um grafo Neo4j ​

Abra um banco Neo4j, selecione Dados e depois Ver dados. O explorador mostra uma amostra somente leitura de até 80 nós e 160 relações. As contagens representam a visualização atual, não o banco inteiro.

Busque pelo texto das propriedades dos nós ou informe um rótulo exato para reduzir a amostra. Selecione um nó para inspecionar seus rótulos e propriedades; Explorar conexões carrega esse nó e seus vizinhos imediatos. Selecione uma relação para ver sua direção, tipo e propriedades. Voltar à visão geral limpa a vizinhança e os filtros. Arraste o grafo para movê-lo, use os controles de zoom ou mude para Registros para navegar em lista. Nós, relações e controles também podem ser selecionados pelo teclado.

O grafo usa transições curtas com mola no zoom e nas mudanças de visualização. A seleção desenha as conexões uma vez. Com movimento reduzido, as mudanças são imediatas; ao sair da página, as animações param.

As propriedades são prévias: até 50 chaves, 1.024 caracteres por valor e 50 itens por lista. Um aviso de limite indica que existem mais dados fora da amostra. Refine a busca ou explore uma vizinhança. Se uma leitura falhar, o grafo anterior e a busca continuam disponíveis para tentar novamente. Bancos novos mostram um estado vazio até seu aplicativo ou o terminal Cypher gravar nós.

O Orbit executa leituras fixas e parametrizadas pelo pod privado, com limite de 15 segundos para o processo. Não expõe o Bolt, não habilita HTTP, não envia credenciais ao navegador e não aceita Cypher arbitrário nesta visualização. O console de demonstração usa dados de exemplo.

Buscar documentos no OpenSearch ​

Abra um banco OpenSearch, selecione Dados e depois Ver dados. A faixa de índices mostra até 100 índices abertos que não são do sistema, com estado e contagens de itens indexados. Essas contagens incluem documentos aninhados e podem diferir do número de resultados da busca. Selecione um índice ou busque nos índices listados.

A busca aceita palavras, frases entre aspas e * no final de um prefixo, usando a sintaxe de simple query string. Os resultados são ordenados por relevância, com 25 documentos por página e navegação pelos primeiros 1.000 resultados. A contagem é exata até 10.000 ocorrências; um + indica um limite inferior. Refine a consulta quando chegar ao limite. Quando nada corresponde, Mostrar todos os documentos limpa a busca e o índice escolhido.

Selecione um documento pelo ponteiro ou teclado para inspecionar os campos, alternar para JSON formatado ou copiar a prévia do conteúdo. Documentos grandes são reduzidos mantendo JSON válido, com um aviso. Se uma leitura falhar, os últimos resultados e a busca continuam disponíveis para tentar novamente. Bancos vazios mostram como adicionar o primeiro índice pela aplicação.

O Orbit envia requisições fixas de leitura pelo pod privado. As credenciais ficam nele, a busca não aceita DSL ou scripts arbitrários, as consultas têm limite de dez segundos e as respostas de rede são limitadas a 8 MiB. A demonstração local usa documentos de exemplo. As transições param imediatamente com movimento reduzido ou quando a página está oculta.

Conectando do seu computador ​

Mostrar credenciais na página do banco revela usuário, senha e banco, com dois caminhos:

  • Um túnel SSH pelo servidor onde o banco roda, que mantém o banco privado: rode o comando mostrado e conecte psql, DBeaver ou TablePlus em 127.0.0.1:15432 (13306 para MySQL, 37017 para MongoDB, 16379 para Redis, 13900 para um Space). O túnel vai até o endereço do banco dentro do cluster, então qualquer cliente com túnel SSH consegue salvar: o servidor como host SSH, e esse endereço e porta como host do banco.
  • Abrir na Lily DB salva o banco na Lily DB com esse túnel configurado. A Lily abre o túnel sozinha a cada conexão e pede a senha uma vez.
  • O endereço público, quando o acesso é público.

Cada revelação fica registrada na Atividade.

Vendo os dados ​

Ver dados abre um explorador próprio para cada motor. PostgreSQL e MySQL mostram a lista de tabelas, linhas e tamanhos estimados, e páginas de 50 registros. O MongoDB mostra coleções com uma coluna por campo de primeiro nível dos documentos. A primeira tabela disponível abre automaticamente; filtre a lista, troque de tabela ou abra uma consulta somente leitura. As colunas ficam numa grade com rolagem em telas pequenas.

O Redis percorre as chaves por padrão em lotes. Selecione uma chave para inspecionar tipo, tamanho, expiração e valor. Strings com JSON válido alternam entre JSON formatado e texto original; hashes, listas, conjuntos, conjuntos ordenados e streams usam a grade. Carregar mais continua a busca mesmo quando um lote não encontra correspondências. Os valores são prévias limitadas, não exportações.

Transições curtas acompanham as seleções. Teclado, foco visível e movimento reduzido funcionam em toda a tela. Uma falha ao ler tabela ou chave preserva o valor anterior; uma consulta que falha preserva o texto e o último resultado obtido, com um aviso de erro.

  • Consultas: a aba Consulta roda um comando SQL (um SELECT, WITH, VALUES ou TABLE) numa transação somente leitura. Ela para depois de 15 segundos, devolve até 500 linhas e corta células em 1.000 caracteres. Cada consulta fica registrada na Atividade com o texto.
  • Consultas no MongoDB são um find na sintaxe do shell, como db.orders.find({status: "paid"}).sort({_id: -1}).limit(20), com projeção, sort, skip e limit opcionais. O próprio Orbit lê a consulta e não roda mais nada, então um método que escreve é recusado.
  • Somente leitura é uma proteção, não uma permissão: um comando que escreve é recusado antes de rodar, e a transação pega o resto. Para mudar dados, conecte do seu computador.

Shell ​

Shell, na página de um banco, abre o cliente do próprio banco, psql, mysql, mongosh ou redis-cli, dentro da instância primária, conectado como o usuário do banco. Diferente de ver os dados, ele escreve, então exige o papel de admin. Fecha depois de 15 minutos sem digitar, quando você sai da conta ou quando seu papel muda, e a atividade registra quem abriu e fechou; o que você digita nunca é gravado. Spaces não têm shell.

Acesso público ​

Tornar um banco público o publica no IP do servidor, na porta do motor (5432, 3306, 27017, 6379 ou 3900, ou a próxima livre). Abra essa porta no firewall do seu provedor só para os endereços que precisam, e volte o banco para privado quando não precisarem mais.

Memória e armazenamento ​

Memória e armazenamento, na página do banco, muda os dois com uma prévia antes: quanta memória fica livre no servidor depois da mudança, como o banco reinicia e o que observar. Uma mudança que não cabe no servidor é recusada antes de qualquer reinício.

  • Um novo limite de memória reinicia o banco uma vez. Com uma instância, ele fica indisponível durante o reinício, normalmente menos de um minuto. Com réplicas no CloudNativePG, as réplicas reiniciam primeiro e depois a primária passa para uma delas. O Orbit espera até que todas as instâncias rodem com o novo limite e respondam com as credenciais; se isso não acontecer, o limite anterior volta.
  • A memória do próprio PostgreSQL acompanha o limite. Um PostgreSQL no CloudNativePG com 1 GB ou mais mantém um quarto da memória como buffers compartilhados (shared_buffers), diz ao planejador que pode contar com três quartos como cache (effective_cache_size), e recebe um dezesseis avos para manutenção, como VACUUM e criação de índices (maintenance_work_mem, até 1 GB), e, para cada ordenação ou hash, uma fatia que cem conexões podem usar ao mesmo tempo (work_mem, de 4 a 64 MB). Um banco de 4 GB recebe 1 GB, 3 GB, 256 MB e 10 MB. Abaixo de 1 GB os padrões do PostgreSQL já estão nessa proporção e ficam. Essas configurações só mudam com um reinício que você pediu: quando o banco é criado, quando a memória dele muda e quando você as aplica a um banco de antes. Um banco criado antes de o Orbit dimensionar essas configurações roda com os padrões do PostgreSQL, 128 MB de buffers compartilhados e 4 MB por ordenação seja qual for o tamanho. Num banco assim com 1 GB ou mais, Memória e armazenamento avisa isso, e Revisar o reinício abre a prévia do tamanho que ele já tem. Aplicar reinicia o banco uma vez, como um novo limite de memória, e as configurações anteriores voltam se o PostgreSQL não subir com as novas. Mudar a memória dele também dimensiona as configurações, e a prévia mostra o que o PostgreSQL recebe. Mudar só o armazenamento planejado não reinicia nada e as deixa como estão.
  • O armazenamento é um plano, não um redimensionamento. Volumes locais não são impostos nem redimensionados, então o armazenamento planejado é o que o Orbit reserva e usa no aviso de armazenamento. O volume mantém o tamanho com que foi criado, e a página avisa quando os dois ficam diferentes.
  • Ficar sem memória abre um incidente, como acontece com as aplicações: depois de dois reinícios por memória em 30 minutos, o incidente mostra as evidências e Aumentar o limite passa pela mesma prévia.
  • O formulário aplica a memória mínima do motor escolhido. Aumente o limite aqui conforme o uso do banco crescer.

Sugestões de tamanho ​

O mesmo painel pode sugerir um tamanho de memória menor. O Orbit lê o uso de memória de cada instância a cada 30 segundos e guarda oito dias de leituras; a sugestão usa a maior leitura de qualquer instância nos últimos sete dias no tamanho atual, porque um redimensionamento muda quanto o motor usa. Ela soma uma margem de 50%, ou de 100% para Neo4j e OpenSearch, cujo heap é uma fração fixa do tamanho e falha na hora quando fica pequeno demais, e para Redis, que guarda todos os dados na memória. Ela arredonda para cima em múltiplos de 64 MB e nunca fica abaixo do mínimo do motor. Precisa de pelo menos 95% de cobertura, nenhuma lacuna maior que cinco minutos e uma leitura recente; um reinício por falta de memória nos últimos sete dias ou um incidente de memória aberto bloqueiam a sugestão.

As configurações que um motor calcula a partir do tamanho são gravadas de novo quando ele reinicia com o novo tamanho, então diminuem junto: o Neo4j usa um quarto para o heap e um quarto para o cache de páginas, o OpenSearch metade para o heap, o MySQL um terço para o buffer pool e o MongoDB metade do que passa de 512 MB para o cache. PostgreSQL e Redis não têm essa configuração. A sugestão mostra os valores no tamanho atual e no proposto. Revisar sugestão de tamanho preenche o formulário; aplicar passa pela mesma prévia e pelo mesmo reinício de qualquer outra mudança, e os sete dias recomeçam no novo tamanho.

O que ocupa o espaço ​

O que ocupa o espaço, em Armazenamento na página do banco, mede o volume de dentro do banco quando a página abre e de novo com Medir de novo. Precisa do papel de desenvolvedor, como ver os dados.

  • PostgreSQL se divide nos dados dos seus bancos, no WAL e no resto. O WAL é o log que o PostgreSQL escreve antes de mudar os dados. Ele costuma ficar entre algumas centenas de MB e pouco mais de 1 GB, conforme wal_keep_size e max_wal_size permitem, e a página avisa quando é só isso.
  • Quando o WAL cresce, a página diz por quê:
    • O arquivamento falha. Com a recuperação até um momento, o PostgreSQL guarda cada arquivo de WAL até ele chegar ao armazenamento de backup. Se o armazenamento recusa (chaves erradas, bucket apagado, disco cheio), o WAL se acumula e o volume pode passar do tamanho planejado. A página mostra quando o último arquivo foi arquivado, o arquivo que falha e o erro que o arquivador dá, como um endpoint que ele não alcança ou uma chave sem permissão de escrita. Corrija o armazenamento e o WAL que espera é enviado e removido.
    • O arquivamento fica para trás quando o banco escreve WAL mais rápido do que ele é enviado.
    • Um slot de replicação que ninguém lê guarda cada arquivo de WAL desde que o leitor saiu. Se nenhuma réplica ou ferramenta precisa dele, remova com pg_drop_replication_slot.
  • MySQL se divide em dados, logs binários e o resto. Por padrão o MySQL guarda os logs binários por 30 dias, o que pode ocupar mais que os dados; se nenhuma réplica precisa deles, diminua binlog_expire_logs_seconds ou rode PURGE BINARY LOGS.
  • Maiores tabelas lista as dez maiores, com as linhas mortas no PostgreSQL: as linhas que updates e deletes deixam para trás até o VACUUM limpar. Uma tabela com muitas linhas mortas é apontada. O autovacuum deixa esse espaço livre para linhas novas; o VACUUM FULL devolve ao disco, mas trava a tabela enquanto roda.
  • Redis e MongoDB mostram só o total. Um Space mostra o que os buckets guardam e quantos arquivos são, os dois vindos dos contadores que o Garage mantém, então nada varre o volume nem lista o bucket.

Trocando credenciais ​

O Orbit troca a senha, atualiza todas as aplicações que usam o banco (inclusive as versões guardadas para rollback) e as reinicia, e depois confere que a senha antiga é recusada. Aplicações que leem a senha de outro lugar que não as variáveis do Orbit precisam ser atualizadas à mão. Um Space mantém as chaves; veja Spaces.

Upgrades ​

O Orbit faz backup do banco antes, roda a versão nova e confere que ela tem as mesmas tabelas e linhas (ou chaves).

  • No CloudNativePG, o PostgreSQL faz upgrade no lugar com pg_upgrade, e a versão anterior volta se isso falhar.
  • No runtime StatefulSet, mais antigo, levar o PostgreSQL para uma versão major nova restaura o backup num volume novo, então demora mais ou menos o mesmo que um restore. Um upgrade que falha sobe a versão anterior de novo com os seus próprios dados.

PostgreSQL no CloudNativePG ​

O Orbit instala o operador CloudNativePG e o plugin Barman Cloud quando o primeiro banco PostgreSQL é criado. O CloudNativePG traz réplicas em outros servidores e recuperação até um momento.

Movendo um banco antigo: um banco PostgreSQL criado antes do CloudNativePG mostra Mover para o CloudNativePG na sua página. A prévia diz por quanto tempo as escritas pausam, para onde vai o backup, se o servidor tem disco para uma segunda cópia e que o volume atual é mantido.

  1. O Orbit faz backup do banco.
  2. Ele sobe o cluster ao lado do banco atual.
  3. Ele pausa as escritas (as leituras continuam) e copia os dados, conferindo que o cluster tem as mesmas tabelas e linhas.
  4. Ele aponta o endereço que as aplicações usam para o cluster e as reinicia, com as mesmas variáveis.

Se uma etapa falhar, o Orbit remove o cluster e o banco antigo volta a aceitar escritas. O volume antigo fica no servidor, congelado e somente leitura, até Remover volume antigo.

Quando o cluster não está saudável, a página do banco mostra o que o CloudNativePG informa: uma mudança em andamento, como um switchover ou uma réplica nova, mostra o banco como degradado, e um cluster que não consegue se recuperar, por exemplo depois de perder todas as instâncias, aparece como com falha, com o motivo dado pelo CloudNativePG. Um cluster com falha não consegue trazer os dados de volta das próprias instâncias: reconstrua a partir do arquivo ou restaure um backup verificado.

PostGIS e pgvector ​

Um banco PostgreSQL no CloudNativePG pode ter duas extensões, escolhidas na criação ou adicionadas depois em Recursos → Extensões:

ExtensãoPara quêO que adicionar faz
PostGISMapas, distâncias e áreas, com tipos de geografia e geometriaO banco passa para a imagem do PostGIS da mesma versão do PostgreSQL, então reinicia uma vez
pgvectorBusca por similaridade em embeddingsNada reinicia: ele já está na imagem que todo banco PostgreSQL roda

O Orbit cria a extensão no banco da aplicação, então a aplicação só usa: CREATE EXTENSION não precisa entrar nas suas migrations.

  • Adicionar o PostGIS a um banco em uso fecha as conexões por cerca de um minuto enquanto ele volta na nova imagem. Com réplicas, elas reiniciam primeiro e o primário por último. Se o banco não voltar, ou o PostgreSQL recusar a extensão, o Orbit coloca a imagem anterior de volta e o banco fica como estava.
  • Backups registram as extensões que o banco tinha. O teste de restauração roda na imagem que traz essas extensões, e restaurar no banco as traz de volta.
  • Fazer upgrade do PostgreSQL mantém as extensões: a nova versão também roda na imagem do PostGIS quando o banco o tem.
  • A contagem de linhas nos testes de restauração e nos upgrades deixa de fora as tabelas que pertencem a uma extensão, como a spatial_ref_sys do PostGIS.
  • Remover uma extensão é feito em SQL, com DROP EXTENSION. Isso também apaga o que foi construído sobre ela, por isso o Orbit não faz por você. Um banco que teve PostGIS continua rodando na imagem do PostGIS.
  • Uma extensão que você mesmo criou antes disso, como a vector, continua funcionando. Adicione aqui também, para o Orbit saber dela e testar os backups na imagem certa.
  • Um banco PostgreSQL que não foi movido para o CloudNativePG mostra por que não pode ter extensões. Mova-o primeiro, em Onde roda.

Um arquivo Compose que usa uma imagem postgis/postgis ou pgvector/pgvector vira um PostgreSQL gerenciado com essa extensão.

MySQL ​

  • Ele precisa de pelo menos 512 MB.
  • O usuário da aplicação só alcança o próprio banco. Um root local, cuja senha o Orbit guarda e nunca mostra, faz backups, restores e trocas de senha.
  • Um restore primeiro confere que o dump está completo e o carrega num banco de preparação, e só então troca o banco em uso, então um backup quebrado deixa os dados como estavam.

MongoDB ​

  • O MongoDB 8.0 roda numa instância só, sem replica set.
  • Ele precisa de pelo menos 512 MB. O cache dele fica com metade da memória acima de 512 MB, e no mínimo 256 MB.
  • Em servidores x86 ele precisa de um processador com AVX, e em servidores ARM de ARMv8.2-A, como todo MongoDB desde o 5.0. A maioria das VPS tem; um Raspberry Pi 4 não tem.
  • O usuário da aplicação lê, escreve e gerencia índices só no próprio banco. Um usuário root, cuja senha o Orbit guarda e nunca mostra, faz backups, restores e trocas de senha. Um banco não pode se chamar admin, config nem local.
  • O pod tem um segundo container, client, para o mongosh e as ferramentas do banco, com limite de memória próprio, então um backup ou uma consulta nunca tira memória do banco.
  • Os backups são arquivos do mongodump --archive --gzip. Uma instância só não tem snapshot de um momento, então o backup de um banco que está recebendo escritas lê uma coleção depois da outra.
  • Um restore carrega o arquivo num banco de preparação primeiro, e só então troca o banco em uso, então um backup quebrado deixa os dados como estavam.
  • O MongoDB Community Server é publicado sob a SSPL. O Orbit baixa a imagem oficial mongo no seu servidor; ele não distribui o MongoDB.

Conferir o PostgreSQL depois de redimensionar o servidor ​

O provedor pode desligar a máquina abruptamente e iniciar pela primeira vez um kernel já instalado. Antes de agendar o redimensionamento, confira o aviso de kernel pendente, o último backup verificado e os servidores que hospedam a instância primária e suas réplicas.

Depois da inicialização, compare o kernel em uso com a versão anterior. Na página do banco, acompanhe quantas instâncias ficaram prontas e confirme que a aplicação consegue ler do banco. Durante a recuperação, o operador pode conservar a indicação anterior de banco saudável. Falhas repetidas de checkpoint ou a mensagem “could not signal for checkpoint: Permission denied”, junto do aviso do AppArmor no servidor, indicam que a recuperação precisa de atenção: veja Containers e AppArmor. Guarde os logs do PostgreSQL e do kernel da mesma inicialização. Se o banco continuar indisponível, siga o plano de recuperação da manutenção com um kernel que já funcionou nesse servidor.
