Bancos de dados ​

O Orbit roda PostgreSQL, MySQL 8.4, MongoDB 8.0 e Redis 7.4 ao lado das suas aplicações, cada um com um volume no disco do servidor em /var/lib/rancher/k3s/storage. Bancos PostgreSQL novos rodam no CloudNativePG. Arquivos, como uploads, ficam em Spaces.

Os dados ficam no disco de um servidor

Se esse servidor for perdido, os dados vão junto, a menos que os backups vão para um armazenamento externo. Os tamanhos de armazenamento são pedidos, não impostos.

Conectando aplicações ​

  • Só aplicações do mesmo ambiente conseguem conectar. O endereço é <nome>.orbit-<projeto>-<ambiente>.svc.cluster.local. O Orbit cria o banco e o usuário com o nome do serviço (- vira _) e uma senha aleatória.
  • Conectar numa aplicação adiciona uma referência como DATABASE_URL (MONGODB_URL para MongoDB, REDIS_URL para Redis, quatro delas para um Space) às variáveis dela. O valor é preenchido no deploy da aplicação, então publique de novo depois de conectar. A página do banco lista as aplicações que o usam.
  • O mesmo banco pode atender várias aplicações do ambiente: conecte cada uma, ou marque o banco ao adicionar uma aplicação ao projeto.

Conectando do seu computador ​

Mostrar credenciais na página do banco revela usuário, senha e banco, com dois caminhos:

  • Um túnel SSH pelo servidor onde o banco roda, que mantém o banco privado: rode o comando mostrado e conecte psql, DBeaver ou TablePlus em 127.0.0.1:15432 (13306 para MySQL, 37017 para MongoDB, 16379 para Redis, 13900 para um Space). O túnel vai até o endereço do banco dentro do cluster, então qualquer cliente com túnel SSH consegue salvar: o servidor como host SSH, e esse endereço e porta como host do banco.
  • Abrir na Lily DB salva o banco na Lily DB com esse túnel configurado. A Lily abre o túnel sozinha a cada conexão e pede a senha uma vez.
  • O endereço público, quando o acesso é público.

Cada revelação fica registrada na Atividade.

Vendo os dados ​

Ver dados abre as tabelas, com linhas e tamanho estimados, e pagina as linhas delas. No MongoDB, mostra as coleções e os documentos, com uma coluna por campo de primeiro nível. No Redis, busca as chaves por padrão e mostra cada valor conforme o tipo.

  • Consultas: a aba Consulta roda um comando SQL (um SELECT, WITH, VALUES ou TABLE) numa transação somente leitura. Ela para depois de 15 segundos, devolve até 500 linhas e corta células em 1.000 caracteres. Cada consulta fica registrada na Atividade com o texto.
  • Consultas no MongoDB são um find na sintaxe do shell, como db.orders.find({status: "paid"}).sort({_id: -1}).limit(20), com projeção, sort, skip e limit opcionais. O próprio Orbit lê a consulta e não roda mais nada, então um método que escreve é recusado.
  • Somente leitura é uma proteção, não uma permissão: um comando que escreve é recusado antes de rodar, e a transação pega o resto. Para mudar dados, conecte do seu computador.

Shell ​

Shell, na página de um banco, abre o cliente do próprio banco, psql, mysql, mongosh ou redis-cli, dentro da instância primária, conectado como o usuário do banco. Diferente de ver os dados, ele escreve, então exige o papel de admin. Fecha depois de 15 minutos sem digitar, quando você sai da conta ou quando seu papel muda, e a atividade registra quem abriu e fechou; o que você digita nunca é gravado. Spaces não têm shell.

Acesso público ​

Tornar um banco público o publica no IP do servidor, na porta do motor (5432, 3306, 27017, 6379 ou 3900, ou a próxima livre). Abra essa porta no firewall do seu provedor só para os endereços que precisam, e volte o banco para privado quando não precisarem mais.

Memória e armazenamento ​

Memória e armazenamento, na página do banco, muda os dois com uma prévia antes: quanta memória fica livre no servidor depois da mudança, como o banco reinicia e o que observar. Uma mudança que não cabe no servidor é recusada antes de qualquer reinício.

  • Um novo limite de memória reinicia o banco uma vez. Com uma instância, ele fica indisponível durante o reinício, normalmente menos de um minuto. Com réplicas no CloudNativePG, as réplicas reiniciam primeiro e depois a primária passa para uma delas. O Orbit espera até que todas as instâncias rodem com o novo limite e respondam com as credenciais; se isso não acontecer, o limite anterior volta.
  • O armazenamento é um plano, não um redimensionamento. Volumes locais não são impostos nem redimensionados, então o armazenamento planejado é o que o Orbit reserva e usa no aviso de armazenamento. O volume mantém o tamanho com que foi criado, e a página avisa quando os dois ficam diferentes.
  • Ficar sem memória abre um incidente, como acontece com as aplicações: depois de dois reinícios por memória em 30 minutos, o incidente mostra as evidências e Aumentar o limite passa pela mesma prévia.
  • Bancos novos começam com até 1 GB; aumente aqui quando o banco precisar de mais.

O que ocupa o espaço ​

O que ocupa o espaço, em Armazenamento na página do banco, mede o volume de dentro do banco quando a página abre e de novo com Medir de novo. Precisa do papel de desenvolvedor, como ver os dados.

  • PostgreSQL se divide nos dados dos seus bancos, no WAL e no resto. O WAL é o log que o PostgreSQL escreve antes de mudar os dados. Ele costuma ficar entre algumas centenas de MB e pouco mais de 1 GB, conforme wal_keep_size e max_wal_size permitem, e a página avisa quando é só isso.
  • Quando o WAL cresce, a página diz por quê:
    • O arquivamento falha. Com a recuperação até um momento, o PostgreSQL guarda cada arquivo de WAL até ele chegar ao armazenamento de backup. Se o armazenamento recusa (chaves erradas, bucket apagado, disco cheio), o WAL se acumula e o volume pode passar do tamanho planejado. A página mostra quando o último arquivo foi arquivado, o arquivo que falha e o erro que o arquivador dá, como um endpoint que ele não alcança ou uma chave sem permissão de escrita. Corrija o armazenamento e o WAL que espera é enviado e removido.
    • O arquivamento fica para trás quando o banco escreve WAL mais rápido do que ele é enviado.
    • Um slot de replicação que ninguém lê guarda cada arquivo de WAL desde que o leitor saiu. Se nenhuma réplica ou ferramenta precisa dele, remova com pg_drop_replication_slot.
  • MySQL se divide em dados, logs binários e o resto. Por padrão o MySQL guarda os logs binários por 30 dias, o que pode ocupar mais que os dados; se nenhuma réplica precisa deles, diminua binlog_expire_logs_seconds ou rode PURGE BINARY LOGS.
  • Maiores tabelas lista as dez maiores, com as linhas mortas no PostgreSQL: as linhas que updates e deletes deixam para trás até o VACUUM limpar. Uma tabela com muitas linhas mortas é apontada. O autovacuum deixa esse espaço livre para linhas novas; o VACUUM FULL devolve ao disco, mas trava a tabela enquanto roda.
  • Redis e MongoDB mostram só o total, e um Space mostra quantos arquivos guarda.

Trocando credenciais ​

O Orbit troca a senha, atualiza todas as aplicações que usam o banco (inclusive as versões guardadas para rollback) e as reinicia, e depois confere que a senha antiga é recusada. Aplicações que leem a senha de outro lugar que não as variáveis do Orbit precisam ser atualizadas à mão. Um Space mantém as chaves; veja Spaces.

Upgrades ​

O Orbit faz backup do banco antes, roda a versão nova e confere que ela tem as mesmas tabelas e linhas (ou chaves).

  • No CloudNativePG, o PostgreSQL faz upgrade no lugar com pg_upgrade, e a versão anterior volta se isso falhar.
  • No runtime StatefulSet, mais antigo, levar o PostgreSQL para uma versão major nova restaura o backup num volume novo, então demora mais ou menos o mesmo que um restore. Um upgrade que falha sobe a versão anterior de novo com os seus próprios dados.

PostgreSQL no CloudNativePG ​

O Orbit instala o operador CloudNativePG e o plugin Barman Cloud quando o primeiro banco PostgreSQL é criado. O CloudNativePG traz réplicas em outros servidores e recuperação até um momento.

Movendo um banco antigo: um banco PostgreSQL criado antes do CloudNativePG mostra Mover para o CloudNativePG na sua página. A prévia diz por quanto tempo as escritas pausam, para onde vai o backup, se o servidor tem disco para uma segunda cópia e que o volume atual é mantido.

  1. O Orbit faz backup do banco.
  2. Ele sobe o cluster ao lado do banco atual.
  3. Ele pausa as escritas (as leituras continuam) e copia os dados, conferindo que o cluster tem as mesmas tabelas e linhas.
  4. Ele aponta o endereço que as aplicações usam para o cluster e as reinicia, com as mesmas variáveis.

Se uma etapa falhar, o Orbit remove o cluster e o banco antigo volta a aceitar escritas. O volume antigo fica no servidor, congelado e somente leitura, até Remover volume antigo.

Quando o cluster não está saudável, a página do banco mostra o que o CloudNativePG informa: uma mudança em andamento, como um switchover ou uma réplica nova, mostra o banco como degradado, e um cluster que não consegue se recuperar, por exemplo depois de perder todas as instâncias, aparece como com falha, com o motivo dado pelo CloudNativePG. Um cluster com falha não consegue trazer os dados de volta das próprias instâncias: reconstrua a partir do arquivo ou restaure um backup verificado.

MySQL ​

  • Ele precisa de pelo menos 512 MB.
  • O usuário da aplicação só alcança o próprio banco. Um root local, cuja senha o Orbit guarda e nunca mostra, faz backups, restores e trocas de senha.
  • Um restore primeiro confere que o dump está completo e o carrega num banco de preparação, e só então troca o banco em uso, então um backup quebrado deixa os dados como estavam.

MongoDB ​

  • O MongoDB 8.0 roda numa instância só, sem replica set.
  • Ele precisa de pelo menos 512 MB. O cache dele fica com metade da memória acima de 512 MB, e no mínimo 256 MB.
  • Em servidores x86 ele precisa de um processador com AVX, e em servidores ARM de ARMv8.2-A, como todo MongoDB desde o 5.0. A maioria das VPS tem; um Raspberry Pi 4 não tem.
  • O usuário da aplicação lê, escreve e gerencia índices só no próprio banco. Um usuário root, cuja senha o Orbit guarda e nunca mostra, faz backups, restores e trocas de senha. Um banco não pode se chamar admin, config nem local.
  • O pod tem um segundo container, client, para o mongosh e as ferramentas do banco, com limite de memória próprio, então um backup ou uma consulta nunca tira memória do banco.
  • Os backups são arquivos do mongodump --archive --gzip. Uma instância só não tem snapshot de um momento, então o backup de um banco que está recebendo escritas lê uma coleção depois da outra.
  • Um restore carrega o arquivo num banco de preparação primeiro, e só então troca o banco em uso, então um backup quebrado deixa os dados como estavam.
  • O MongoDB Community Server é publicado sob a SSPL. O Orbit baixa a imagem oficial mongo no seu servidor; ele não distribui o MongoDB.
