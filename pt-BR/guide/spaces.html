Spaces ​

Um Space dá às suas aplicações um bucket para arquivos, como uploads e imagens, atrás da API S3. Crie um em Spaces → Criar Space. O Orbit roda o Garage 2.4 para isso, num nó só e com os dados no disco do servidor, em /var/lib/rancher/k3s/storage. Como um banco, ele fica num ambiente, as aplicações o referenciam, e ele tem backup, teste de restauração e restore com a mesma política. A página dele mostra o endpoint, o bucket, as chaves e o que ele guarda: quantos arquivos e quanto espaço ocupam.

Os arquivos ficam no disco de um servidor

Se esse servidor se perder, os arquivos vão junto, a não ser que os backups vão para um armazenamento externo. O tamanho planejado é reservado, não imposto.

  • O bucket tem o nome do serviço, então o nome segue as regras do S3: pelo menos 3 caracteres, terminando com letra ou número. Ele precisa de pelo menos 256 MB.

  • Conectar adiciona quatro referências à aplicação, com o prefixo que você escolher (S3 por padrão):

    VariávelValor
    S3_ENDPOINThttp://<nome>.orbit-<projeto>-<ambiente>.svc.cluster.local:3900
    S3_BUCKETo bucket
    S3_ACCESS_KEY_IDa chave de acesso, que só alcança esse bucket
    S3_SECRET_ACCESS_KEYa chave secreta

  • No cliente S3, configure o endpoint, a região us-east-1 e requisições path-style: forcePathStyle: true no AWS SDK para JavaScript, addressing_style path no boto3. Com o AWS SDK para JavaScript v3:

    js
    import { PutObjectCommand, S3Client } from "@aws-sdk/client-s3";

const s3 = new S3Client({
  endpoint: process.env.S3_ENDPOINT,
  region: "us-east-1",
  forcePathStyle: true,
  credentials: {
    accessKeyId: process.env.S3_ACCESS_KEY_ID,
    secretAccessKey: process.env.S3_SECRET_ACCESS_KEY,
  },
});
await s3.send(
  new PutObjectCommand({
    Bucket: process.env.S3_BUCKET,
    Key: "hello.txt",
    Body: "hello",
  }),
);

  • As chaves ficam por toda a vida do Space. O Garage não consegue dar um segredo novo a uma chave, então um Space não tem Trocar credenciais. Para substituir as chaves, crie outro Space e copie os arquivos.

  • Os backups são um tar dos objetos do bucket com as chaves, o conteúdo e a data de modificação. Outros metadados, como um Content-Type próprio, voltam a ser definidos pela extensão do arquivo no restore. Um backup e um restore copiam os arquivos para o disco do servidor antes, então precisam de espaço livre do tamanho do bucket, mais ou menos.

  • O teste de restauração carrega o tar num Garage isolado e conta os objetos. Um restore deixa o bucket igual ao backup: objetos gravados depois dele são removidos, e um tar quebrado deixa o bucket como estava.

  • Importações recebem um tar dos arquivos, feito dentro da pasta deles, como aws s3 sync s3://bucket ./bucket && tar -cf bucket.tar -C ./bucket . (no macOS, comece o tar com COPYFILE_DISABLE=1 para ele não adicionar arquivos de metadados). Não há importação a partir de uma URL.

  • Explore os arquivos na aba Arquivos. Para enviar, baixar ou alterar um objeto, use um cliente S3 do seu computador; o túnel responde em 127.0.0.1:13900.

  • O acesso público publica o endpoint na porta 3900 em HTTP simples, então prefira o túnel.

  • O pod tem um segundo container, client, onde o rclone faz backups, restores e contagens com limite de memória próprio.

Na API um Space continua sendo um serviço database com o motor s3, então scripts e tokens de API que criavam armazenamento S3 antes continuam funcionando.

Explorar arquivos ​

Abra Spaces → seu Space → Arquivos para navegar pelas pastas, conferir tamanho e data de modificação dos objetos e copiar o caminho completo. A visualização é somente leitura e exige o papel developer, admin ou owner no workspace. As credenciais do armazenamento não chegam ao navegador.

A lista carrega 100 itens por vez. Carregar mais busca a próxima página; o filtro de nomes considera apenas os itens já carregados na pasta atual. O tamanho das pastas do bucket não é calculado.

Para sites estáticos, Publicações recentes dos sites oferece atalhos para até 20 deploys bem-sucedidos ainda retidos. Ver arquivos abre o conteúdo de um pacote registrado, após verificar SHA-256, quantidade e tamanho dos arquivos. Você pode navegar pelas pastas internas sem baixar o pacote novamente enquanto esta aba permanecer aberta. Os arquivos continuam dentro do pacote original no Space; nada é extraído ou alterado. Os arquivos internos não têm datas individuais de modificação.

Abrir uma publicação transfere o pacote compactado inteiro pelo controlador uma vez. Pacotes grandes podem demorar mais; a leitura tem limite de 60 segundos e no máximo duas leituras simultâneas por controlador. Valem os limites existentes de 1 GiB e 50.000 arquivos por publicação. Pacotes expirados, ausentes ou inválidos retornam um erro. Outros arquivos compactados enviados ao Space não podem ser abertos aqui. A tela lista metadados; use um cliente S3 para acessar o conteúdo ou baixar arquivos.

Publicar um site estático ​

Em uma aplicação Git com estratégia Estático, abra Projeto → Configurações → Publicação estática, selecione um Space e clique em Salvar e publicar. A mesma escolha aparece nas configurações avançadas de um novo projeto. Vários sites do mesmo workspace podem compartilhar um Space. Manter Container da aplicação selecionado preserva o fluxo atual.

O build continua no BuildKit, usando a pasta de saída detectada (dist ou a pasta do framework). O Orbit exporta os arquivos, sem criar uma imagem de execução. É obrigatório ter index.html. Os servidores estáticos compartilhados entregam os arquivos pelos domínios e HTTPS existentes. O resultado pode ser servido em nós ARM64 e x86_64; cada site e preview deixa de precisar de imagem e pod próprios.

Arquivos e versões separados ​

Cada deploy gera um arquivo compactado neste prefixo reservado:

text
_orbit/sites/v1/<instalação>/<workspace>/<projeto>/<ambiente>/<serviço>/<deploy>/<sha256>.tar.gz

Os uploads e outros objetos que já estão no bucket ficam no lugar. A publicação e a limpeza usam apenas as chaves exatas registradas no histórico. Nunca sincronizam, esvaziam ou apagam o bucket recursivamente. Reserve _orbit/sites/ para os arquivos do Orbit.

Cada servidor baixa os arquivos em uma pasta temporária, verifica checksum, quantidade e tamanho e instala a versão de uma vez. O tráfego muda depois que os servidores compartilhados prontos têm cópias completas. Se a publicação falhar, a rota anterior é restaurada. Na migração do container, o workload anterior fica com zero réplicas após o sucesso; os templates continuam disponíveis para voltar a uma versão antiga em container.

São mantidas as 10 últimas versões distintas de arquivos publicadas com sucesso, a versão ativa, publicações pendentes e até três artefatos de tentativas com falha. O rollback reutiliza os arquivos, sem rebuild. Versões expiradas continuam no histórico, mas não podem ser restauradas. Assets com hash das versões publicadas ainda retidas continuam disponíveis para quem está com uma página antiga aberta. Falhas na limpeza deixam os arquivos para outra tentativa. Excluir um site remove apenas os arquivos registrados dele e seu cache. Não é possível excluir um Space, seu ambiente ou projeto enquanto outro site retido depender dele.

Rotas e limites ​

  • SPA abre index.html quando uma rota de página não existe; 404 devolve erro para sites convencionais. JavaScript, CSS e imagens inexistentes retornam 404 nos dois modos.
  • HTML e arquivos sem hash no nome exigem revalidação. Assets identificados por hash recebem cache imutável de um ano. HEAD, requisições condicionais e intervalos de bytes são suportados.
  • Caminhos ocultos (exceto .well-known), node_modules, Dockerfile e orbit.json não são publicados. Links simbólicos e arquivos especiais são recusados. .dockerignore e .orbitignore se aplicam ao contexto do build.
  • Cada versão admite 1 GiB compactado e descompactado e 50 mil arquivos. Reserve espaço para as versões retidas no Space e em cada servidor que entrega o site.
  • Os logs de acesso são associados ao site e ao deploy. Terminal, autoscaling e gráficos de CPU/memória por aplicação não se aplicam ao runtime compartilhado.
  • Este fluxo serve arquivos estáticos públicos. Não executa SSR, funções de servidor, redirects/headers via orbit.json, nem inclui CDN externa. Use container quando a aplicação precisar de um processo de servidor.

Disponibilidade e atualização ​

Atualize o Orbit e os agentes juntos antes de usar a funcionalidade: o DaemonSet compartilhado inicia o binário nativo orbit-agent instalado em cada nó Linux. A versão é conferida antes da publicação. O cache fica em /var/lib/orbit/static-sites, separado dos buckets do usuário e das pastas de build.

Servidores com os arquivos preparados continuam atendendo se o Space ficar indisponível. Um servidor novo, sem cache, precisa do Space para baixar a versão. Esse cache não replica o Garage nem transforma um Space de nó único em armazenamento distribuído durável. Mantenha backups externos; restaurar um backup antigo do Space pode remover arquivos de deploys mais novos. O cache local não substitui esse backup.
